  1. **squad memory 目录未预建**：现 `ensureSquadDirSkeleton`（`stores/squad-store.ts` L169）没建 `.rocky_squad/memory.md` 父目录——但 `squads/<squadId>/.rocky_squad/state/` 已建（用于 scheduler.json 等），memory.md 与 state/ 同级，`.rocky_squad/` 已存在。首次 writeSquadEntry 时 atomicWriteSync 会创建 memory.md 本身（fs.writeFileSync 会创建缺失的文件但不建缺失的中间目录——`.rocky_squad/` 已存在故 OK）。**coder 编码时应验证**：squadCreated 后 `.rocky_squad/` 存在 = squad memory.md 可直接写。若发现建 squad 时 `.rocky_squad/` 未建（老 squad 数据），writeSquadEntry 需先 mkdirSync recursive（防御式）。
  2. **cron + 手动 lock 撞车行为**：cron fire 到点 acquire 失败 → 静默跳过 + **不推进 lastFiredAt**（本表约束列已注）。潜在场景：手动触发跑了 10 分钟，cron 每天 04:00 触发正好撞上，跳过后下 tick（30s 后）会再评估 due——若手动仍在跑，继续跳过；手动完成后 acquire 成功。**这是良性**（cron 会自愈到本窗口某个时刻真正 fire 一次）；但极端场景下 handler markDone 前手动跑 24h 会导致 cron 永远跳过本天窗口——**评估**：runConsolidationTier2 单次 forkedRun MAX_ITER=10 + 三段串行，实测应远快于 24h，此风险可控。coder 编码时应观察实际耗时。
  3. **AppTaskLock reconcileOnStartup no-op**：进程崩溃时如果 markDone/markFailed 未执行，重启后内存清空 → 锁自然 idle（对齐 SessionTaskLock 决策）。**风险**：崩溃前 handleConsolidationRun 已 fire-and-forget 但未 markFailed，重启后表面上锁 idle 但可能有 orphan runConsolidationTier2 Promise 已死——实际内存 only 语义天然容忍（进程死 = Promise 也死，无泄漏）。
  4. **squadDir 缺失时 skill resolver 后向兼容**：SessionConfig.squadId 只对 studio session 存在；非 studio session 传 squadDir=undefined 走原三层路径。playground rocky session 没 squadDir 也不需要——不误触发。
  5. **memory_squad mapper 无 squad 上下文**：非 studio session（playground）无 squadId → readMemorySources squad=[] → memory_squad mapper 空贡献 fragment（不注入）——正确行为，不误显示。
