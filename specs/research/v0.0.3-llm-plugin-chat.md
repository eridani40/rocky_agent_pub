## 1. provider/model 配置数据结构（refs vs spec）

### 1.1 spec 已定义（对照基线）

- `LlmProviderConfig`（per-instance，app_config `providers` 组一条 record 的 `data`）：`id` / `name(ProviderName)` / `baseUrl` / `credentials.key` / `pluginId` / `enabled` / `models[]`。见 `specs/tech/config/[P0]app_config.md:62-107` 与 `specs/tech/agent/providers_and_models/[P0]llm_provider_interface.md:25-33`。
- `LlmModelConfig`（`providers[].models[]` 一条）：`modelId` / `inputModalities` / `outputModalities` / `contextWindow` / `maxOutputTokens` / `paramConstraints` / `pricing` / `providerId` / `protocolId` / `default`。见 `[P0]llm_model_interface.md:20-48`。
- provider↔model 关联：**model 嵌套在 provider 实例的 `models[]` 数组里**（同一条 app_config record），`providerId` 隐式 = 该实例 id；`protocolId` 引用 `llm_protocol` 扩展点 ext impl。

### 1.2 refs/openclaw 的做法（与 spec 的差异点）

openclaw 用**单一 `Model` 对象**把「provider 实例数据」与「model 能力数据」合并，未做 spec 那种 provider/model 分离：

```typescript
// refs/openclaw/packages/llm-core/src/types.ts:582-632
export interface Model<TApi extends Api = Api> {
  id: string;          // wire 模型 id
  name: string;
  api: TApi;           // "anthropic-messages" 等 = spec 的 protocolId
  provider: Provider;  // string = spec 的 provider name (type)
  baseUrl: string;     // ← 直接挂在 model 上（spec 放 providerConfig）
  reasoning: boolean;
  input: ("text" | "image")[];
  cost: { input; output; cacheRead; cacheWrite };  // $/M token
  contextWindow: number;
  maxTokens: number;
  params?: Record<string, unknown>;
  headers?: Record<string, string>;   // ← 自定义 header 也挂在 model 上
  authHeader?: boolean;               // ← 走 Bearer 还是 x-api-key
  compat?: ...;                       // per-api 兼容开关
  mediaInput?: { image?: {...} };
}
```

**关键差异**：

| 字段 | openclaw | spec（v0.0.3） | 说明 |
|------|----------|----------------|------|
| `baseUrl` | `model.baseUrl` | `providerConfig.baseUrl` | spec 按 instance 归 provider，更合理（多 model 共享一个 baseUrl） |
| `headers` | `model.headers` | （extra headers → `ext_impl_config` overlay） | spec 把 extra header 归 provider impl 的 overlay |
| `authHeader` (Bearer vs x-api-key) | `model.authHeader` | 由 `providerConfig.name`（ProviderName）决定 | spec 按鉴权族分 type，openclaw 按 per-model 标志 |
| model 与 provider 关联 | `model.provider` (string type) | model 嵌套在 `providerConfig.models[]` | spec 是 per-instance 挂载，openclaw 是 per-type 引用 |
| model catalog 来源 | manifest `modelCatalog.providers.<id>.models[]` 静态 + runtime augment | app_config `providers[].models[]` 用户填 | openclaw 把 catalog 放 plugin manifest，spec 放 app_config |

**catalog 静态声明**（refs/openclaw 的模式，spec 可借鉴用于"预置模型模板"）：

```jsonc
// refs/openclaw/extensions/anthropic/openclaw.plugin.json:21-49（节选）
"providers": {
  "anthropic": {
    "baseUrl": "https://api.anthropic.com",
    "api": "anthropic-messages",       // = protocolId
    "models": [
      {
        "id": "claude-sonnet-4-6",
        "name": "Claude Sonnet 4.6",
        "reasoning": true,
        "input": ["text", "image"],
        "cost": { "input": 3, "output": 15, "cacheRead": 0.3, "cacheWrite": 3.75 },
        "contextWindow": 200000,
        "maxTokens": 64000
      }
    ]
  }
}
```

### 1.3 给 spec 的补充建议

spec 字段已足够，无需补。仅**提示 arch**：
- spec 未定义"model 模板/预置 catalog"概念（用户每次手填 modelId/contextWindow/pricing）。openclaw 的 manifest `modelCatalog` 是一个可参考的"预置模板"机制——但 v0.0.3 用户自填即可，**不建议引入**，避免增加复杂度。
- spec 的 `credentials: { key: string }` 是明文占位，注释指向 isolation 模块。**v0.0.3 维持明文即可**，isolation 留待后续。

## 3. openclaw plugin 静态注册参考

### 3.1 注册机制（refs 的做法）

openclaw 用**两层注册**：
1. **manifest 静态声明**（`openclaw.plugin.json`）：`id` / `providers`（provider id 数组）/ `modelCatalog`（静态 model 列表）/ `providerCatalogEntry`（discovery 入口）/ `setup`（onboarding）。**纯静态、可被 discovery 读、不跑代码**。见 `refs/openclaw/extensions/anthropic/openclaw.plugin.json:1-250`。
2. **runtime 注册**（插件 `register.runtime.ts` 导出 `registerAnthropicPlugin(api)`，行 873-875）：调 `api.registerProvider(buildAnthropicProvider())` 把运行时行为（auth/catalog/stream wrapper）注入 registry。`buildAnthropicProvider()` 返回 `ProviderPlugin`（`refs/openclaw/src/plugins/types.ts:1248-1394`），含 `id` / `label` / `auth[]` / `catalog` 等字段。

**LLM API 注册**（protocol+stream impl 合并注册，**这是 spec 的 `llm_protocol` ext impl 真正落地的地方**）：

```typescript
// refs/openclaw/packages/llm-runtime/src/api-registry.ts:77-90
export function registerApiProvider<TApi, TOptions>(
  provider: ApiProvider<TApi, TOptions>,
  sourceId?: string,    // 用于按 plugin 反注册
): void {
  apiProviderRegistry.set(provider.api, {   // Map<api, ...>，按 api id 索引
    provider: { api, stream: wrapStream(...), streamSimple: wrapStreamSimple(...) },
    sourceId,
  });
}
```

registry 是 `Map<api, ApiProviderInternal>`，**按 api id（= spec 的 protocolId）索引**，一个 api 一个实现（与 spec `llm_protocol` cardinality=`list` 略不同——openclaw 实际是 exclusive per-api）。

### 3.2 spec 对应（v0.0.3 静态注册怎么落地最自然）

spec 的 P0 模型（`specs/tech/plugin_system/[P0]ext_impl_and_manifest_interface.md`）：
- `PluginManifest`：`{ id, extImpls[], configSchema?, config? }`，纯静态。
- `ExtImpl`：`{ implId, point, impl, priority?, configSchema? }`，`impl` 是模块路径，导出**类**。
- 注册时机：`getExtensionImpls` 时框架实例化 impl 类（`[P1]plugin_lifecycle.md`，P0 可简化为"启动时实例化全部内置 impl"）。

**v0.0.3 P0 静态注册建议**（最自然落地）：

内置 plugin（如 `llm_anthropic`）的 manifest 声明 2 个 ext impl：

```jsonc
{
  "id": "llm_anthropic",
  "extImpls": [
    {
      "implId": "anthropic_compatible",
      "point": "llm_provider",
      "impl": "./provider.ts",          // 导出 class AnthropicCompatibleProvider implements LlmProvider
      "priority": 10
    },
    {
      "implId": "anthropic_messages",
      "point": "llm_protocol",
      "impl": "./protocol.ts",          // 导出 class AnthropicMessagesProtocol implements LlmProtocol
      "priority": 10
    }
  ]
}
```

- provider impl 类实现 `buildAuthHeaders(config) → { "x-api-key": ..., "anthropic-version": "2023-06-01" }`。
- protocol impl 类自承载 `path="/v1/messages"` / `contentType="application/json"` / `encode` / `parse` / `parseStream`。
- registry 启动时遍历所有内置 manifest，按 `point` 分桶，`llm_provider` / `llm_protocol` 都是 `list`（spec §4），按 `implId` 索引。

**与 openclaw 的差异**：
- openclaw 把 protocol 和 provider 的 stream impl **合并注册**到一个 `ApiProvider`（按 `api` id 索引）。spec 拆成 2 个扩展点（`llm_provider` 管 auth header、`llm_protocol` 管 encode/parse/stream），**更解耦**——同一 protocol 可跑多个 provider，同一 provider 可对接多 protocol。v0.0.3 坚持拆 2 个 point。
- openclaw manifest 字段更多（`providers` / `modelCatalog` / `setup` / `activation`），spec manifest 极简（`id` + `extImpls` + `configSchema`）。**v0.0.3 用 spec 极简版即可**，model catalog 由 app_config 用户填。

### 3.3 给 spec 的补充建议

spec manifest 已足够。**唯一建议**：spec 未明确"内置 plugin 放哪个目录 / 如何被 discovery 发现"。建议 arch 在 `specs/tech/plugin_system/[P0]plugin_manager_interface.md` 或新增文档约定：内置 plugin 放 `src/plugins/builtins/<id>/`（或 `plugins/<id>/`），manifest 文件名 `plugin.json`（或 `manifest.json`），discovery 启动时扫描该目录。**这是 arch 需要细化的点**。

## 4. chat 流式 UI 参考

### 4.1 refs/openclaw 的做法（不算理想参考）

openclaw UI（`refs/openclaw/ui/src/ui/`）是**重型 transcript 持久化系统**：
- 流式 event（`AssistantMessageEvent`，`refs/openclaw/packages/llm-core/src/types.ts:369-390`）由 backend 推送。
- UI 把 assistant 消息拍平成 text（`strip-thinking-tags.ts` 把 thinking 内容剥离/折叠），再 markdown 渲染。
- UI 层**没有直接的 event reducer**（grep `thinking_start|text_delta` 在 `ui/src/` 下无命中），而是 reload transcript 后整体渲染。
- thinking 控制是独立的"thinking level"选择器（`ui/src/ui/thinking.ts`），不是流式渲染逻辑。

**结论**：openclaw UI 不是"thinking/answer 分段流式渲染"的好参考——它把流式细节藏在了 transcript 系统里。

### 4.2 通用推荐模式（基于 anthropic SSE 协议天然分段）

anthropic SSE 的 `index` 字段天然支持"thinking block 和 answer block 是不同 index 的独立 block"，**UI 端最自然的模式**：

**数据模型**（前端 in-memory，req 要求"前端记录、不持久化、传 10 个 message"）：

```typescript
// 一条 assistant 消息 = 多个 part（按 index 顺序）
interface ChatMessage {
  id: string;
  role: "user" | "assistant";
  parts: ChatPart[];   // user 一般 1 个 text part；assistant 多个 part（thinking + answer）
}
interface ChatPart {
  id: string;          // = messageId + ":" + index，作为 React key（与 CLAUDE.md「以 message+part 为 key」原则一致）
  type: "text" | "thinking";
  content: string;     // 累积的 delta
  state: "streaming" | "done";
}
```

**SSE → UI reducer**（伪代码）：

```
on message_start:   创建空 assistant message
on content_block_start (text):      push 一个 { type:"text", content:"", state:"streaming" } part
on content_block_start (thinking):  push 一个 { type:"thinking", ... } part
on content_block_delta (text_delta):      找到对应 index 的 text part，append text
on content_block_delta (thinking_delta):  找到对应 index 的 thinking part，append thinking
on content_block_stop:  part.state = "done"
on message_delta:   记录 stop_reason / usage
on message_stop:    整条 message state = "done"
```

**渲染**：
- thinking part：折叠面板（默认折叠/展开可切），streaming 时显示光标。
- text part：markdown 渲染，streaming 时光标。
- part 用 `messageId:partIndex` 作 React key（不要用数组 index，因为 part 可能乱序到达——anthropic SSE 的 `index` 是协议层稳定 id）。

### 4.3 给 spec 的补充建议

- spec `[P0]agent_message_interface.md` 已定义 `Message` / `ContentBlock`（text/thinking/tool_use），但**未定义前端 chat message 的 part 模型与流式 reducer**。这部分归 `specs/ui/`，coder 在实现时产出，**不在本次调研范围**。
- **建议 arch/spec 明确**：chat 前端的 SSE event 协议（backend → frontend）是否复用 `StreamEvent`（spec protocol 层），还是另定义一个 wire event。若复用，则 §2.4 提到的 `thinking_delta` 必须加进 `StreamEvent`。
- req 要求"传递 10 个 message"——建议 arch 在 `[P0]agent_loop.md` 或 chat API spec 明确：chat API 是**无 session、无持久化、每次请求带最近 10 条 message** 的简单形态（v0.0.3 验证用）。
