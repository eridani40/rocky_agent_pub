# browser_use 工具调研报告（openclaw / hermes-agent / claude-code）

- **调研范围**：浏览器自动化工具的三种模式——headless、启动新 profile chrome（持久化）、attach 到用户已开 chrome（无需手动端口）
- **调研对象**：`refs/openclaw`（TS，attach 模式核心参考）、`refs/hermes-agent`（Python，对照）、`refs/claude-code`（TS，对照）
- **调研日期**：2026-06-25

---

## 1. 概述 + 策略枚举

三家共同底座是 **Chrome DevTools Protocol (CDP)**。差异在"如何拿到 CDP 端点"和"如何驱动页面"。三模式对应三种 CDP 获取策略：

| 策略 | 是什么 | openclaw | hermes | claude-code |
|---|---|---|---|---|
| **A. 自启 managed chrome** | 自己 spawn chrome 进程，`--remote-debugging-port=N` + `--user-data-dir=DIR` | `driver: "openclaw"` | local headless（`--session`） | N/A（仅 open URL） |
| **B. 持久 profile 自启** | 策略 A 的子集，profile 目录持久化复用登录态 | `driver: "openclaw"` + 持久 `userDataDir`（默认即持久） | `--session <name>` 复用 | N/A |
| **C. attach 已开 chrome** | 连到用户真实 chrome | `driver: "existing-session"` + `--autoConnect`（Chrome MCP） | `/browser connect` + `BROWSER_CDP_URL`（**需手动端口/URL**） | N/A |
| **D. 远程 CDP URL** | 显式 `cdpUrl`（loopback 或远程主机） | `cdpUrl` / `attachOnly` | `browser.cdp_url` config | N/A |

**关键结论**：**openclaw 是唯一做到 attach "无需用户手动指定端口"的竞品**，机制是 **spawn 官方 `chrome-devtools-mcp` npm 包并用其 `--autoConnect` 流程**（不是自己扫端口、不是 native messaging、不是 chrome 扩展）。详见 §4。

claude-code 的 `browser.ts` **不是** agent 浏览器自动化，只是 `open`/`xdg-open`/`explorer` 打开 URL（`refs/claude-code/src/utils/browser.ts:24-68`），与本需求无关，仅作对照排除。

## 2. 模式 1：headless

### 2.1 chrome 二进制发现（openclaw 最完整）

`refs/openclaw/extensions/browser/src/browser/chrome.executables.ts`（822 行）实现跨平台 chrome 发现，三级 fallback：

1. **用户配置 `executablePath`**（最高优先级）：`resolveBrowserExecutableForPlatform()` `refs/openclaw/.../chrome.executables.ts:796-822`——存在则校验 `fs.existsSync`，用 `{ kind: "custom" }`。
2. **系统默认浏览器探测**（`detectDefaultChromiumExecutable`，`:182-329`）：
   - **macOS**：读 `~/Library/Preferences/com.apple.LaunchServices/com.apple.launchservices.secure.plist` 的 `LSHandlers`，resolve `http`/`https` scheme → bundleId（如 `com.google.Chrome`），白名单 `CHROMIUM_BUNDLE_IDS`（`:28-52`，含 Chrome/Brave/Edge/Chromium/Arc/Vivaldi/Opera/Yandex），再用 `osascript` + `defaults read CFBundleExecutable` 定位可执行文件（`:195-222`）。
   - **Linux**：`xdg-settings get default-web-browser` → `.desktop` 文件 → 解析 `Exec=` 行 → `which` 解析（`:275-307`）。
   - **Windows**：`reg query ...UrlAssociations\\http\\UserChoice` ProgId → `HKCR\\<ProgId>\\shell\\open\\command` → 正则提 `.exe` 路径（`:309-329, 421-465`）。
3. **硬编码候选路径 fallback**（`findChromeExecutableMac/Linux/Windows`，`:540-710`）：如 macOS `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`；Linux `/usr/bin/google-chrome`、`/opt/google/chrome/chrome`、**还含 Playwright 缓存** `~/.cache/ms-playwright/chromium-*/chrome-linux/chrome`（`findPlaywrightChromiumExecutableCandidatesLinux` `:497-513`）；Windows `%LOCALAPPDATA%\Google\Chrome\Application\chrome.exe` + `Program Files`/`Program Files (x86)`。

### 2.2 版本兼容

`readBrowserVersion()` `:747-760`：macOS 优先用 `PlistBuddy` 读 `CFBundleShortVersionString`（快，800ms 超时），否则 fallback `chrome --version`（6000ms 超时）。`parseBrowserMajorVersion()` `:785-793` 用正则 `/\b(\d+)(?:\.\d+){1,3}\b/g` 取**最后一个**匹配的主版本号。

**版本门槛**：attach 模式（Chrome MCP autoConnect）要求 chrome **144+**（`refs/openclaw/docs/tools/browser.md:689`）。

### 2.3 无头启动参数

`buildOpenClawChromeLaunchArgs()` `refs/openclaw/.../chrome.ts:728-770`：

```typescript
const args = [
  `--remote-debugging-port=${profile.cdpPort}`,
  `--user-data-dir=${userDataDir}`,
  "--no-first-run", "--no-default-browser-check", "--disable-sync",
  "--disable-background-networking", "--disable-component-update",
  "--disable-features=Translate,MediaRouter", "--disable-session-crashed-bubble",
  "--hide-crash-restore-bubble", "--password-store=basic",
];
if (headlessMode.headless) { args.push("--headless=new"); args.push("--disable-gpu"); }
if (resolved.noSandbox) args.push("--no-sandbox");
if (process.platform === "linux") args.push("--disable-dev-shm-usage");
if (!hasChromeProxyControlArg(resolved.extraArgs)) args.push("--no-proxy-server");
```

- 用 **`--headless=new`**（Chrome 109+ 的新无头，非旧 `--headless`）。
- **headless 解析优先级**（`resolveManagedBrowserHeadlessMode()` `config.ts:592-622`）：request override > `OPENCLAW_BROWSER_HEADLESS` env > profile config > **Linux 无 `$DISPLAY`/`$WAYLAND_DISPLAY` 自动 fallback 到 headless**（`:617-619`）> 全局 config > default。
- **CDP 就绪探测**：`isChromeCdpReady()` `chrome.ts:878-889` 调 `diagnoseChromeCdp()`（`chrome.diagnostics.ts`，429 行）做 `/json/version` HTTP 发现 + WS 握手，带 SSRF 校验。launch 后轮询直到 ready（`CHROME_LAUNCH_READY_POLL_MS` / `CHROME_LAUNCH_READY_WINDOW_MS`）。

### 2.4 hermes 对照

`refs/hermes-agent/tools/browser_tool.py:1966-1990`：local 模式用 `agent-browser` CLI（Rust sidecar）+ `--session <name>` + `--engine chromium/chrome/lightpanda`，本质是 Playwright 无头 chromium。chrome 二进制靠 Playwright 自带 + `npx playwright install --with-deps chromium`（`browser_tool.py:843-844, 1937-1948`）。**hermes 没有自己的 chrome 发现逻辑**，完全依赖 Playwright/agent-browser。

## 3. 模式 2：启动新 profile chrome（profile 持久化）

### 3.1 profile 目录约定

openclaw 的 `driver: "openclaw"` profile，userDataDir 解析：`resolveOpenClawUserDataDir(profileName)` `refs/openclaw/.../chrome.ts:718-720`：

```typescript
return path.join(CONFIG_DIR, "browser", profileName, "user-data");
// macOS: ~/.openclaw/browser/{profileName}/user-data
```

即**每个 profile 一个独立 `user-data` 目录**，chrome 的 `--user-data-dir` 指向它（`chrome.ts:740`）。cookie/localStorage/登录态/扩展/历史 全部由 chrome 写入此目录，**进程退出后持久保留**，下次启动同一 profile 名即复用同一目录 = 复用登录态。

### 3.2 CDP port 分配（持久化）

`refs/openclaw/.../profiles.ts:23-58`：默认端口段 **18800-18899（100 profile 上限）**，`allocateCdpPort(usedPorts)` 取段内首个未占用端口。**port 在 profile 创建时分配一次并持久化进 config**（`profiles.<name>.cdpPort`），多实例可传自定义 range 避免冲突。预留端口：18789 gateway WS、18790 bridge、18791 control server、18793 canvas（`profiles.ts:14-21`）。

`getUsedPorts()` `:65-88` 从 config 的 profiles 提已用端口（支持 `cdpPort` 数字或 `cdpUrl` 解析）。

### 3.3 profile 命名规则 + 多 profile 切换

`isValidProfileName()` `profiles.ts:32-37`：`/^[a-z0-9][a-z0-9-]*$/`，最长 64 字符。多 profile 通过 config `browser.profiles.<name>` map 管理，`browser.defaultProfile` 选默认。profile 颜色 `allocateColor()` `:105-115` 从 10 色调色板取首个未用色。

### 3.4 与 headless 的关系

**同一 profile 既能 headless 又能有头**——`headless` 是 per-profile/per-launch 的开关（`ResolvedBrowserProfile.headless` `config.ts:100-115`），与 profile 目录（持久登录态）正交。`launchOpenClawChrome()` `chrome.ts:892` 接收 `launchOptions.headlessOverride` 可在单次启动覆盖。**模式 1（headless）和模式 2（持久 profile）本质是同一套 launch 路径，区别仅在 userDataDir 是否持久化命名 + headless 是否开**。openclaw 的默认 `openclaw` profile 就是持久的。

### 3.5 SingletonLock 处理（重要坑）

chrome 对 `user-data-dir` 加 `SingletonLock`/`SingletonSocket`/`SingletonCookie` 文件锁（`chrome.ts:81-86`）。openclaw 大量代码处理：

- `readSingletonLockTarget()` `:148-165`：`readlinkSync` 读锁，正则 `^(?<lockHost>.+)-(?<pid>\d+)$` 解析持锁主机+pid。
- `clearStaleChromeSingletonLocks()` / `clearChromeSingletonArtifacts()` `:449-483`：清僵尸锁。
- `recoverOwnedStaleManagedChromeCdpListener()` `:580-650`：恢复"本机 pid 持有但进程已死"的锁，复用其 CDP listener。
- `CHROME_SINGLETON_IN_USE_PATTERN` `:86` 检测"profile 正被另一 chromium 进程使用"错误并重试。

**教训**：同一持久 profile 不能被两个 chrome 进程同时打开——agent 用 headless 开着时，用户手动开同 profile 会失败。需在 PRD 确认是否需要"占用检测/排队"。

## 4. 模式 3：attach 到 chrome（核心——自动发现机制）

### 4.1 自动发现机制：Chrome DevTools MCP 的 `--autoConnect`

**这是本次调研最重要的发现。** openclaw 不自己扫端口、不用 native messaging、不用 chrome 扩展。它 spawn 官方 npm 包 **`chrome-devtools-mcp`** 作为 stdio MCP server，传 `--autoConnect` flag，**让 chrome-devtools-mcp 库内部去发现并连接 chrome**。

`refs/openclaw/extensions/browser/src/browser/chrome-mcp.ts:121-148`：

```typescript
const DEFAULT_CHROME_MCP_COMMAND = "npx";
const DEFAULT_CHROME_MCP_PACKAGE_ARGS = ["-y", "chrome-devtools-mcp@latest"];
// ...
const CHROME_MCP_CONNECTION_FLAGS = new Set([
  "--autoConnect", "--auto-connect",
  "--browserUrl", "--browser-url", "--wsEndpoint", "--ws-endpoint", "-w",
]);
```

参数构建 `buildChromeMcpConnectionArgs()` `chrome-mcp.ts:370-380`：

```typescript
function buildChromeMcpConnectionArgs(options) {
  if (hasFlag(options.extraArgs, CHROME_MCP_CONNECTION_FLAGS)) return []; // 用户已显式给
  if (options.browserUrl) {  // 显式 cdpUrl
    return isChromeMcpWebSocketEndpoint(options.browserUrl)
      ? ["--wsEndpoint", options.browserUrl]
      : ["--browserUrl", options.browserUrl];
  }
  return ["--autoConnect"];  // ← 默认：无需端口的自动发现
}
```

完整 args（`buildChromeMcpArgsFromOptions()` `:448-463`）：`npx -y chrome-devtools-mcp@latest --autoConnect --no-usage-statistics --experimentalStructuredContent --experimental-page-id-routing [--userDataDir <dir>]`。

spawn + stdio transport `createRealSession()` `chrome-mcp.ts:732-793`：

```typescript
const transport = new StdioClientTransport({
  command: options.command,         // "npx"
  args: buildChromeMcpArgsFromOptions(options),
  stderr: "pipe",
});
const client = new Client({ name: "openclaw-browser", version: "0.0.0" }, {});
await client.connect(transport);
const tools = await client.listTools();
if (!tools.tools.some(t => t.name === "list_pages")) throw ...;
```

### 4.2 "只需用户在 chrome 打开相关配置"是什么配置

`refs/openclaw/docs/tools/browser.md:658-697` 明确：用户须在目标浏览器里：

1. 打开 inspect 页：`chrome://inspect/#remote-debugging`（Brave: `brave://inspect/...`，Edge: `edge://inspect/...`）
2. **Enable remote debugging**（开启远程调试开关）
3. chrome **version 144+**
4. attach 时**批准 chrome 弹出的连接同意 prompt**（consent prompt）

即 chrome 144+ 提供的"inspect 页一键开启 remote debugging"特性。`--autoConnect` 的 chrome-devtools-mcp 库通过 chrome 144+ 的这个新机制（chrome 自己暴露的本地发现端点）连上，**用户无需 `--remote-debugging-port` 手动启动 chrome、无需知道端口号**。

### 4.3 userDataDir 透传（非默认 profile）

`buildChromeMcpUserDataDirArgs()` `chrome-mcp.ts:382-392`：当 profile 配了 `userDataDir`（如 Brave 的 `~/Library/Application Support/BraveSoftware/Brave-Browser`），透传 `--userDataDir <dir>` 让 chrome-devtools-mcp 定位到该浏览器的 profile（非默认 Google Chrome profile 时必需）。config.ts 的 `resolveProfile()` 对 `existing-session` drivers 也解析 `userDataDir`（`config.ts:523-541`）。

### 4.4 fallback：显式 cdpUrl

若 chrome 是用 `--remote-debugging-port=N` 手动启动的，profile 配 `cdpUrl: "http://127.0.0.1:9222"` + `attachOnly: true`，走 `--browserUrl` 而非 `--autoConnect`（`browser.md:692-694`）。

### 4.5 attach 后列举 tab / 连目标 page / 注入指令

attach 后**完全走 chrome-devtools-mcp 的 MCP tool 协议**（非裸 CDP）：

- `list_pages` → 列举已开 tab（`extractStructuredPages()` `chrome-mcp.ts:239-242`，返回 `[{id, url, selected}]`）
- `select_page` / navigate / snapshot / click / type / eval 等 MCP tool（`chrome-mcp.ts:757` 校验 `list_pages` 存在）
- 错误处理：`CHROME_CONNECTION_TOOL_ERROR_RE` `:147` 匹配 "Could not connect to Chrome / DevToolsActivePort / ECONNREFUSED" 触发 reconnect；`STALE_SELECTED_PAGE_ERROR` `:149` 触发重连重试（`shouldReconnectForToolError()` `:308`）。

session 缓存 key = `[profileName, userDataDir, browserUrl, command, extraArgs]` JSON（`buildChromeMcpSessionCacheKey()` `:394-405`），profile 切换时 `closeChromeMcpSessionsForProfile()` `:423-446` 清旧 session。

### 4.6 与模式 2 的差异

| 维度 | 模式 2（managed profile） | 模式 3（attach existing） |
|---|---|---|
| 浏览器进程 | openclaw spawn + own | 用户自己开，openclaw 只 attach |
| profile | 独立隔离 `~/.openclaw/browser/<name>/user-data` | 用户真实 profile（含所有登录态/扩展/历史） |
| 端口 | openclaw 分配 18800+ | chrome 自己决定（autoConnect）/ 用户指定（cdpUrl） |
| 关闭 | openclaw 杀进程 | `attachOnly`：stop 只清 emulation，不杀浏览器（`server-context.lifecycle.ts:15`） |
| 风险 | 低（隔离） | **高**（能操作用户已登录 session） |
| 要求 | chrome 装了即可 | chrome 144+ + 用户手动开 remote debugging + 批准 prompt |

### 4.7 hermes 对照（需手动端口）

hermes 的 attach **不做到"无需端口"**：`/browser connect <url>` 命令设 `BROWSER_CDP_URL` env 或 `browser.cdp_url` config（`browser_tool.py:284-310`），用户必须自己先 `chrome --remote-debugging-port=9222` 启动并给出 URL。`browser_supervisor.py` 用 `websockets` 直连 ws endpoint，`Target.attachToTarget` flatten 模式（`browser_cdp_tool.py:94-152`）。**openclaw 的 autoConnect 是更优方案**。

## 5. 横向：CDP 底座 / 驱动模型 / 生命周期 / 安全

### 5.1 CDP 是共同底座

三家都基于 CDP。TS 侧客户端选型：

- **openclaw**：模式 2 用 **Playwright** 的 `connectOverCdp`（`pw-session.ts:229` 缓存 `connectOverCdp` 连接，按 cdpUrl+targetId 缓存 page）；模式 3 用 **chrome-devtools-mcp**（MCP over stdio，非直连 CDP）。还有裸 CDP helpers（`cdp.ts` 967 行，WS 握手）。
- **hermes**：模式 1 用 **Playwright**（agent-browser sidecar）；attach 用裸 **websockets**（`browser_supervisor.py`）。

### 5.2 agent 驱动模型：a11y tree + element ref（非截图坐标）

openclaw 和 hermes 都走 **accessibility tree + element ref** 路线（类 browser_use），**非** computer-use 的截图+坐标：

- openclaw `client.ts:344-411`：snapshot format 支持 `"aria"` 和 `"ai"`，返回 `{ snapshot: string, refs: Record<id, {role, name, nth}>, refsWithBoundingBoxes }`。`pw-ai.ts:66-68` 有 `snapshotAiViaPlaywright / snapshotAriaViaPlaywright / snapshotRoleViaPlaywright`。click 用 ref locator（`pw-ai.ts:26 refLocator`）。
- hermes `browser_tool.py:11`：明确"The tool uses agent-browser's accessibility tree (ariaSnapshot) for text-based"snapshot；`:22` "Text-based page snapshots using accessibility tree"。ref 形式 click/type（`browser_tool.py:2598-2637` camofox_click/camofox_type 接 `ref`）。

截图（`screenshot.ts` / `pw-tools-core.snapshot.ts`）是**辅助**，用于 vision 校验或给 LLM 看页面，但**点击/输入走 ref 不走坐标**。

### 5.3 生命周期 / 清理

`refs/openclaw/src/browser-lifecycle-cleanup.ts`（43 行）：`cleanupBrowserSessionsForLifecycleEnd()` → `closeTrackedBrowserTabsForSessions()`（按 sessionKey 关 agent 开的 tab，不杀用户浏览器）。配置 `browser.tabCleanup`（`config.ts:238-257`）：`enabled / idleMinutes / maxTabsPerSession / sweepMinutes`——解决"僵尸 tab 泄漏"。`session-tab-registry.ts` 跟踪每个 session 开的 tab。`attachOnly`/remote profile 的 stop 只清 emulation 不杀进程（`server-context.lifecycle.ts:15`）。

### 5.4 安全

- **SSRF**（attach/remote CDP）：`assertCdpEndpointAllowed()` `chrome.ts:803` + `cdp-reachability-policy.ts`（40 行）+ `chrome.loopback-ssrf.integration.test.ts`。loopback 默认 fail-closed 私网检查（`config.ts:282-313` resolveBrowserSsrFPolicy）。
- **attach 鉴权**：`refs/openclaw/extensions/browser/src/browser/control-auth.ts`（`ensureBrowserControlAuth / resolveBrowserControlAuth / shouldAutoGenerateBrowserAuth`），auto-generate token 守 control server。
- **反检测（camofox）**：仅 hermes 有，`refs/hermes-agent/tools/browser_camofox.py`（C++ fingerprint spoofing 的 Camoufox fork，REST API）。openclaw **不做反检测**（driver 用真实 chrome，profile decoration 仅改颜色/名称 `chrome.profile-decoration.ts`）。**反检测是 hermes 独有、openclaw 明确不做的路线**——待 PRD 确认是否需要。

## 6. 推荐实现路线（rocky_agent，TS）

### 模式 1（headless）—— 推荐方案

- **CDP 客户端**：**Playwright**（`chromium.launch()` 或 `connectOverCdp`）。理由：生态成熟、自带 chromium、a11y snapshot API、openclaw 也用 Playwright。备选 `chrome-remote-interface`（更裸但要自己实现 snapshot）。
- **chrome 发现**：复刻 openclaw `chrome.executables.ts` 的三级 fallback（用户配置 > 系统默认 > 硬编码路径），**macOS plutil/osascript、Linux xdg-settings、Windows reg** 三套都要。
- **启动参数**：照搬 `buildOpenClawChromeLaunchArgs` 的参数集（`--no-first-run`/`--disable-sync`/`--password-store=basic` 等），headless 用 `--headless=new`。
- **CDP 就绪轮询**：launch 后轮询 `http://127.0.0.1:<port>/json/version` 直到 200（带 timeout），再 `connectOverCdp`。

### 模式 2（持久 profile）—— 推荐方案

- **profile 目录**：`~/.rocky_agent/browser/<profileName>/user-data`（沿用 openclaw 约定）。
- **CDP 端口段**：选一段（如 18800-18899），`allocateCdpPort` 取首个未占用，**持久化进 profile config**。
- **headless 与 profile 正交**：同一 profile 支持有头/headless 两种启动（per-launch 开关）。
- **SingletonLock 处理（必须做）**：复刻 openclaw 的 `readSingletonLockTarget` + 清僵尸锁 + "profile in use" 检测，否则用户手动开同 profile 会撞锁。
- **Linux 无显示自动 headless**：检测 `$DISPLAY`/`$WAYLAND_DISPLAY` 缺失则强制 headless。

### 模式 3（attach，无需端口）—— 推荐方案（重点）

**直接复刻 openclaw 的 chrome-devtools-mcp autoConnect 方案**，不要自己造轮子：

1. **核心机制**：spawn `npx -y chrome-devtools-mcp@latest --autoConnect [--userDataDir <dir>] --experimentalStructuredContent --experimental-page-id-routing`，用 `@modelcontextprotocol/sdk` 的 `StdioClientTransport` 连 stdio，`client.listTools()` 校验，然后调 MCP tool（`list_pages`/`select_page`/`navigate_page`/`snapshot`/`click`/`type`/`evaluate_script`）。
2. **"无需手动端口"= chrome 144+ 的 inspect 页 remote-debugging 开关 + chrome-devtools-mcp 库内部的 autoConnect 发现逻辑**。用户操作：打开 `chrome://inspect/#remote-debugging` → 开启 → 批准 attach prompt。**我们的代码不需要知道端口**。
3. **fallback**：若用户已 `chrome --remote-debugging-port=9222` 启动，支持 profile 配 `cdpUrl` 走 `--browserUrl`（= hermes 的 connect 模式，作为兜底）。
4. **userDataDir 透传**：attach Brave/Edge 等非默认 chrome profile 时必须传 `--userDataDir`。
5. **session 缓存**：key = `[profileName, userDataDir, browserUrl, command, extraArgs]`，profile 切换清旧 session。
6. **超时**：handshake 30s（`CHROME_MCP_HANDSHAKE_TIMEOUT_MS`），stderr pipe 收集诊断（8KB tail）。
7. **错误恢复**：匹配 "Could not connect to Chrome / DevToolsActivePort / ECONNREFUSED" 重连；"selected page closed" 重连重试一次。

**依赖**：`chrome-devtools-mcp`（npm，需用户机器装了 chrome 144+ 和 npx）。**注意**：这把我们 attach 模式的"驱动层"绑定到 MCP tool 协议（非裸 CDP），与模式 1/2 的 Playwright 路线是**两套驱动**——这是 openclaw 也接受的代价。

### 驱动模型 —— 推荐 a11y tree + ref

三家都用 **accessibility snapshot + element ref**（非截图坐标）。理由：精度高、token 省、不需 vision 模型二次定位。Playwright 原生支持 `page.accessibility.snapshot()` + `ariaSnapshot`。截图作为**辅助**（vision 校验、给 LLM 看长相），不作为主交互通道。

## 7. 待 PRD 确认的开放问题

1. **反检测**：是否做（hermes camofox 路线）？openclaw 明确不做。建议**不做**（复杂、易失效、Chrome 检测升级快）。
2. **attach 模式的驱动分裂**：模式 3 用 chrome-devtools-mcp（MCP tool 协议），模式 1/2 用 Playwright（CDP）——是否接受两套驱动？或统一都用 Playwright `connectOverCdp`（但放弃"无需端口"的 autoConnect，退回 hermes 的手动端口模式）？**这是最关键的 PRD 决策**。
3. **截图+坐标（computer-use 路线）**：是否支持？三家都不主用，但某些 canvas/视频场景 a11y tree 够不到。建议**不支持**（P2 再说）。
4. **profile 占用冲突**：用户手动开同 profile 时 agent 行为（报错/排队/抢锁）？openclaw 是报错重试。
5. **多 profile 上限**：100（openclaw 默认）够否？端口段范围。
6. **attach 鉴权**：control server 是否要 token（openclaw `control-auth.ts` auto-generate）？单机本地用可能不需要。
7. **远程 chrome attach**：是否支持 `cdpUrl` 指向远程主机（WSL2/容器场景）？openclaw 支持 + SSRF 校验。
8. **chrome-devtools-mcp 版本钉死**：用 `@latest`（openclaw 默认，跟官方最新）还是钉版本（稳定但错过新特性）？
