## 2. 现有「resolve」机制 = 3 层过滤（已存在，只是没叫 resolveTools）

每次 main agent run，工具列表由 3 层正交过滤决定（`scope-allowed-tools.ts:13` 自述「三重过滤」）：

- **Layer A — config 层**（实例白名单）：`handlers/session-config.ts:199-228` `buildSessionConfigFromDeps` 建 `config.tools: Tool[]`。
  - studio-squad → `[send_message]`（:213）
  - studio-leader/mate → `defaultTools ∩ member.tools`（:216-225；leader 空 fallback→`LEADER_DEFAULT`，mate 空 fallback→FULL）
  - subagent → `defaultTools ∩ subAgentConfig.tools`（:227，template 白名单）
  - top-level → 全集（:229）
- **Layer B — schema 层**（LLM 看到的）：`scope-allowed-tools.ts:123-136` `filterToolDefinitionsBySessionType(sessionType, allDefs)`，表在 :80-86。callLLM 前应用（`agent-loop-call-main.ts:87`, `agent-loop-stage-llm.ts:94`）。
- **Layer C — exec 层**（LLM 可执行的）：`scope-allowed-tools.ts:164-186` `deriveAllowedTools(scope, names, sessionType)`，每 run 一次（`build-deps.ts:204-208`），存 `RunSpec.allowedTools`（`loop-ports.ts:217`），`engine.execute(allowedTools)` 消费（`engine.ts:60-70`）。

> **结论**：section 1 的 `resolveTools` 不是从零建，而是把 A+B+C 三层**收敛成单一 `resolveTools(sessionType, config)`**。

## 4. 「forked」术语歧义（关键，影响 section 2 范围）

代码里两个**不同**概念：

- **subagent**：LLM 用 `agent` tool 派生的子**会话**（type='subagent'，独立 transcript，持久化）。派生路径：`agent-tool.ts:210` → `spawn-action.ts:81` `executeSpawn` → `createChildSession`（agent-tool.ts:280）→ 存 `subAgentConfig`。**不继承** main 的 prompt（用 template prompt）/ tools（用 template.tools）；只继承 modelId。
- **side run**（旧名 forked，v0.0.204 rename）：compact/summary 用的**内存内**后台 run（`sideRun`）。**复用** main 的 `toolDefinitions`（保 cache，`bootstrap.ts:485-499`），`allowedTools:[]`（summary 无工具）。`side-run-scope-bootstrap.ts:80` **显式禁用** `system_reminder_injector`（「注入 reminder 会污染 cache 前缀」）。

req section 2 描述（「上下文复用 + system prompt/tools 来自 main + 专注本 message 任务」）= **side run (compact/summary)**（调研时旧名 forked） 模式。subagent 不匹配（它有自己的 template prompt）。**需用户确认「所有 forked」指哪个。**

## 10. 各场景 tool 列表方案（定稿 — JSON tool policy 驱动）

**核心原则**：工具只属于它有意义的场景。当前 bug——`filterToolDefinitionsBySessionType(undefined)=FULL`，playground-rocky 的 LLM 能看到 `team`/`goal`/`requirement`/`task`/`send_message`（= 用户「多余和 bug」来源）。本方案把矩阵**形式化为一份 JSON tool policy**，`resolveTools` 读配置按当前 session 类型 resolve。

### 10.1 模型：bound（上限）+ 动态 allowedTools

- **顶层角色**（playground-rocky / studio-squad / studio-leader / studio-mate）：resolve = 该角色的 `bound`（静态全量）。
- **子角色**（subagent = playground-subagent & studio-subagent；以及 forked）：resolve = **main 动态传入的 `allowedTools` ∩ 子角色 `bound`**。`bound` 是上限，main 决定实际子集。
  - studio-subagent 再 ∩ 派生它的 member/leader 的 `bound`（「不超父」）。
  - → forked 与 subagent **共用同一套**动态白名单机制（req section 2），不再分两套；所谓「△ 即对勾」——在 bound 池里就算 ✓，实际子集由 main 传。

### 10.4 JSON tool policy（resolveTools 读这个；静态代码资源，非用户可配）

```json
{
  "roles": {
    "playground-rocky": { "bound": ["read","write","edit","glob","grep","bash","skill","web_search","web_fetch","browser","agent","send_message"] },
    "studio-squad":     { "bound": ["send_message"] },
    "studio-leader":    { "bound": ["send_message","team","goal","requirement","task","read","write","edit","glob","grep","bash","skill","web_search","web_fetch","browser"] },
    "studio-mate":      { "bound": ["send_message","team","requirement","task","read","write","edit","glob","grep","bash","skill","agent","web_search","web_fetch","browser"] },
    "subagent":         { "bound": ["read","write","edit","glob","grep","bash","skill","web_search","web_fetch","browser","send_message"], "capByParent": true }
  }
}
```

**resolveTools 语义**：
- 顶层角色 → `policy.roles[role].bound`
- subagent → `mainAllowedTools ∩ policy.roles["subagent"].bound`；若 `capByParent` 且父为 studio member/leader → 再 ∩ `policy.roles[parentRole].bound`
- forked（compact/summary）→ 用新 option `enableToolWhitelist=true` + `toolWhitelist` 表达（compaction = `[]` 即无工具，见 §10.6）；+ 注入 system reminder（cache 前缀之后，不污染 cache）

> main 如何传 `mainAllowedTools`：spawn 时 `agent(action=spawn, input.tools)` 优先，缺省回退 template.tools（template 仅作 default 白名单），结果再 ∩ bound。

### 10.5 判定点（已定稿，2026-07-02 多轮对话）

1. playground-rocky `send_message` = ✓（rocky 有 subagent，a2a 互通）— 修订（原判 ✗ 错）
2. subagent 工具 = **main 动态传 allowedTools ∩ subagent bound**（△=对勾；与 forked 同机制）；studio-subagent 再 ∩ 父 bound
3. studio-mate `agent` = ✓（mate 派生 subagent 干活）；studio-leader `agent` = ✗（不创建子 agent）
4. studio-leader / studio-mate 都联网（web_search/web_fetch/browser ✓）
5. side-run 语义 = compact/summary 内存 run（`sideRun`），不含 LLM 派生 subagent
6. 形式化为 JSON tool policy（静态代码资源）；session manager / resolveTools 读配置 resolve——替代现 `scope-allowed-tools.ts` 硬编码常量

### 10.6 forked 白名单选项语义 + compaction 事实

两个新 agent option（formal 化，替代现 ad-hoc `allowedTools`）：
- `enableToolWhitelist: boolean` — toolEngine 是否强制白名单拒绝
- `toolWhitelist: string[]` — 允许的 tool 名表

语义（三态）：
- `enableToolWhitelist=true`  + `toolWhitelist=[...]` → 仅列出的工具可执行
- `enableToolWhitelist=true`  + `toolWhitelist=[]`   → **啥都不允许**（零工具）
- `enableToolWhitelist=false`                       → 不强制，bound 内全可执行

**事实（记录）**：compaction 的 forked agent **无工具**（不执行任何 tool），summary 直接输出到 answer。其形式化表达 = `enableToolWhitelist=true, toolWhitelist=[]`（「没有 allowed」= 白名单强制 + 空表 → 零工具，不是另一套机制）。`toolDefinitions` 仍复用 main（保 cache 前缀），但 toolEngine 全拒。

> 即：forked 与 subagent 的「实际可执行工具」都统一走 `enableToolWhitelist` + `toolWhitelist` 这对 option；bound（§10.4 policy）是上限，这对 option 是 main/caller 动态传入的实际白名单。
