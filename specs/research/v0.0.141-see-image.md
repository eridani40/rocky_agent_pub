# see_image 工具调研报告

- **调研范围**: see_image 多 vender 视觉理解工具的实现参照物（web_search 架构、anthropic protocol 复用、zai-mcp 选型、工具注册 scope、@图片 mention 现状）
- **调研对象**: 本项目 `app/`（web_search / anthropic protocol / tool-policy / mention）+ 用户 claude code MCP 配置
- **调研日期**: 2026-07-14
- **需求**: `reqs/[working] v0.0.141.see_img/req.md`

## 0. 结论速览

- **see_image 完全可以照 web_search 复刻**：新 EP `see_image_provider`（list，按 app_config.type 单点路由）+ 2 个 builtin ext impl（minimax_m3 / zhipu_image）+ 一个 tool 层（读 app_config 选 provider、校 isAvailable、传 cfg）。可直接类比复制的文件已列于 §2.5。
- **anthropic image block 项目已原生支持**（v0.0.105）：`ImageBlock`（spec 形 base64 source）+ `encodeContentBlock` 翻译成 anthropic wire 形，`vision_check.py` 已用 MiniMax-M3 anthropic 端点 + base64 image block 实测跑通（§3）。MiniMax vender 直接 base64 + fetch 即可，**不必挂平台 LlmClient / provider 配置体系**。
- **zhipu_image 两条路**（§4）：A=真 MCP client 调 `@z_ai/mcp-server`（npx/stdio）；B=REST 直调智谱 GLM 视觉 API。**强烈倾向 B**：与现有 record/replay + proxyFetch 架构天然兼容，packaged（asar/Electron，cwd=/，process.env 干净，无 npx）下 A 有 spawn npx 子进程的高风险，B 零风险。现有 zhipu_web_search 即 REST 直调先例。
- **「除 squad-chat 外」= TOOL_POLICY**（§5）：把 `see_image` 加进 `playground-rocky / studio-leader / studio-mate / subagent` 的 bound，**不加 studio-squad**（squad-chat 只有 send_message）。
- **@图片 mention 零前端改动即可用**（§6）：@file mention 落成消息文本里的 `<mention type="file" path="..." .../>` 字符串，LLM 直接读到本地路径 → 调 see_image 传路径。tool 入参只有路径+文字，完全符合「base64 不进上下文」硬约束。

## 1. 概述

see_image 需求本质 = web_search 的镜像：一套 provider 协议 + 一个 list 扩展点 + app_config 凭证路由 + 若干 builtin ext impl，唯一差别是「search(query)→结果列表」换成「understand(text, imagePaths[])→文字理解」。web_search 在 v0.0.72 完成「凭证迁 app_config + list EP + cfg 入参」重构、v0.0.123 拆成 2 个 impl，其架构与 see_image 的「双 vender + 未配置报错 + 凭证独立」诉求高度同构，是最佳参照物。

两个 vender 的传输细节不同：MiniMax M3 走 anthropic 兼容 `/v1/messages`（base64 image block，多图有序，项目 protocol 已支持）；zhipu_image 走智谱 GLM 视觉能力（req 说「和 web_search zhipu 一样」——实为 REST 直调，见 §4）。硬约束贯穿两者：**tool 入参/出参只有本地路径 + 文字，base64 只在 vender 实现内部 → 出站 API 的一环出现**。

## 3. anthropic-message protocol 复用点

### 3.1 代码位置
- **protocol impl**：`app/server/src/llm/protocol.ts`（`AnthropicMessagesProtocol`，`path='/v1/messages'`, `contentType='application/json'`）；builtin re-export：`app/plugins/builtins/llm_anthropic/protocol.ts`。
- **请求构造（encode）**：`app/server/src/llm/protocol-encode.ts`（`encodeAnthropicMessages` canonical→wire，纯函数不碰网络）。
- **流式解析**：`app/server/src/llm/protocol-parse-stream.ts`。
- **canonical 类型**：`app/server/src/llm/protocol-types.ts`（`ContentBlock` 含 image）；业务权威 `app/server/src/message/types.ts`（`ImageBlock` / `ImageSource`）。

### 3.2 image content block 已原生支持（v0.0.105）
- **spec 形 ImageBlock**：`message/types.ts:78-88` `{ type:'image', source:{kind:'base64',data} | {kind:'url',url}, mediaType }`（**裸 base64，无 data: 前缀**，mediaType 顶层）。
- **wire 翻译**：`protocol-encode.ts:255-265` `encodeContentBlock` case 'image' → anthropic wire `{ type:'image', source:{ type:'base64', media_type, data } }`（url 形则 `{type:'url',url}`）。**唯一翻译点，禁别处透传 source**。
- 这正是 MiniMax M3 anthropic 端点期望的 image block 格式（req 附 `text-chat-anthropic.md` §MediaSource：`source.type∈{base64,url}` + `media_type` + `data`；JPEG/PNG/GIF/WEBP ≤10MB，仅 M3 支持 vision）。

### 3.3 已实测跑通的参照（vision_check.py）
`tests/e2e/lib/vision_check.py` **已用 MiniMax-M3 anthropic 端点 + base64 image block 实战跑通**，是 MiniMax vender 的现成蓝本：
- endpoint：`https://api.minimaxi.com/anthropic` + `/v1/messages`（`call_vision_api`，:35）
- headers：`Content-Type: application/json` + `Authorization: Bearer <key>`（:44-46）
- body：`{ model:'MiniMax-M3', max_tokens:2048, messages:[{role:'user', content:[...blocks]}] }`（:37-39）
- image block：`{type:'image', source:{type:'base64', media_type, data:<b64>}}`（`_image_block`, :26）
- **多图有序**：content 数组按顺序放多个 image block（+ 文本 block），顺序即模型理解顺序 → 天然满足 req「按顺序传多图」
- 响应：取 `result.content[]` 中 `type==='text'` 的 text 拼接（:58）
- key 与 test.env 同源：`MINIMAX_API_KEY`（用户确认测试可用）

### 3.4 reuse 到「独立 vender」需要抽/借什么（关键判断）
req 明确：see_image vender **独立于平台的 LLM provider 配置体系**（endpoint/模型名/温度写死）。因此**不要挂 LlmClient / llm_provider / app_config providers**。两种 reuse 力度：
- **轻量 reuse（推荐）**：MiniMax vender 自己拼 anthropic body（照 vision_check.py 蓝本），直接 `fetch`；只 borrow「base64 image block 结构」这个知识 + record/replay fetch 装饰。**不复用 encodeAnthropicMessages**（它带 cache_control/reminder/tool 编码等平台耦合，see_image 用不上）。写死：`model='MiniMax-M3'`、`temperature=1.0`、`max_tokens`（建议 2048~4096）、endpoint。
- **可选 reuse**：若想复用 `ImageBlock`/`encodeContentBlock` 只翻译单条 user message，也可，但收益低于耦合成本。建议只抄 image block 的 `{type:'base64',media_type,data}` 形，不引 protocol 层。
- **record/replay 兼容**：出站 fetch 必须走 `pickWebFetch(getRegistry()) ?? proxyFetch`（见 `zhipu-api-provider.ts:37,133`），否则 AT 无法录制/回放（server fetch 层拦截仅 NODE_ENV=test）。这是 see_image AT 能双关 PASS 的前提。

## 4. zhipu_image vender 选型调研（zai-mcp vs REST，供架构决策，不下结论）

req 原文：「自己查看目前 claude code 里的 mcp server zai-mcp-server，采用代码调用 mcp 的方式……我们好像 web_search 的 zhipu 实现和他一样，采用类似的方式」。但**事实澄清**（context.md findings + §2 实证）：现有 `zhipu_web_search` 是 **REST 直调**（POST open.bigmodel.cn），**不是** MCP 调用。因此存在两条实现路径，本节列材料供架构阶段裁决。

### 4.1 zai-mcp-server 是什么（用户 claude code MCP 配置，已核）
用户 `~/.claude.json` 的 `mcpServers.zai-mcp-server` 条目（**key 值已脱敏，不入报告**）：
- `command: "npx"`，`args: ["-y", "@z_ai/mcp-server"]`，`type: "stdio"`，`env: { Z_AI_API_KEY: <脱敏> }`
- 即：npm 包 `@z_ai/mcp-server`，`npx -y` 拉起，**stdio transport**（JSON-RPC over stdin/stdout 子进程），凭证走环境变量 `Z_AI_API_KEY`。
- 其 `analyze_image` 工具（context.md 已核）：入参 `image_source` 支持「Local file path or remote URL」——**本地路径直接传，MCP server 本地自读文件**；出参为文字理解。**单图**（req：zhipu 传入数量≠1 即报错）。

### 4.2 方案 A：代码内起真 MCP client 调 @z_ai/mcp-server
- **依赖引入**：需引 MCP client SDK（如 `@modelcontextprotocol/sdk`）+ 运行期能拉起 `@z_ai/mcp-server`（npx 或预装依赖）。
- **进程管理复杂度**：**高**。须 spawn stdio 子进程、握手 initialize、管生命周期（启动/超时/回收/僵尸进程）、错误传播。属于「串行管线 + 无超时 IO」高风险面（见 memory `serial-pipeline-io-needs-timeout-decouple`）。
- **record/replay 兼容**：**差**。stdio 子进程流量不经 server fetch 层，现有 `pickWebFetch`/proxyFetch 拦截**拦不到**；AT 无法离线回放，须另造 stub 或走 live，违反「新增 case 必录制双关」纪律。
- **packaged 风险（关键，参 CLAUDE.md 可打包护栏）**：**极高**。packaged=Electron Node CJS + asar + cwd=`/` + `process.env` 干净（不继承 shell）。①`npx` 在 packaged app 内基本不可用（无 npm/node 在 PATH、cwd 不可写、无网络拉包保证）；②即便把 `@z_ai/mcp-server` 打进依赖，spawn 子进程 + stdio 在 asar 内路径解析/可执行权限坑多；③macOS TCC：裸 spawn 子进程拿不到宿主签名权限（memory `macos-tcc-spawn-no-perm-use-electron-host`）。**dev 能跑 ≠ packaged 能跑**，且这类崩溃 dev 的 AT/ET 测不到。

### 4.3 方案 B：REST 直调智谱 GLM 视觉 API（chat/completions，image_url 支持 base64 data URL）
- **端点**：智谱 GLM-4V 系列 `POST https://open.bigmodel.cn/api/paas/v4/chat/completions`，`messages[].content=[{type:'text',text}, {type:'image_url', image_url:{url:'data:image/png;base64,<b64>'}}]`（OpenAI 兼容多模态形，base64 data URL）。Bearer apiKey。
- **依赖引入**：**零新依赖**——复用 `proxyFetch` + `pickWebFetch`，与 `zhipu-api-provider.ts` 同源同骨架。
- **进程管理复杂度**：**无**（单次 HTTP）。
- **record/replay 兼容**：**完美**——出站 fetch 走 pickWebFetch，AT 可录制双关，与现有全套测试架构无缝。
- **packaged 风险**：**零**——纯 HTTP，undici 已 external 进 asar（`scripts/build-plugins.ts:30`），无子进程/无 npx/无 fs 可写要求（base64 在内存）。
- **代价**：与「用户 claude code 里那个 zai-mcp」不是同一条链路（换成智谱官方 REST 视觉 API）；需确认智谱视觉模型名 + 该 key 是否开通视觉能力（zhipu 真 key 由用户自测，见 req）。

### 4.4 两路对比表
| 维度 | 方案 A（真 MCP client） | 方案 B（REST 直调 GLM 视觉） |
|---|---|---|
| 依赖引入 | MCP SDK + npx/@z_ai/mcp-server | 零（复用 proxyFetch） |
| 进程管理 | 高（spawn stdio 子进程） | 无（单次 HTTP） |
| record/replay | 拦不到，AT 难离线回放 | 完美兼容 pickWebFetch |
| packaged（asar/Electron） | 极高风险（npx/spawn/TCC/cwd=/） | 零风险（undici 已 external） |
| 与现有 zhipu_web_search 一致 | 不一致（现有是 REST） | **一致**（同骨架） |
| 忠于 req「代码调用 mcp」字面 | 是 | 否（但 req 事实已澄清现有是 REST） |

## 6. @图片 mention 现状（用户场景：@图片 + 问问题）

### 6.1 mention = 消息 content 里的内嵌 XML 字符串（端到端零转换）
`specs/tech/mention/message-content.md`：mention 以单行自闭合 XML tag 内嵌在 **string** content 里，POST/DB/SSE/LLM prompt/GET **同一份字符串零转换**，server 不解析、原样透传，**只有前端渲染时**扫正则替换成 pill。

### 6.2 @file 产出什么
`message-content.md §3.1/§4`：`file` type 的 address 属性是 `path`（**workspaceDir 下相对路径，POSIX `/`**）。样例：
```xml
<mention type="file" path="src/utils/helper.ts" icon="file" label="helper.ts"/>
```
mention 前端类型见 `component-mention-popover.tsx:18-28`（file/skill=path；workitem=kind+id；member=id）。**@file 不会自动转成 image content block**——它就是一段带本地路径的文本，LLM 原样收到。

### 6.3 对 see_image 的意义（零前端改动即可用）
用户「@一个图片，问里面有什么」→ 消息文本含 `<mention type="file" path="..." .../>` → 主 agent LLM 读到路径文本 → LLM 决定调 `see_image({text:'里面有什么', imagePaths:['...']})` → see_image 读文件 base64 → vender API → 回文字。**tool 入参只有路径 + 文字，base64 全程不进上下文**——与 req 硬约束完全一致，**无需任何前端 mention 改动**。

**依据**：mention 已支持 @file 且传本地路径（相对 workspace）；LLM 天然能从 mention tag 文本抽 path 作 tool 入参。唯一需 coder 注意的边界见 §7。

## 7. easy-harness 实现建议

### 7.1 推荐方案

### 7.2 注意事项 / 坑
- **相对路径解析**：@file mention 的 path 是**相对 workspaceDir**。see_image tool 必须用 `ctx.workdir`（`ToolCtx.workdir`, `tools/types.ts:179`）把相对路径 resolve 成绝对路径再读文件；同时兼容 LLM 直接给绝对路径。参考现有 file 工具的路径解析。
- **base64 只在内部**：tool 入参/出参严禁 base64（req 硬约束 + 防上下文爆炸）；读文件→base64 只在 provider.understand 内部完成，出参只回 `{text}`。
- **media_type 推断**：按扩展名映射（`.png→image/png` 等，见 `image_to_base64` :18）；不支持格式（非 JPEG/PNG/GIF/WEBP）应 ToolError。
- **大小限制**：MiniMax 单图 ≤10MB、请求体 ≤64MB；zhipu 单图。超限先本地判并报错，别打到 API 才 413。
- **未配置报错**：复用 web_search 三分支错误（type 未配置 / impl 未激活 / isAvailable false 凭证空），全走 errorResult 不静默降级（req 裁决）。
- **record/replay**：出站必走 pickWebFetch（§3.4/§4.3），否则 AT 录不了、回放不命中（memory `record-replay-dynamic-marker-breaks-stub`）。
- **packaged 依赖归属**：MiniMax/zhipu(B) 仅用 undici（已 external）+ node fs，无新第三方依赖 → packaged 安全。若选方案 A，新依赖须进 `@app/server` workspace package.json 且 build-plugins EXTERNALS 决策（CLAUDE.md 护栏 1/2）。
- **isAvailable 禁 I/O**：只查 `cfg.apiKey` 非空（照 web_search §5.3）。

### 7.3 可复用的设计模式
- **协议 + list EP + app_config 路由 + cfg 入参透传**（web_search v0.0.72 范式）：凭证不进协议、tool 每次从 app_config 构造 cfg 传 impl，多 vender 共存单点路由。
- **1 plugin 多 extImpls**（`zhipu_web_search` 2 impl / `llm_anthropic` provider+protocol）：see_image 一个 plugin 挂 minimax_m3 + zhipu_image 两条 extImpls。
- **自渲染 config section**（saveMode='item' 自管 GET/PUT + implId-agnostic 下拉 + SecretInput）：section-web-search-config 可近乎照抄。
- **pickWebFetch ?? proxyFetch 出站装饰**：record/replay + 代理层统一入口。
- **未配置即精确报错**（三错误分支不回退）：web_search tool.run 现成。

### 7.4 供架构阶段决策的开放点

- 前端是否需要 see_image 专属 section，还是复用某处——建议新建独立 section（与 web_search 对等）。
