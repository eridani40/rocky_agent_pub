## 1. Feature Gate build-time 落点

### 1.1 现状

项目**无现成 feature gate 机制**（grep `feature.gate|featureGate|FEATURE_GATE` 全空）。但 build pipeline 已具备所有基础设施：

- **前端**：`app/web/vite.config.ts` 是标准 Vite 配置（`defineConfig`），未配置 `define` 但支持。已有 `import.meta.env.VITE_*` 内联机制——`api-base.ts:16` 读 `import.meta.env.VITE_API_BASE`，build-dmg.sh:94 在 build 期 `export VITE_API_BASE=...` 让 vite 内联进产物（dev 未设 → '' → 走 vite proxy）。
- **后端/electron**：`scripts/build-dmg.sh` 通过 `app/electron/runtime-config.json`（白名单键，由 `runtime-config.ts:29 RUNTIME_CONFIG_WHITELIST` 加载）把 build 期 env 注入 packaged app 的 `process.env`（packaged app cwd=`/`、process.env 干净）。
- **plugin 编译**：`scripts/build-plugins.ts` 把 builtin plugin `.ts` 编成自包含 `.cjs`（external `@app/server`）。

### 1.2 ④③ 两项是前端 UI 呈现，后端零涉及

| 漏出项 | 实现方式 | 落点 |
|---|---|---|
| ① 工具 | **plugin 配置直接摘**（非 feature gate） | `app/plugins/session-types/studio-leader.parent.main.yaml:8-9`（`goal`/`requirement` 行删）+ 同文件 mate/squad |
| ② system prompt | **plugin 配置直接摘**（非 feature gate） | `app/plugins/builtins/rocky_context/prompt/` 下 OKR/requirement 段（rules.ts / identity.ts 等，待 coder 定位具体段） |
| ③ task 卡「所属 requirement」呈现 | **feature gate 管代码**（前端） | `app/web/src/components/studio-page/component-board-task-card.tsx:132` `<span>src · req:{task.source.requirementId}</span>` 条件渲染 |
| ④ 全景 tab | **feature gate 管代码**（前端） | `app/web/src/components/studio-page/component-panorama-route.tsx:52-56` `STATIC_TABS = [goals, requirements, tasks]`——gate 关时滤掉 goals/requirements，仅留 tasks |

③④ 均为前端 React 渲染层，**后端/electron 主进程不需要 feature gate**（工具/prompt 已通过 ①② 在 plugin 配置层摘除，后端不会产出相关数据）。

### 1.3 推荐注入方案

**推荐：vite `define` 编译期常量**（最轻、零运行时开销、对齐 VITE_API_BASE 既有模式）。

- **flag 命名**：`__FEATURE_OKR__`（双下划线表编译期 sentinel，对齐 C/C++/bundlers 约定；TS 需在 `app/web/src/global.d.ts` 或 vite-env.d.ts 声明 `declare const __FEATURE_OKR__: boolean`）。
- **vite.config.ts 注入**（`app/web/vite.config.ts` 加 `define: { __FEATURE_OKR__: JSON.stringify(process.env.FEATURE_OKR === 'true') }`）。
- **dev 行为**：默认关（`FEATURE_OKR` 未设 → `false`），dev 跑时若需调试 OKR 功能显式 `FEATURE_OKR=true bun run dev`。
- **packaged 行为**：`scripts/build-dmg.sh` 默认不 export `FEATURE_OKR`（即关），build 出来的 dmg 对用户隐藏 OKR/req。未来若重启 OKR，build 时 `export FEATURE_OKR=true` 即可，零代码改动。
- **代码读法**：`if (__FEATURE_OKR__) { ...STATIC_TABS 全集... } else { STATIC_TABS.filter(t => t.id === 'tasks') }`——dead-code elimination 让 hidden 分支不进 bundle，对 packaged 体积也有利。

**为什么不选 runtime-config.json**：那是后端 process.env 注入机制（packaged cwd=`/`），而 ③④ 是前端 React 渲染——前端打包后不再读 process.env，必须编译期内联。vite `define` 是标准答案。

**为什么不选 import.meta.env.VITE_FEATURE_OKR**：也可，但 `define` 更显式（不绑 VITE_ 前缀约定）、对齐"编译期常量"语义。两者等价，二选一即可。

### 1.4 风险 / 开放问题

- **TS 类型声明**：`__FEATURE_OKR__` 必须在 `.d.ts` 声明，否则 tsc 报未定义。落 `app/web/src/vite-env.d.ts`（已存在则追加）。
- **UT 影响**：`component-panorama-route` / `component-board-task-card` 现有 UT 假设 goals/requirements tab 与 req 呈现恒存在。gate 关后这些 UT 需适配（mock `__FEATURE_OKR__=true` 跑旧断言，再加一条 `=false` 验隐藏）。
- **mate/squad profile 也需摘工具**：① 摘 toolBound 要覆盖 `studio-mate.parent.main.yaml` / `studio-squad.parent.main.yaml`（如含 goal/requirement）。

### 2.2 响应式宽度问题（写死窄）

**根因**：`component-panorama-kanban.tsx:39` 列宽硬编码 `w-[240px] shrink-0`——固定 240px，`shrink-0` 不允许收缩。

```
refs/local/app/web/src/components/studio-page/component-panorama-kanban.tsx:39
  'flex w-[240px] shrink-0 flex-col rounded-xl border bg-surface ' +
```

容器层（`component-panorama-view.tsx:215`）用 `overflow-y-auto` + kanban 根（line 31）`overflow-x-auto`——列横向溢出滚轮，不响应式。

**改造点**：
- 简单版：去 `shrink-0` + 改 `w-[min(240px,100%)]` 或 `flex-1 min-w-[180px]`，让列在视口窄时收缩。
- 进阶版：用 container query / Tailwind `@container`（v4 支持）/ `clamp()` 算列宽，使列数与视口宽度匹配（视口宽 → 多列平铺；窄 → 少列 + 横滚兜底）。
- 顶层 `component-panorama-route.tsx:131 <main className="flex flex-1 flex-col overflow-y-auto bg-bg">` + line 197 `<div className="max-w-[920px] ...">`（schema 编辑/idle 区）——kanban 区在 view 组件（`px-8 pb-6 pt-5`），列宽改在 kanban.tsx 即可，无需动 route。

### 2.3 甬道色块看不清状态

**根因**：`component-panorama-kanban.tsx:67` 列头只用一个 `h-2 w-2 rounded-full`（8×8px）小圆点表状态色——「色块」太小，远看不清。

```
refs/local/app/web/src/components/studio-page/component-panorama-kanban.tsx:67
  <span className="h-2 w-2 rounded-full" style={{ background: statusColor(entity, col) }} aria-hidden />
```

状态→色映射在 `panorama-utils.ts:47-49 statusColor()`，数据驱动（来自 DSL `entity.display.status_colors[status]`，缺省灰 `#8b949e`），**映射本身没问题**——问题纯是渲染「色块」尺寸/对比度不够。

卡片 badge 也用同色但仅 1px border（line 146 `borderColor: statusColor(...)`）——更不显。

**改造点**：
- 列头色块放大：8×8 → 整条列顶色带（`h-1 w-full` 全宽色条放列顶，或列左缘竖条 `border-l-4` 配色）。
- 列头底色：整列 header 区 `bg-[color-mix(...)]` 或 `style={{ backgroundColor: statusColor + '20' }}`（透明度 20% 作背景）。
- 状态文字带色：列标题文字直接用 statusColor（`text-[color]`），多通道编码（色 + 文 + 计数）防止色弱用户失效。
- 同步卡片：卡片左缘竖条用 statusColor 加强（`border-l-4` + 色）。

### 2.4 风险 / 开放问题

- **设计稿待明确**：req.md §「todo 的视图」末尾「需要看 demo」——kanban 改造可能也有 demo 设计稿待用户提供，PRD/视觉基线未定前不要直接改样式。
- **状态色由 DSL 驱动**：若 DSL 未配 `status_colors`，全部 fallback 灰——「看不清」部分是数据侧（DSL 缺色）+ 渲染侧（色块小）双重。改造需在渲染侧兜底（即使色未配也用对比明显的状态徽章）。

## 4. todo + session 存储 + reminder 现状

### 4.1 Session 数据结构（todo 要加字段的影响面）

权威类型 = `app/server/src/agent/session-store-types.ts:65-218 interface Session`（业务视图），持久化经 `CompositeStore` putAsync/deleteAsync（line 419 `crud: CompositeStore`），4 schema mount。

**加字段模式（lazy default，多处先例）**：
- `effort?`（v0.0.148 line 201）、`approvalMode?`（line 207）、`alwaysApprovedKeys?`（line 214）、`pendingToolCalls?`（v0.0.101 line 90）均「兼容历史 session（无字段）→ toSession lazy 缺省」。
- 加 `todos?: TodoItem[]`：影响面 = Session interface 加字段 + `toSession`（session-store-converters）lazy 缺省 `[]` + `CreateSessionInput` 不加（新建空）+ `UpdateSessionBody`（若 UI 直写）或独立 store。

**两种存储路线**：
- **(A) 嵌入 Session.todos**：简单、reminder 直接读 `config.todos`（同 effort）；但 Session 已 30+ 字段偏臃肿，且 todo 频繁更新会触 Session record 整写。
- **(B) 独立 store（仿 cron）**：`scheduling/persistence/cron-adapter.ts` 走 CrudStore 独立 collection，session 级 key。todo 仿此 = `<DATA_DIR>/sessions/<sid>/todos.json` 独立文件，tool/HTTP 直写不触 Session 主记录，reminder 经 ReminderCtx 扩展读。
- **推荐 (B)**：todo 高频更新（agent 每 turn 可能改），独立 store 避免 Session 频繁整写 + 减少并发写冲突；对齐 cron/memory 的「session 级结构化数据走独立 store」既有模式。
