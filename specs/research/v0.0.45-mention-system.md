### 1.2 popup / autocomplete / suggestion 现状

**完全不存在。** Grep `mention|autocomplete|suggestion|popover|floating|pill|chip` 在 `app/web/src/` 只命中无关上下文（`component-run-finish` 的 `popover` 是 tooltip 误匹配，实际是 `primitive-tooltip`）。

### 1.3 提交链路

```
textarea onKeyDown(Enter)
  → handleSend() [section-chat-detail.tsx:116]
    → onSend(text) [prop]
      → PageChat.handleSend(content) [page-chat.tsx:227]
        → postMessage(activeSessionId, { content, providerId?, modelId? }) [lib/chat-api.ts:141-151]
```

### 1.4 消息渲染与 editor 选型

## Q2 — Skill 系统现状

### 2.1 三层位置与发现机制

| 层 | 路径 | scope 值 | 优先级 |
|---|---|---|---|
| builtin（最低） | `app/plugins/builtins/skills/` | `'builtin'` | 最低 |
| app（中） | `<dataDir>/skills/` | `'app'` | 中 |
| workspace（高） | `<workspace>/.rocky/skills/` | `'workspace'` | 最高 |

**发现机制**：`SkillResolver.resolve()` 同步全量扫描三层目录 + frontmatter 解析 + 按 name 去重合并（workspace > app > builtin）。**无状态、不缓存、每次全量扫**。

代码位置：
- `app/server/src/skills/resolver.ts:139-162`（resolve 主逻辑）
- `app/server/src/skills/resolver.ts:35-54`（三层路径计算）
- `app/server/src/skills/resolver.ts:65-93`（parseSkillDir — 读 SKILL.md frontmatter）
- `app/server/src/skills/resolver.ts:101-123`（scanLayer — 单层扫描）

### 2.2 Skill 列表 API

**Server 端**：

| 端点 | 方法 | 功能 | 代码位置 |
|---|---|---|---|
| `/skill` | GET | 列表（可选 `?workspace=`） | `app/server/src/handlers/skill.ts:146-155` |
| `/skill/:name` | PATCH | toggle enabled | `skill.ts:158-195` |
| `/skill/:name` | DELETE | 物理删除（mv soft_deleted） | `skill.ts:209-227` |
| `/skill/:name/tree` | GET | 文件树 | `skill.ts:230-235` |
| `/skill/:name/file` | GET | 单文件内容 | `skill.ts:238-266` |

**返回字段（SkillEntry）**：

```typescript
// app/server/src/skills/types.ts:24-39
interface SkillEntry {
  name: string;        // kebab-case，= 目录名 = frontmatter name
  description: string; // frontmatter description（≤1024）
  scope: 'builtin' | 'app' | 'workspace';
  skillDir: string;    // 绝对路径
  enabled: boolean;
  source?: 'user' | 'agent';
  productionMethod?: 'handwritten' | 'consolidation' | 'download';
  mutable?: boolean;
}
```

**Web 端**：
- `listSkills(base?, workspace?)` → `GET /skill` → `SkillEntry[]`（`app/web/src/lib/api-client.ts:498-501`）
- 无 web 端 zustand store（skill 页直接调 API，不缓存）

### 2.3 检索维度

**全量枚举，无模糊搜索。** `SkillResolver.resolve()` 每次扫描所有目录，返回完整 `SkillCatalog`。skill 数量预期小（数十个），设计原则明确"新鲜度 > 性能"（`specs/tech/agent/skills/index.md` §4.4）。

## Q3 — Workspace 文件系统现状

### 3.1 现有 workspace API

| 端点 | 功能 | 代码位置 |
|---|---|---|
| `GET /session/:id/workspace/tree` | 文件树 lazy 加载（depth=1） | `app/server/src/handlers/session-workspace.ts:77-161` |
| `POST /session/:id/workspace/open` | 系统应用打开文件 | `session-workspace.ts:192-248` |
| `POST /session/:id/workspace/pick-directory` | 原生 dialog 选目录 | `session-workspace.ts:261-297` |

**无文件搜索/模糊查找 API。** tree 端点只返回一层子项（lazy），不支持递归搜索。

Web 端封装：`getWorkspaceTree()` / `openWorkspaceItem()` / `pickWorkspaceDirectory()`（`app/web/src/lib/chat-api.ts:251-298`）。

### 3.2 索引与排除规则

- **无文件索引**：每次 tree 请求实时 `readdirSync` + `statSync`。
- **排除规则极简**：`IGNORED_NAMES = new Set(['node_modules', '.git'])`（`session-workspace.ts:31`）。与 chokidar `WATCH_OPTIONS` 一致。**无 `.gitignore` 解析**。

### 3.3 Workspace 传递方式

Session 记录中 `workspaceDir: string` 字段（`app/server/src/agent/session-store-types.ts:136`）。前端通过 `GET /session/:id` 获取 `Session.workspaceDir`；切换目录走 `PUT /session/:id { workspaceDir }`（`app/web/src/lib/chat-api.ts:65-75`）。

### 4.4 _conventions.md 新组件 spec 要求

1. 判定层级（primitive/component/section/page/framework）→ 起名（前缀+kebab）

6. 更新 `specs/ui/overall/` 可观测节点表

视觉基线字段（§9，行 89-95）：字体族+字号+字重、关键宽高/padding、边框/圆角、配色 token。

## 未解问题

以下问题需用户拍板，本调研不假设答案：

1. **editor 升级决策**：mention 需要结构化节点（pill/chip）。当前 `<textarea>` 无法渲染内联 pill。是升级到 contenteditable 自研，还是引入 Tiptap/Slate/Lexical？各方案的 bundle size / 学习成本 / 维护成本差异大。
2. **workspace 文件搜索范围**：`GET /workspace/tree` 是 lazy 单层。mention 文件需要搜索能力——是新增递归搜索 API，还是前端拉全树后本地过滤？大目录（>10000 文件）性能如何保证？
3. **`.gitignore` 解析**：当前只排除 `node_modules` + `.git`。mention 文件列表是否需要尊重 `.gitignore`？如需要，是否引入 `ignore` npm 包？
4. **mention 触发字符**：仅 `@` 还是也支持 `/`（slash command）/ `#`（session/channel）？本调研只覆盖 `@` 场景，如需扩展需在架构层预留扩展点。
5. **mention 内容注入方式**：用户选中 mention 后，消息内容如何编码？纯文本 `@skill-name` 还是结构化标记（如 `@[skill-name](skill:xxx)`）？server 端是否需要解析/替换？
6. **studio 单聊页**：studio 的 `chat-placeholder.tsx` 目前是禁用态 textarea。mention 是否也要覆盖 studio 单聊？如果是，两者共享 composer 组件还是各自实现？
