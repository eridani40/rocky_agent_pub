# v0.0.166 竞品调研 — Part A：官方 + Claude Code 生态 + 社区 skill 市场

> 调研范围 A：为「搜索 + 安装 skill」后端 + UI 市场做竞品/格式调研。我们项目 skill 格式 = Anthropic Agent Skills（`SKILL.md` + YAML frontmatter: name/description，目录式，可含脚本/资源）。
> 限时聚焦调研（≤12 次工具调用），结论先行。

---

## 核心结论（TL;DR）

1. **skill 格式已标准化，manifest 极简**：Anthropic Agent Skills = 目录 + `SKILL.md`（YAML frontmatter 只强制 `name` + `description`，body 是 Markdown 指令）。**单个 skill 没有独立 manifest/index 文件**——frontmatter 就是它的全部元数据。我们的格式与官方完全一致，可直接兼容。

2. **分发 = git-backed，安装 = clone/copy 到本地缓存**：官方仓库、Claude Code 插件市场、社区 marketplace 全部基于 git 仓库分发；Claude Code `/plugin install` 会把目录**复制**到 `~/.claude/plugins/cache`。没有中心化包注册中心（无 npm-registry 式的官方 registry）。

3. **唯一的「聚合元数据」来自 Claude Code 的 `.claude-plugin/marketplace.json`**——这是生态里最结构化的清单，字段丰富（见下表），是我们后端「搜索索引 + 分类/标签」最现实的数据源。但注意它是 **plugin 级**而非 skill 级（skill 是 plugin 的一个组件）。

4. **下载量 / 评分 / 热度：git-backed 源几乎全部拿不到**。GitHub 只有 stars/forks（仓库级，非 skill 级）。真正有「install 数 / 评分 / 评论」的只有少数**中心化托管平台**（Agensi、SkillsMP 用 star 数近似），而非我们要对接的 git 源。→ **UI 市场页的「热度/评分」需要我们自建，或降级为 GitHub stars。**

5. **社区 marketplace 规模与分类**：主流社区仓库（superpowers 14 skills、claude-code-templates 100+ 组件、davila7 有 aitmpl.com 网页目录）**普遍带分类（目录路径即分类）+ GitHub topic 标签**，但分类是非标准的、各家自定义。搜索能力靠 GitHub 或各自网站，无统一 API。

## 2. Claude Code 插件市场（`.claude-plugin/marketplace.json`）

URL: https://code.claude.com/docs/en/plugin-marketplaces ; https://code.claude.com/docs/en/plugins-reference

**这是生态中最结构化、字段最丰富的清单格式——我们搜索后端的首选参考。**

### `marketplace.json` schema（顶层）
- **必填**：`name`（kebab-case）、`owner`（含 `name`）、`plugins`（数组）
- **可选**：`$schema`、`description`、`version`、`metadata`、`allowCrossMarketplaceDependenciesOn`、`renames`

### 每个 plugin 条目字段
- **必填**：`name`、`source`
- **可选**：`displayName`、`author`、`homepage`、`repository`、`license`、`keywords`、`category`、`tags`、`strict`、`relevance`、`defaultEnabled`
- **组件路径**：`skills`、`commands`、`agents`、`hooks`、`mcpServers`、`lspServers`

> 关键：`category` / `tags` / `keywords` / `displayName` / `description` / `author` / `license` 都是**声明式可读的结构化元数据** → 直接可喂给我们的搜索/筛选 UI。

### source 类型（安装来源）
- 相对路径 `./plugins/x`、`github`（含 `repo`）、`url`（git）、`git-subdir`（monorepo 取子目录）、`npm`

### `/plugin marketplace add <target>` 机制
- target 支持：GitHub 简写、git URL、直接指向 JSON 文件的链接、本地路径；可 `@ref` 锁定分支
- 注册表存于 `~/.claude/plugins/known_marketplaces.json`

### 安装机制
- `/plugin install <name>@<marketplace>` → 目录**复制**到本地缓存 `~/.claude/plugins/cache`
- 因为是复制，插件**不能**用 `../shared-utils` 访问外部目录（自包含约束）

### plugin ↔ skill 关系（plugins-reference）
- plugin 通过根部 `skills/` 文件夹（`<name>/SKILL.md` 结构）或根 `SKILL.md` 打包 skill
- `plugin.json` 的 `skills` 字段可指定额外 skill 目录（追加到默认扫描）
- 组件安装时**自动发现**；skill 调用名取 frontmatter `name` 或目录 basename
- **skill 是 plugin 的子组件**——marketplace 清单描述的是 plugin，skill 元数据仍在各自 `SKILL.md`

## 5. 关键判断 — 对我们 UI 市场页的直接含义

### git-backed 源能提供的结构化元数据（可放进 UI）
从 **`.claude-plugin/marketplace.json`** 可靠拿到（plugin 级）：
- `name` / `displayName` / `description` / `author` / `homepage` / `repository` / `license`
- `category` / `tags` / `keywords`（→ 分类筛选、标签、搜索关键字）
- 组件清单：`skills` / `commands` / `agents` 路径（→ 展示「此 plugin 含哪些 skill」）
- `source`（→ 安装：github/git-subdir/url/npm/本地）

从 **单个 SKILL.md frontmatter** 拿到（skill 级）：
- `name`、`description`（**仅此二者是强制**，是 skill 级唯一可靠元数据）

从 **GitHub API**（仓库级，非 skill 级）可补：
- stars / forks / 最近更新时间 / 开源 license（可作弱热度代理）

### git-backed 源「拿不到」的（UI 别指望）
- ❌ **真实下载量 / 安装数**（无中心化统计端点）
- ❌ **用户评分 / 评论**
- ❌ **热度排序**（除非用 GitHub stars 近似，但那是仓库级不是 skill 级）
- ❌ **统一搜索 API**（去中心化 GitHub 注册表，无聚合 API）

### 设计建议（给后端 + UI 决策）
1. **搜索索引数据源**：以 `.claude-plugin/marketplace.json`（plugin 级：category/tags/keywords/description）+ 各 skill 的 `SKILL.md` frontmatter（name/description）为主。我们需**自己 clone/拉取 git 源后解析并建索引**（没有现成搜索 API 可调）。
2. **安装机制对齐生态**：git clone / git-subdir 取子目录 → 复制到本地 skills 目录（与 Claude Code `~/.claude/plugins/cache` 复制式安装同构，自包含、不许外部相对路径）。
3. **热度/评分栏位**：git 源无此数据 → 要么**降级用 GitHub stars/更新时间**做弱排序，要么**自建**（本地安装计数 / 我们自己的评分系统）。UI 设计不要假设能从上游拿到 install 数或评分。
4. **分类是非标准的**：官方 4 大类 vs 社区各自目录分类不统一 → 若要统一分类筛选，需我们做一层映射/归一。
