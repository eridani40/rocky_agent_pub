## 1. 概述

refs/ 中**三个**仓库有成熟的 cron/定时调度实现，恰好覆盖 v0.0.58 三大需求点：

| 仓库 | 模块 | 与 v0.0.58 的契合点 |
|---|---|---|
| `refs/claude-code/src/utils/cronScheduler.ts` | 1s 轮询调度器 + cron 工具 + 持久化 | **直接对应** scheduler 单例 + cron tool + lastFiredAt 续接；现有 `[P1]scheduler.md` 已部分引用 |

## 2. claude-code cronScheduler 深入（主参考）

### 2.1 模块拆分（清晰四层）

```
src/utils/cron.ts           # 5 字段 cron expr 解析 + computeNextCronRun + cronToHuman（自实现，零依赖）
src/utils/cronTasks.ts      # CronTask 类型 + .claude/scheduled_tasks.json 读写 + 抖动算法
src/utils/cronTasksLock.ts  # O_EXCL 排他锁 + PID liveness probe + stale 恢复（多 REPL 共享 cwd）
src/utils/cronScheduler.ts  # createCronScheduler()：1s 轮询主循环 + chokidar watch + lockProbe
src/tools/ScheduleCronTool/ # CronCreate / CronList / CronDelete 三个 LLM 工具 + prompt + UI
src/hooks/useScheduledTasks.ts # REPL 接入：onFire = enqueuePendingNotification（投递到 lead）
src/cli/print.ts:2709       # SDK / -p 模式接入：onFire = enqueue + run()
```

### 2.2 1s 轮询机制（`cronScheduler.ts:230-394`）

`CHECK_INTERVAL_MS = 1000`（`cronScheduler.ts:40`）。`check()` 每 tick：

1. **killswitch**：`if (isKilled?.()) return` —— `cronScheduler.ts:231`，每 tick 轮询，**不是缓存**（toggle ≤1s 生效）。
2. **isLoading 跳过**（即 busy）：`if (isLoading() && !assistantMode) return` —— `cronScheduler.ts:232`。REPL 模式 `isLoading = REPL 正在跑 query`；mode 等下一个 1s tick 再尝试（不堆积，不丢失，等当前 turn 结束自然 drain）。
3. 遍历 `tasks`：每 task 维护 `nextFireAt: Map<id, epochMs>`。`now < next` 跳过；到点 → `onFire(prompt)` / `onFireTask(task)`。
4. **first-sight 锚定**（`cronScheduler.ts:253-281`）：从未见过的 task，从 `lastFiredAt ?? createdAt` 计算 next（防止进程重启后 nextFireAt 内存丢失，从磁盘 lastFiredAt 重建）。
5. **reschedule from now**（`cronScheduler.ts:315-324`）：recurring 到点 fire 后，`newNext = jitteredNextCronRunMs(cron, now, ...)` —— **从 now 重排，不追溯**（即错过多次只跑一次，claude-code 称为 "no rapid catch-up"）。
6. **batched lastFiredAt 落盘**（`cronScheduler.ts:358-369`）：`firedFileRecurring[]` 在 tick 末尾一次 `markCronTasksFired` 写盘（N fires = 一次 read-modify-write）。
7. `.unref()`（`cronScheduler.ts:459`）：`checkTimer.unref?.()` —— 不阻塞进程退出（`-p` 单 turn 模式跑完即退）。

### 2.3 lastFiredAt 续接（`cronTasks.ts:30-65, 261-278`）

`CronTask.lastFiredAt?: number`（epoch ms）。**只在 recurring fire 后写回**，one-shot 不写（fire 即删）。

续接链路：
- 进程重启 → `start() → load(true) → readCronTasks()` 读盘（`cronTasks.ts:91-140`）
- check() 首次见 task → `jitteredNextCronRunMs(cron, t.lastFiredAt ?? t.createdAt, ...)` —— 锚 lastFiredAt（`cronScheduler.ts:264`）
- fire 后 → `markCronTasksFired(ids, now, dir)`（`cronTasks.ts:261-278`）写盘 lastFiredAt=now

> **关键不变式**（`cronTasks.ts:38-46` 注释）：内存 nextFireAt 与磁盘 lastFiredAt 计算出的 next 必须一致，否则 daemon 子进程 despawn 时丢失 nextFireAt 后下次 spawn 会从 10 天前的 createdAt 重锚 → 每个 cycle 全部 task 误触发。

### 2.4 busy 跳过与 fire-and-forget

`cronScheduler.ts:232` 的 `isLoading()` 是 **gate 性质**：当前正在跑 → 整个 tick 直接 return（不发任何 task）。

但 `onFire` 本身**同步投递**到 inbox（REPL `useScheduledTasks.ts:71-82` 用 `enqueuePendingNotification({priority:'later'})`；`-p` 模式 `print.ts:2710-2728` 用 `enqueue + void run()`）。run 有 mutex，若已在跑则 no-op，由 post-run recheck 自 drain。

> 对照 v0.0.58：现有 `[P1]scheduler.md §4 gate3` 已经把 busy check 放在 deliverTo **前**（防 tick 堆积）。claude-code 的"isLoading 跳过整 tick"是同思路但更粗（整 tick 0 fire vs 我们的 per-role 判 busy）。

### 2.5 cron expr 解析（自实现，零依赖 — `cron.ts`）

5 字段 minute-hour-dom-month-dow，**不支持 L/W/?/name 别名**（`cron.ts:1-9` 注释明确）。

- `expandField()`（`cron.ts:31-77`）：支持 `*`、`*/N`（步长）、`N-M`、`N-M/S`、`N,M,...`、单 `N`。dayOfWeek 接受 `7=Sunday`。
- `parseCronExpression()`（`cron.ts:83-101`）：5 字段必填，每字段独立 expand，返回 `{minute[],hour[],dayOfMonth[],month[],dayOfWeek[]}` 或 null。
- `computeNextCronRun(fields, from)`（`cron.ts:119-181`）：从 `from` 严格向后走，**分钟级迭代**（`maxIter = 366*24*60`），返回下一个匹配 Date 或 null。处理了 **dom/dow OR 语义**（`cron.ts:151-158`：当两者都 constrained，任一匹配即触发——标准 vixie-cron 行为）。
- **时区**：所有时间用**进程本地时区**（`cron.ts:7-8`），不支持 per-job tz。
- DST（`cron.ts:108-118` 注释）：spring-forward gap 跳过当天；fall-back repeat 仅触发一次。

> v0.0.58 决策：req.md 已说"用户时区"。直接搬 claude-code 实现 + 加 per-job tz 字段即可（参考 openclaw 的 `Intl.DateTimeFormat().resolvedOptions().timeZone` fallback — `schedule.ts:13-19`）。

### 2.6 killswitch（双层）

- `isKairosCronEnabled()`（`prompt.ts:36-45`）：feature flag `AGENT_TRIGGERS` × GrowthBook `tengu_kairos_cron`（5 min refresh cache）× env `CLAUDE_CODE_DISABLE_CRON`。注入到 scheduler 作 `isKilled: () => !isKairosCronEnabled()`（`useScheduledTasks.ts:119`）—— 每 tick 轮询，toggle 后 ≤1s 生效。
- `isDurableCronEnabled()`（`prompt.ts:56-62`）：更窄，只 kill durable 持久化路径，session-only cron 不受影响（在 `CronCreateTool.ts:120` 强制 `effectiveDurable = durable && isDurableCronEnabled()`）。

### 2.7 持久化与重启续接

- 文件：`<project>/.claude/scheduled_tasks.json`，shape `{tasks: CronTask[]}`（`cronTasks.ts:74, 165-182`）。每次写完 `mkdir .claude`（idempotent）+ 末尾换行。
- **session-only task**（`durable: false`，默认）：bootstrap state in-memory only，**不写盘**，进程死即销毁。scheduler check() 每 tick 直接从 `getSessionCronTasks()` 读（不依赖 chokidar，`cronScheduler.ts:376-378`）。
- **file task**（`durable: true`）：写盘，chokidar watch（`cronScheduler.ts:441-454`），`awaitWriteFinish.stabilityThreshold = 300ms`（防半写）。
- **重启 missed task 补偿**（`cronScheduler.ts:179-228`）：startup `load(initial:true)` 时 `findMissedTasks(tasks, now)`（next 在过去的 one-shot），调 `onMissed` 或 `onFire(buildMissedTaskNotification())` 让用户/lead 决定补跑。**recurring missed 不补**（check() 会自然到点 fire，`cronScheduler.ts:191-192` 注释）。

### 2.8 多 REPL/cwd 锁（`cronTasksLock.ts`）

`.claude/scheduled_tasks.lock`，`O_EXCL 'wx'` atomic create（`cronTasksLock.ts:64-91`）。锁内容 `{sessionId, pid, acquiredAt}`。

- 非持有者每 `LOCK_PROBE_INTERVAL_MS = 5000` 重试（`cronScheduler.ts:43, 418-436`）。
- PID liveness probe（`isProcessRunning`）→ stale 自动抢占。
- `--resume` 后 sessionId 不变 pid 变 → 自动更新锁文件（`cronTasksLock.ts:139-145`）。

> v0.0.58：单进程部署可不做（`[P1]scheduler.md §9` 已留 hook）。但**多 squad 隔离**对应的是"多 cwd"场景——claude-code 是 per-cwd scheduler 实例，我们是 per-squad 实例，每个 squad 自己 own 一份 jobs.json。

### 2.9 多 job 并发处理

claude-code 是**串行 fire**（check() 单线程循环遍历 tasks），但**onFire async 投递不 await**（`useScheduledTasks.ts:71` enqueuePendingNotification 同步入队；`print.ts:2727 void run()` fire-and-forget）。所以从 tick 角度看是串行触发 + 异步执行；同一 task 不会双触发（`inFlight` set 防双 fire，`cronScheduler.ts:170, 335-343`）。

## 3. 其他 refs 框架的定时/cron/heartbeat

### 3.1 hermes-agent/cron（Python，最完整）

**Tool 层**（`tools/cronjob_tools.py`）：单一 `cronjob(action=...)` 工具，action ∈ `create/list/update/pause/resume/remove/run`（`cronjob_tools.py:465-716`）。**所有 cron 工具合并为一个 schema**，注释（`cronjob_tools.py:5-7`）说"avoid schema/context bloat"。

- schedule 输入支持多种格式：`30m`（one-shot）、`every 2h`（recurring）、`0 9 * * *`（cron）、ISO timestamp（`jobs.py:289-375 parse_schedule`）。
- 持久化：`~/.hermes/cron/jobs.json`（`jobs.json`），shape `{jobs: [...], updated_at}`（`jobs.py:559-560`）。**原子写**：`tempfile.mkstemp + os.fsync + atomic_replace`（`jobs.py:557-570`）。
- 跨进程锁：`~/.hermes/cron/.jobs.lock`，`fcntl.flock LOCK_EX` 阻塞型（`jobs.py:69-129`）。**注释（jobs.py:75-83）说明**：threading.RLock（进程内并发 tick 线程）+ flock（gateway 进程 vs standalone CLI 跨进程）。
- **调度触发**：外部 gateway 每 60s 调 `tick()`（`scheduler.py:1-9, 1970-2209`），不在 scheduler 内自己 setInterval。
- **tick 内并发**（`scheduler.py:1970-2197`）：
  - `advance_next_run()` 先于执行推进 recurring job 的 next_run_at（at-most-once 语义，`scheduler.py:2017-2018`）。
  - 拆分 sequential_jobs（带 workdir，env-mutating，必须串行）vs parallel_jobs（无 workdir，可并行，`scheduler.py:2095-2096`）。
  - `_get_sequential_pool()`：单 worker ThreadPool，跨 tick 保序（`scheduler.py:190-204`）。
  - `_get_parallel_pool(max_workers)`：可配 ThreadPool（`scheduler.py:176-187`）。
  - `_running_job_ids` set + `_running_lock`（`scheduler.py:166-167, 2101-2123`）：fire-and-forget 提交时 if in set 跳过（防上一 tick 还在跑的同 job 重复触发）。
- **next_run 计算**（`jobs.py:456-499`）：cron kind 用 `croniter(expr, last_run_at or now).get_next(datetime)` —— **锚 last_run_at**（同 claude-code 不变式），重启后从 last 而非 now 续接。

**Stale fast-forward**（`jobs.py:1060-1159`）：`_compute_grace_seconds = clamp(period/2, 120s, 2h)`（`jobs.py:424-453`）。gateway 重启后若 `now - next_run_at > grace`，**不补跑直接重排到下次**（避免重启雪崩）。

> v0.0.58 可借鉴：1) advance_next_run at-most-once；2) workdir/无 workdir 拆 sequential/parallel；3) atomic_replace 落盘。

### 3.2 openclaw/src/cron（TS，最抽象）

**Service 抽象**（`service.ts:14-83`）：`CronService implements CronServiceContract`，方法 `start/stop/status/list/listPage/add/update/remove/run/enqueueRun/getJob/readJob/wake`。**纯 facade**，实现在 `service/ops.ts`（1082 行）+ `service/state.ts`（277 行）+ `service/timer.ts`（2265 行）。

**schedule 三 kind**（`types.ts:9-18`）：
```typescript
type CronSchedule =
  | { kind: "at"; at: string }                                      // 一次性
  | { kind: "every"; everyMs: number; anchorMs?: number }           // 间隔
  | { kind: "cron"; expr: string; tz?: string; staggerMs?: number } // cron expr
```

**调度算法 = setTimeout 自适应（非 1s 轮询）**（`service/timer.ts:1058-1123 armTimer`）：
- `nextWakeAtMs(state)` 找最近 job.nextRunAtMs。
- `setTimeout(onTimer, min(delay, MAX_TIMER_DELAY_MS=60_000))` —— 没到点 job 时长 sleep，到点就触发；MAX 60s 兜底防 drift。
- `MIN_REFIRE_GAP_MS = 2_000`（`timer.ts:104`）：完成到下一 fire 至少 2s 间隔，防 cron 边界 spin-loop（issue #17821）。

**cron 解析用 `croner` 库**（`schedule.ts:3`）：`new Cron(expr, {timezone, catch: false})`。LRU cache 512 条（`schedule.ts:11-41`）。croner 比 croniter 更现代，支持 5/6 字段 + tz。

**Heartbeat 集成**（`timer.ts:1918-2054 executeMainSessionCronJob`）：cron 触发后调 `state.deps.runHeartbeatOnce()` 或 `requestHeartbeat()` —— **cron 不是直接 run agent，而是发 heartbeat 唤醒 main session**（类似我们的 `deliverTo(sessionId) + tickMessage`）。

**反 thundering-herd stagger**（`stagger.ts:51-53`）：top-of-hour 默认 stagger 5min（`DEFAULT_TOP_OF_HOUR_STAGGER_MS = 5*60*1000`）。

> v0.0.58 可借鉴：1) at/every/cron 三 kind union 类型；2) setTimeout 自适应 vs 1s 轮询的取舍（claude-code 1s 简单，openclaw setTimeout 省电但状态机复杂）；3) main session job 用 heartbeat 唤醒而非 spawn——跟我们 deliverTo 一致。

## 4. cron expr 人话化展示

### 4.1 refs/ 中实现

**仅 `refs/claude-code/src/utils/cron.ts:183-308` 有 `cronToHuman(cron, opts?)`**：

- 覆盖模式（`cron.ts:231-307`）：`*/N * * * *` → "Every N minutes"、`M H * * *` → "Every day at HH:mm"、`M H * * D` → "Every Sunday at..."、`M H * * 1-5` → "Weekdays at..."。
- **不支持的直接返回原始 cron expr**（`cron.ts:307`）。
- `utc?: boolean` 选项（`cron.ts:218`）：CCR 远程触发用 UTC cron，UTC → 本地展示（含跨午夜 weekday 重算，`cron.ts:288-298`）。
- 时间格式化用 `Date.toLocaleTimeString('en-US', {hour:'numeric', minute:'2-digit'})`（`cron.ts:200-205`）。
- **英文**输出，无中文。代码注释（`cron.ts:183-188`）说"Intentionally narrow: covers common patterns; falls through to the raw cron string for anything else"。

**hermes-agent / openclaw**：均**无人话化**。hermes 存 `schedule_display` 字段（创建时直接写 `"every 30m"` / `"0 9 * * *"` 原样字符串，`jobs.py:318, 337, 753`）；openclaw UI 直接渲染 expr。

claude-code 的 cron 工具调用结果 UI（`UI.tsx:17-24, 46-57`）：`Scheduled <id> (<humanSchedule>)`，lead 用户读人话；list 视图同样 `<id> <humanSchedule>`。

### 4.2 v0.0.58 实现建议

- **不要照抄 claude-code `cronToHuman`**：1) 仅英文；2) 覆盖窄（范围/list/复合 expr 直接 fallback raw）；3) 自实现维护成本。
- **推荐：选 npm 库 + UI 层包装中文模板**。候选对比：
  | 库 | 大小 | 中文 | 双向（parse + stringify） | 备注 |
  |---|---|---|---|---|
  | `cronstrue` | ~50KB | ✅ 内置 i18n（含 zh_CN） | stringify only | 最流行，覆盖最全 |
  | `cron-parser` | ~30KB | ❌（仅 parse/iter） | parse only | 解析+迭代，无翻译 |
  | `cron-expression-parser` | ~20KB | ❌ | parse + toHuman（en） | 较小众 |
  | `croner` | ~15KB | ❌ | parse + iter（openclaw 用） | 无翻译，纯解析 |
- **推荐方案**：`cronstrue`（直接 zh_CN 输出 "每 30 分钟"、"周一至周五 09:00"）+ 自实现"频率选择器"（req.md 需求 2）→ 后端 cron expr 的双向转换（选「每 30 分钟」UI → 生成 `*/30 * * * *`；后端 expr → cronstrue → 中文展示）。
- claude-code 的 fallback 策略可借鉴：库翻译不出的 expr 直接展示 raw（高级用户/自定义场景）。

## 5. cron 触发动作（醒着的人怎么唤醒 agent）

refs/ 三家**全部用"投递消息 + 唤醒现有 session"模式**，没有 spawn 子进程的：

| 仓库 | 触发动作 | 代码位置 |
|---|---|---|
| claude-code（REPL） | `enqueuePendingNotification({value:prompt, priority:'later', isMeta:true, workload:WORKLOAD_CRON})` → lead 命令队列 | `useScheduledTasks.ts:71-82` |
| claude-code（-p/SDK） | `enqueue({mode:'prompt', value:prompt, priority:'later', isMeta:true}) + void run()` → headless 单 turn | `print.ts:2710-2728` |
| claude-code（teammate） | `injectUserMessageToTeammate(teammate.id, task.prompt)` → 直接 push 到 teammate 的 user message queue | `useScheduledTasks.ts:91-108` |
| hermes-agent | `AIAgent(model, session_id=f"cron_{job_id}_{ts}").run_conversation(prompt)` —— **新建 ephemeral session 跑一轮**，结果通过 `_deliver_result` 发到 telegram/discord/origin | `scheduler.py:1726-1892` |
| openclaw（main） | `enqueueSystemEvent(text, {agentId, sessionKey}) + requestHeartbeat({target:'last'})` —— 系统事件入队 + heartbeat 触发 main session drain | `timer.ts:1948-2052` |
| openclaw（isolated） | `runIsolatedAgentJob({job, message})` —— 起独立 isolated agent 跑一轮 | `timer.ts:2128-2135` |

**与 v0.0.58 `deliverTo(sessionId) + tickMessage` 对照**：
- claude-code `enqueuePendingNotification` ≈ 我们的 `enqueue(msg)`；REPL 没有"激活"步骤（命令队列自己 drain）。
- openclaw `enqueueSystemEvent + requestHeartbeat` ≈ 我们的 `enqueue + activate(sessionId)`（即 `deliverTo`）。
- **claude-code teammate 路径**（`useScheduledTasks.ts:92-108`）值得参考：cron 创建时记 `agentId`，触发时路由到对应 teammate 的 queue —— **跟 v0.0.58 "cron 归属 session，触发只唤醒该 session" 完全对应**。注：claude-code teammate cron 强制 `durable:false`（`CronCreateTool.ts:107-114`），因为 teammate 不跨 session 存活；v0.0.58 squad member cron 同理（member session 销毁即停）。
- **orphan 清理**（`useScheduledTasks.ts:101-108`）：fire 时发现 teammate 已死 → 自动 `removeCronTasks([task.id])` 防无限触发。**v0.0.58 session 销毁时必须注销其 cron jobs**（req.md 已写）。

## 6. 对 v0.0.58 的可借鉴建议

### 6.1 调度器抽象（需求 3 核心）

1. **直接借鉴 claude-code 模块四层拆分**（`cron.ts` 解析 / `cronTasks.ts` 持久化 / `cronTasksLock.ts` 锁 / `cronScheduler.ts` 主循环），把 v0.0.58 的 `app/server/src/scheduler/` 拆成同构：
   - `scheduler/cron-expr.ts`（搬 `cron.ts` 自实现，0 依赖）
   - `scheduler/cron-store.ts`（per-session `cron.json` 读写 + lastFiredAt 落盘）
   - `scheduler/engine.ts`（1s 轮询单例，handler registry）
   - job handler 按 type 注入（heartbeat handler / cron handler）

2. **handler registry 数据驱动**：注册项 `{id, type, owner, schedule, payload, lastFiredAt}` 完全对应 claude-code `CronTask` + openclaw `CronJob`。type 决定 handler 实现 → 满足 req.md "重启续接按 type 重建 handler"。

3. **fire-and-forget**（req.md 已决）：engine 调 handler 不 await，参考 claude-code `print.ts:2727 void run()` + hermes `_submit_with_guard` fire-and-forget ThreadPool 提交。**注意**：handler 内部门控 + async 自处理。

4. **选 1s 轮询（claude-code）而非 setTimeout 自适应（openclaw）**：v0.0.33.4 已选 1s（`[P1]scheduler.md §1`），保持一致；统一引擎延续此选择，降低复杂度（无 setTimeout 链式 rearm 状态机）。

### 6.2 cron job 持久化与续接

1. **session 级 `cron.json`**（req.md 已定）：shape 借鉴 claude-code `{tasks: CronTask[]}`，每 task 含 `{id, cron, prompt, name, enabled, createdAt, lastFiredAt?}`。
2. **原子写**：照 hermes `tempfile + fsync + atomic_replace`（`jobs.py:557-570`）或 Node `fs.rename` tmp→target 模式。避免半写。
3. **lastFiredAt 续接不变式**（claude-code 教训）：内存 nextFireAt 必须从磁盘 lastFiredAt 可重算出相同值。每次 fire 后**立即**落盘 lastFiredAt（`cronScheduler.ts:358-369`），不要积批。
4. **重启不补 recurring**（claude-code/`[P1]scheduler.md §6` 一致）：recurring missed 自然到点 fire；one-shot missed 走 onMissed 回调（v0.0.58 cron 都是 recurring 可省，但 hermes/openclaw 都有 one-shot 概念，未来扩展预留）。

### 6.3 cron expr 解析与人话化

1. **解析**：搬 claude-code `cron.ts`（零依赖、5 字段、含 dom/dow OR 语义）。若需 per-job tz → 改用 `croner`（openclaw 同款，~15KB，支持 tz）。
2. **人话化**：UI 层用 `cronstrue`（zh_CN 内置），fallback raw expr；**工具层仍收 raw cron expr**（req.md 已决）。
3. **频率选择器双向转换**（req.md 需求 2）：参考 claude-code `cronToHuman` 的模式判定（every-N-min / every-hour / daily-HH:mm / weekly / weekdays），UI 选定后程序生成 expr。

### 6.4 gate 下沉 handler（req.md 已决）

claude-code 的 `isLoading` gate 在 scheduler 层（粗，整 tick 跳过），v0.0.58 **gate 下沉 handler** 更细：
- heartbeat handler：gate = squad.enableHeartBeat + squad.budget + busy（`[P1]scheduler.md §4` 已有，迁移即可）
- cron handler：gate = busy（session.state==='running' → 跳过当周期，下 tick 重来）；squad session 额外查 squad budget；playground 无 budget gate（req.md 已决）

### 6.5 边界与坑

1. **reschedule from now（不追溯）**：claude-code/hermes/openclaw 三家一致——错过多次只跑一次（at-most-once）。`[P1]scheduler.md §6` 已采此模式，公共化引擎保持。
2. **killswitch 每 tick 轮询**：`isKilled` 不缓存（claude-code `cronScheduler.ts:231`），toggle 后 ≤1s 生效。我们的 squad.enableHeartBeat 已同模式（`[P1]scheduler.md §4`）。
3. **`.unref()`**：所有 setInterval 必须 `.unref()`（test-process-cleanup-or-crash 教训）。claude-code 三个 timer 全 unref（`cronScheduler.ts:435, 459, 497`）。
4. **多 session 锁**：单进程无需 lockfile（v0.0.33.4 `[P1]scheduler.md §9` 已留 hook）。多进程部署时再参考 claude-code `cronTasksLock` 的 `O_EXCL + PID probe + stale recovery` 模式。
5. **session 销毁注销 cron**：照 claude-code teammate orphan 清理（`useScheduledTasks.ts:101-108`）—— session 销毁/归档时遍历 cron.json，删 owner=该 session 的 jobs。
6. **batched lastFiredAt 写盘**：v0.0.58 per-session cron jobs 数量预期很小（< 10），可不必 batch（每次 fire 一次写即可）；如未来单 session 大量 job 再考虑 batch。

### 6.6 工具 schema 设计

参考 hermes `cronjob(action=...)` 单工具多 action（vs claude-code 三个独立工具 CronCreate/CronList/CronDelete）：
- **hermes 优势**：LLM schema 上下文小（一个工具描述）；action 枚举清晰；扩展 action 不增 schema 数。
- **claude-code 优势**：每工具独立 enabled/searchHint，UI render 独立。
- **v0.0.58 建议**：req.md 列了 6 个工具（create/list/update/disable/enable/delete），按 6 独立工具实现（对齐现有 squad 工具风格，每工具独立 schema/testid/UI）；如果 LLM 上下文成问题再合并为 `cron(action)` 单工具。
