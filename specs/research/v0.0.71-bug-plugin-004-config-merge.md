# BUG-PLUGIN-004 深挖：config merge 现状 + 修复方案

> 范围：聚焦 `PluginManager.instantiate()` 当前 merge 了哪几层、缺哪几层、D7 删 schemaConfig 后的目标表达式。是 v0.0.71 锁定决策 D7（删 schemaConfig）+ bug-A（inventory JOIN manifest default）+ BUG-PLUGIN-004（instantiate 缺层）三件事在 instantiate() 的交汇点。

## 1. 现状代码 — instantiate() 逐行

**入口**：`app/server/src/plugin/plugin-manager.ts:155-165` `private instantiate<T>(entry, sourceScope): T`

```ts
private instantiate<T>(entry: RegisteredExtImpl, sourceScope: string): T {
  const ImplClass = entry.implClass as new (...args: unknown[]) => T;
  const cfg = this.scopeConfigs.getImplConfig(sourceScope, entry.manifest.implId);
  const defaults = extractConfigDefaults(entry.manifest.configSchema);
  const merged = {
    ...defaults,
    ...(cfg?.configValues ?? {}),
  };
  return new ImplClass(entry.manifest.implId, merged);
}
```

**`extractConfigDefaults()`**（同文件 `:173-184`）只取 `configSchema.properties.{key}.default`（不是顶层 `configSchema.default`），无 schema / 无 properties → 返空对象。

**结论**：当前合并**两层**：
1. `entry.manifest.configSchema.properties.{key}.default`（impl 级 configSchema 的 properties.default 提取）
2. `cfg.configValues`（来自 `ScopeConfig.impls[implId].configValues`）

**缺**：
- `PluginManifest.config`（plugin 级默认值整块）— 从未被 instantiate 读取
- `PluginManifest.configSchema`（plugin 级 schema）— 从未被 instantiate 读取
- `ExtImpl.schemaConfig.{key}.default`（per-key UI default）— 从未被 instantiate 读取
- **浅 merge**：`{...defaults, ...configValues}` 是 spread 浅 merge，嵌套 object 字段会被 configValues 整体替换而非递归合并

`extractConfigDefaults` 只在 instantiate 一处被调用（grep 全文确认）。

**结论：v0.0.67 已完成「读源切到 scopes」**，PluginManager 完全不读 plugin_policy 落盘。

链路（每环节 file:line）：
1. `app/plugins/scopes/default.json:32-41` — `impls.{id}.configValues` 字段（**当前 default.json 实际未声明任何 configValues**，仅 `order` 字段）

## 4. deepMerge 必要性 — 7 个 configSchema 是不是嵌套？

**结论：当前 7 个 configSchema 全是扁平单层 key**，浅 merge 与 deepMerge 在数据上**等价无差别**。

逐个核实（grep `additionalProperties` + `properties`）：

| implId | configSchema.properties 字段 | 形状 |
|---|---|---|
| `query_truncate` (`plugin.json:11-17`) | `queryTruncateChars: integer` | 扁平 |
| `tool_result_truncate` (`:27-33`) | `toolResultTruncateChars: integer` | 扁平 |
| `budget_truncate` (`:129-137`) | `budgetFraction: number` / `floor: integer` / `ceiling: integer` | 扁平 |
| `transcript_reader` (`:150-157`) | `limit: integer` | 扁平 |
| `base_builder` (`:180-192`) | `headMin/headMax/headFraction/tailMin/tailMax/tailFraction`（6 个 number/integer） | 扁平 |
| `threshold_should_compact` (`:287-293`) | `compactRatio: number` | 扁平 |
| `zhipu` (`zhipu_web_search/plugin.json:11-22`) | `apiKey: string` | 扁平 |

**判断**：当前数据形状下，浅→深 merge 对运行值**零影响**。但 spec §3.5/§3.7 明文 deepMerge 是为「未来 plugin 嵌套 object（如 `credentials: {key, header}` / `pricing: {input, output}`）」预留——一旦未来 plugin 用了嵌套 object，浅 merge 会沉默丢失嵌套字段（教训：`resolve-provider-config.ts:79-104` 的 deepMerge 就是为 `credentials` / `pricing` 嵌套对象存在）。

**修复应使用 deepMerge**：即使当前 7 个 configSchema 扁平，对齐 spec + 为未来嵌套 object 预留。

### 风险

1. **行为漂移最小**：当前 7 个 configSchema 全扁平（§4），浅 merge 与 deepMerge **数据等价零差别**——改完跑现有 UT 应**全绿**（4 个 merge case 在扁平数据下行为不变）。如果现有 UT 红了，说明某 case 涉及嵌套 object，需个案检查。
2. **deepMerge 的 `undefined` 语义**：原 spread `{...defaults, ...(cfg?.configValues ?? {})}` 中，若 configValues 显式带 `{ x: undefined }`，spread 会把 `x` 设为 undefined；deepMerge 会跳过 undefined（保留 defaults.x）。**这是语义变化**，但显式写 undefined 是反模式，无现实 case 受影响。UT 中加一条覆盖此契约。
3. **import 依赖反向**：plugin-manager.ts 当前不依赖 llm 模块；改后 plugin → llm 单向依赖。llm 模块不反向依赖 plugin（grep 确认 llm 不 import plugin），**无环**。
4. **位置 inversion**：deepMerge 宿主在 llm 子模块下、被 plugin 模块消费，语义上倒置。短期容忍，长期建议搬到 `app/server/src/utils/deep-merge.ts`（**本版不做**，超 scope）。
5. **bug-A（inventory JOIN manifest default）独立修**：BUG-PLUGIN-004 修的是**实例化注入值**（运行时 impl 拿到的 cfg）；bug-A（§1 of current-state report）修的是**inventory 返回前端的 `config` 字段**（UI 展示）。**两者正交**，可分别改：BUG-PLUGIN-004 在 plugin-manager.ts:155-165；bug-A 在 inventory-builder.ts:214-217。**合并改时勿串**。
6. **D7 删 schemaConfig 不在 instantiate 涉及**：instantiate 本就不读 schemaConfig（§1）。D7 改动跨 manifest.ts / inventory-builder.ts / 前端 modal，本任务只关注 instantiate 的 deepMerge 这一行——**不要在 instantiate 里加 schemaConfig 删除逻辑**（那是 inventory + manifest 的事）。

### 「manifest.config 这层该不该加？」

**不加**。理由：
- §3 已证 0 使用（3 个 builtin plugin.json 全无顶层 `config`）
- spec §3.5 留 plugin 级 configSchema/config 是**预留通道**，不是当前需求
- YAGNI：为不存在的需求加抽象 = 增维护面 + 加测试面
- 修复后 instantiate 内部用 `deepMerge` 链式调用，未来要加 plugin 级 config 时只需在链首插一层：`deepMerge(extractDefaults(plugin.configSchema), plugin.config ?? {}, defaults, cfg?.configValues ?? {})`，**形状已留好**

**spec 同步**：保留 `PluginManifest.configSchema?` / `config?` 字段定义不动（`manifest.ts:23-25`）；spec §3.5 保留「plugin 级 + impl 级两层并存」描述（未来扩展点）。仅 §3.5 末尾的实现偏差注（`:148`）修复后删除。
