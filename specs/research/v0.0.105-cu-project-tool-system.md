## 1. 工具定义契约

### 1.1 三层契约（spec：`specs/tech/agent/tools/[P0]tool_execution_engine.md §2`；code：`app/server/src/tools/types.ts:188-214`）

| 概念 | 职责 | 形态 |
|---|---|---|
| `ToolDefinition` | 给 LLM 的声明（assemble 进 `snapshot.tools`） | `{name, description, inputSchema: JSONSchemaLike}` |
| `Tool` | 引擎执行的实际对象（`config.tools` 持有） | `definition` + 可选 `interaction`/`onReply` + `run` |
| `ToolRunResult` | run 返回值 | `{content: ContentBlock[], isError: boolean}` |
| `ToolCtx` | 引擎构造传给 tool.run 的上下文 | `{config, signal?, workdir, readSet?}` |

### 1.2 Tool 接口（`app/server/src/tools/types.ts:188-214`，三类形态）

```typescript
export interface Tool {
  definition: ToolDefinition;
  /** [v0.0.101] HITL 悬挂判定：返非 null → 引擎不调 run，转 pending 占位 */
  interaction?(input: ToolInput, ctx: ToolCtx): ToolInteraction | null;
  /** [v0.0.101] 仅 handleType='callback' 用：回填进 inbox 后 pre-process 调它返 result */
  onReply?(payload: unknown, ctx: ToolCtx): Promise<ToolRunResult>;
  /** 执行（串行，引擎 await） */
  run(input: ToolInput, ctx: ToolCtx): Promise<ToolRunResult>;
}
```

三种形态：① 普通 tool（只实现 run）；② 悬挂型 direct_result（interaction 恒非 null + 不实现 run）；③ callback tool（interaction + onReply）。

### 1.3 最小样例（摘自 `app/server/src/tools/bash.ts:46-122`）

```typescript
export const bashTool: Tool = {
  definition: {
    name: 'bash',
    description: 'Execute a shell command. Persistent cwd per session ...',
    inputSchema: {
      type: 'object',
      required: ['command', 'description'],
      properties: {
        command: { type: 'string', description: 'Shell command (pipes/&& allowed)' },
        description: { type: 'string', description: 'Human-readable description (5-10 words)' },
        timeout: { type: 'integer', description: 'Timeout ms (default 120000, max 600000)' },
      },
    },
  },
  async run(input: ToolInput, ctx: ToolCtx): Promise<ToolRunResult> {
    const command = String(input.command ?? '');
    if (!command) return errorResult(`[${ToolErrorCode.INVALID_INPUT}] command is required`);
    // ... 用 node:child_process spawn 执行（见 §7）
    return textResult(output);   // 或 errorResult(msg)
  },
};
```

辅助函数（`types.ts:260-270`）：`errorResult(message)` / `textResult(text)` — 单 TextBlock 结果的快捷构造。

### 1.4 inputSchema（`types.ts:35-44`）

`JSONSchemaLike` = JSON Schema 子集宽松形态（`type/properties/required/description` + 索引签名），**不引 ajv**，引擎做轻量校验（必填 + primitive 类型）。Computer use 的 action/coordinate 参数用此 schema 即可。

## 3. 执行引擎（调度/超时/权限/结果回灌）

### 3.1 串行 + 失败不中断（`app/server/src/tools/engine.ts:85-156`）

```typescript
async execute(config, toolCalls, allowedTools?, opts?): Promise<ExecuteResult> {
  // ...
  for (const call of toolCalls) {                    // 串行 for...of + await
    if (allowedSet && !allowedSet.has(call.name)) { results.push(rejectToolCall(call, 'not in whitelist')); continue; }
    const tool = this.resolveTool(config.tools, call.name);
    if (!tool) { results.push(rejectToolCall(call, 'not registered')); continue; }
    const validateErr = validateInput(tool.definition.inputSchema, call.arguments);
    if (validateErr) { results.push(this.wrap(call, errorResult(...))); continue; }
    // interaction HITL 分流（v0.0.101）
    if (tool.interaction) { ... buildPendingResult ... }
    // 普通 tool：调 run，失败不中断
    results.push(await this.runTool(call, tool, ctx));
  }
  return { results, pending };
}
```

**关键不变量**（`[P0]tool_execution_engine.md §4`）：
- 串行 `for...of + await`，**不并发**（避免文件竞争/资源冲突/顺序依赖）
- `results[i]` 对应 `toolCalls[i]` 顺序保证
- 失败不中断：单个 isError 继续下一个
- `sharedReadSet`（`config._readSet`）跨 execute 跟踪 read→write 链

### 3.2 超时/取消（`[P0]tool_execution_engine.md §4` + `bash.ts:131-207`）

引擎层**不主动超时**，通过 `ctx.signal: AbortSignal` 传入 `tool.run`，**工具自行响应**：
- bash.ts:156-171 自管 timer：到时 SIGTERM → 500ms 优雅期 → SIGKILL
- 引擎层可加 overall timeout 兜底（当前未加）

Computer use 工具若做长操作（如等动画），须自管 timeout + 响应 `ctx.signal`。

### 3.3 权限/白名单（`[P0]tool_policy.md`，三层一致）

- **config 层**（`session-config.ts`）：`resolveTools({kind, mainAllowedTools})` → `config.tools`
- **schema 层**（`agent-loop-call-main.ts`）：RunSpec.toolDefinitions 给 LLM（决定 LLM 看得到哪些工具）
- **exec 层**（`build-deps.ts`）：RunSpec.allowedTools 给 engine.execute（决定能执行哪些）

三层查同一份 `TOOL_POLICY`，bound=角色上限。拒绝统一走 `[tool_not_allowed]` code（`[P0]tool_execution_engine.md §3.1`）。

### 3.4 结果回灌 LLM

```
tool.run → ToolRunResult {content: ContentBlock[], isError}
  → engine.wrap → ToolResultBlock {toolCallId, content, isError, status?}
  → agent loop ③ ingest 进 transcript（tool role message）
  → context engine assemble → snapshot.messages
  → llm caller encode（protocol-encode.ts）→ anthropic wire tool_result block
  → 下一轮 LLM 看到
```

**关键卡点（computer use 视角）**：`content: ContentBlock[]` —— 当前 ContentBlock 不含 ImageBlock（见 §6）。截图要回灌 LLM 必须先打通 image block 全链路。

## 4. browser / connector 现状 + computer use 可复用机制（重点）

### 4.1 驱动模型差异（**computer use 与 browser 是两条不同路线**）

| 维度 | browser tool（现状） | computer use（待建） |
|---|---|---|
| 控制对象 | 浏览器（CDP 协议） | 本机 OS（鼠标/键盘/屏幕） |
| **驱动模型** | **a11y tree + element ref**（`browser_tool.md §6`） | **截图 + 坐标**（screenshot + coordinate） |
| 主交互通道 | `snapshot()` 返 `{snapshot, refs}` → click(ref)/type(ref) | screenshot → LLM 看图决策 → click(x,y)/type(text) |
| 截图作用 | **辅助**（vision 校验、给 LLM 看长相，非主通道） | **唯一主通道**（无截图无法决策） |
| spec 决策 | `[P1]browser_tool.md §6/§8`：**「截图+坐标（computer-use 路线）：本版本不支持（P2 再说），主用 a11y+ref」** | 本版本（v0.0.105）要做 |

**结论**：computer use 不是 browser tool 的扩展 mode，而是**平行的另一类工具**。browser tool 的 a11y ref 模型不复用；但底层工程模式（多 driver 抽象、lazy connect、owner lock、node worker 绕 Bun bug）高度可复用。

### 4.2 可复用的工程模式（4 项）

#### 4.2.1 `BrowserDriver` / `BrowserSession` 协议抽象（`[P1]browser_tool.md §2`，code `browser/types.ts`）

```typescript
interface BrowserDriver {
  readonly mode: 'headless' | 'managed-profile' | 'attach';
  connect(opts, signal?): Promise<BrowserSession>;
  executeOnce?(opts, action, params, signal?): Promise<{ok, text?, error?}>;
}
interface BrowserSession {
  listPages/selectPage/navigate/snapshot/click/type/evaluate/screenshot/close
}
```

**借鉴点**：多底层栈（Playwright/CDP vs chrome-devtools-mcp MCP）封装在 driver 内，上层只见统一协议。Computer use 同样面临多平台（macOS Quartz CGWindowListFindWindows vs Linux X11 vs Windows Win32）—— 抽象 `ComputerDriver` + `ComputerSession` 协议，各平台实现。

#### 4.2.2 `ConnectorManager` lazy-connect + owner-lock（v0.0.46 connector_opt）

`app/server/src/tools/browser/connector-manager.ts:60-100` + `connector-types.ts`：

| 机制 | browser attach | computer use 可复用方式 |
|---|---|---|
| **switch（feature flag）** | `switch=on/off`，仅表 intent，与 connect 解耦 | 同样需要：用户可在配置开关「允许 agent 控制本机」 |
| **lazy connect（`connectForToolRun`）** | LLM 首次调 `browser({mode:'attach'})` 才真连，不由 bootstrap 触发 | computer use 同：首次调 `computer({action:screenshot})` 才接管鼠标 |
| **owner 锁（sessionId 粒度全局唯一）** | `owner={sessionId, connectedAt}`，两 session 不能同控一浏览器 | **computer use 更刚需**：一台机器一套鼠标键盘，**必须** owner 锁防两 agent 抢鼠标 |
| **门禁分层错误** | `not_enabled` / `in_use_by_other` / `connect_failed` | 直接套用三态错误模型 |
| **disconnect action（LLM 主动释放）** | `browser({action:'disconnect'})` 幂等 | computer use 也应有：LLM 完成任务后主动释放 |
| **session 结束按 sessionKey 清理** | session 结束关 agent 开的 tab（attach 不杀浏览器） | session 结束应释放 owner 锁 + 可能恢复鼠标位置 |

**直接复用 ConnectorManager 模式**：computer use 应建一个 `ComputerConnectorManager`（或扩展现有 `ConnectorManager` 加 `'computer'` id）。

#### 4.2.3 NodeWorkerDriver 子进程绕 Bun bug（`[P1]browser_tool.md §3`，code `node-worker-driver.ts` + `worker-entry.ts`）

为绕 Bun 下 `playwright.connectOverCDP()` 永久 hang（oven-sh/bun#9357），browser mode①② 把 Playwright 操作整体改走 node 子进程一次性执行器：

```
bun 主进程 → spawn `node browser-worker.cjs`
  → stdin 任务 JSON / stdout 结果单行 JSON / stderr 诊断
  → worker 内 launch chrome + connectOverCDP + dispatch + cleanup
```

**借鉴点**：若 computer use 需要调原生 API（如 macOS CGWindowListSearch、CoreGraphics）而 Bun runtime 有兼容问题，可复用此「node worker + 三流分离 JSON 协议」模式。三流分离（stdin 任务/stdout 结果/stderr 诊断）是经过 BUG-001 验证的健壮设计。

#### 4.2.4 macOS 系统调用先例（chrome-discover.ts + platform/）

- `app/server/src/tools/browser/chrome-discover.ts:109-130`：macOS 默认浏览器探测
  - 读 `~/Library/Preferences/com.apple.LaunchServices/com.apple.launchservices.secure.plist`
  - `osascript -e 'tell application "Finder" to application file id "<bundleId>" as text'`
- `app/server/src/platform/workspace-dialog.ts:59-80`：osascript choose folder（原生目录选择 dialog）
- `app/server/src/platform/workspace-open.ts`：跨平台打开文件

**借鉴点**：项目已有 `app/server/src/platform/` 目录放跨平台 OS 工具，**computer use 的 OS 抽象层应放这里**（如 `platform/screenshot.ts`、`platform/input.ts`），而非塞进 `tools/`。osascript / screencapture CLI 调用有现成范式（spawnSync + 超时 + 错误归类）。

### 4.3 ChromeMcpDriver 的 MCP stdio 协议封装（`chrome-mcp-driver.ts` + `mcp-factory.ts`）

spawn `chrome-devtools-mcp` 作 stdio MCP server，`StdioClientTransport` 连 handshake → listTools 校验 → callTool 调用。**computer use 不走 MCP**（Anthropic computer use 是工具协议，不是 MCP server），此模式不复用。

## 5. 截图 / 图像 / 视觉基建现状

### 5.1 产品侧 — 基本为零

| 能力 | 现状 | 备注 |
|---|---|---|

## 6. LLM 消息是否支持图像 content block（computer use 关键依赖）

### 6.1 两套 ContentBlock 类型 — 形状分叉（**关键发现**）

| 层 | 文件 | 含 ImageBlock？ |
|---|---|---|
| **业务/落库层** | `app/server/src/message/types.ts:174-180` | **否** — 仅 text/tool_call/tool_result/reasoning/usage/tool_reply 6 类 |
| **LLM 协议层** | `app/server/src/llm/protocol-types.ts:17-38` | **是** — `{type:'image', source:{type, media_type, data}}` |
| spec（权威） | `specs/tech/agent/message/[P0]agent_message_interface.md §4.2` | **是** — 定义了 ImageBlock |

`message/types.ts:172` 注释：**「ImageBlock/AudioBlock/VideoBlock/FileBlock/ApprovalResultBlock 标 future 不实现」**。

### 6.2 协议层 encode 已就绪

`app/server/src/llm/protocol-encode.ts:251-256`：
```typescript
function encodeContentBlock(b: ContentBlock): Record<string, unknown> {
  switch (b.type) {
    case 'text': return { type: 'text', text: b.text };
    case 'image': return { type: 'image', source: b.source };   // ✅ 已就绪
    ...
  }
}
```
有 UT 覆盖（`llm/__tests__/protocol-encode.test.ts:103-130`）。

### 6.3 GAP — 要打通的 5 个点（computer use 接入必做）

1. **`message/types.ts:174-180 ContentBlock` 加 ImageBlock**（按 spec §4.2 形态 `{type:'image', source: ImageSource, mediaType}`，`ImageSource = {kind:'url',url} | {kind:'base64',data}`）
2. **两套 image 形态对齐**：spec/message 用 `{kind:'base64', data}` + 顶层 `mediaType`；协议层用 `{type, media_type, data}` 嵌在 source 内 —— 需在 encode/translate 处适配（protocol-encode.ts 已对协议层 shape 做 encode，但 message→protocol 翻译处需确认 image block 不被丢）
3. **ToolResultBlock.content 承载 image**：`message/types.ts:97 content: ContentBlock[]` —— ContentBlock 加了 image 后天然支持，但须验证 CrudStore 序列化 base64 不爆（PNG 截图常 1-2MB base64 字符串，JSON-able 但需考虑 DB 行大小）
4. **context engine assemble 不过滤 image**：grep 确认 context engine 无 normalizeContentBlock drop image（当前调研未见 drop 逻辑，但须在实现时跑 typecheck + UT 验证）
5. **前端渲染 image（可观测性）**：tool result 含截图时 chat UI 要能展示（否则用户看不见 agent 看到了什么）—— 这是 UI 工作量，非阻塞 computer use 工具本身

**建议**：本版本至少做 1-4（后端链路），5（前端）可延后或最小化（显示「[screenshot]」占位 + click 展开）。

### 6.4 protocol-types ImageBlock shape（wire 形态）

```typescript
// app/server/src/llm/protocol-types.ts:22-25
{
  type: 'image';
  source: { type: string; media_type: string; data: string };  // base64
}
```
Anthropic computer use 返回的 `tool_result.content[].type='image'` 与此兼容（`source.type='base64'`）。Computer use 工具产截图 → 包成此 shape → encode → wire，链路通。

## 7. OS/进程交互基建（Bun/macOS 先例）

### 7.1 Bun runtime + node:child_process（`bash.ts:19`）

```typescript
import { spawn } from 'node:child_process';
// bash.ts:138
const child = spawn(command, {
  shell: process.env.SHELL ?? '/bin/sh',
  cwd,
  stdio: ['ignore', 'pipe', 'pipe'],
});
```

bash 工具用 `node:child_process.spawn`（Bun 兼容），per-session 持久 cwd，超时 SIGTERM→SIGKILL，输出 64KB 截断。**Computer use 的 OS 调用（screencapture/cliclick/osascript）同样走此模式**。

### 7.2 macOS 特定代码先例（3 处）

### 7.3 `platform/` 目录是 OS 抽象正确归属

### 7.4 已知坑（memory 提醒）

- **memory `test-no-real-spawn-system-gui`**：测试禁真实 spawn 系统命令（open/osascript 致 IDE 弹窗）。Computer use 测试须用 deps/spawnFn 注入 mock，**不能真跑 screencapture**（会截 IDE）。

### 8.3 5 条最关键结论（给 orchestrator 决策用）

1. **LLM 消息能带图像 — 但当前业务层 ContentBlock 联合不含 ImageBlock（GAP）**。协议层（protocol-types.ts:22 + protocol-encode.ts:255）已完全就绪，spec §4.2 也定义了；但 `message/types.ts:174` ContentBlock 把 ImageBlock 标 future 删了。**这是 computer use 接入的最大前置工作量**：打通 image block 的 message→persist→assemble→encode 全链路（4 个点，见 §6.3）。

2. **browser tool 是 a11y ref 路线，computer use 是 screenshot+coord 路线 — 驱动模型不复用**。browser spec `[P1]browser_tool.md §6/§8` 明确「截图+坐标路线本版本不支持，P2 再说」—— v0.0.105 就是那个 P2，但应作为**平行新工具**而非 browser 的扩展 mode。

3. **browser tool 的工程模式高度可复用 — 尤其 ConnectorManager**。owner 锁（sessionId 粒度全局唯一）对 computer use **比 browser 更刚需**（一台机器一套鼠标键盘，两 agent 不能同控）。lazy connect + switch flag + 门禁三态错误（`not_enabled`/`in_use_by_other`/`connect_failed`）+ disconnect action 模式直接搬。

4. **OS 能力从零建，但有清晰的范式可循**。产品侧零截图/零图像处理能力，但 `app/server/src/platform/` 已有 osascript/spawnSync 跨平台范式（workspace-dialog.ts）。Computer use 的 OS 抽象层应放 `platform/screenshot.ts` + `platform/input.ts`，复用 spawnSync + 超时 + 错误归类模式；工具层只做 Tool 协议适配。

5. **测试侧有硬约束 — 不能真 spawn 系统命令**。memory `test-no-real-spawn-system-gui` 明定：测试禁真实 spawn（screencapture 会截 IDE、osascript 会弹 dialog）。Computer use 的 UT/AT 必须用 deps/spawnFn 注入 mock；E2E 几乎不可行（真 OS 不可控），应考虑 mock LLM 返固定坐标 + 断言下游 tool 调用序列。
