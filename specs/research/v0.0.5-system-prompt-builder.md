## 1. 三竞品各自的 system builder 逻辑

### 1.1 Claude Code — 动态 section 列表 + cache 语义（最接近 map-reduce）

**构建方式**：动态。`getSystemPrompt()` 返回 `string[]`（片段数组），由调用方 `asSystemPrompt([...])` 包装成 `SystemPrompt` branded type（`src/utils/systemPromptType.ts:8-14`）。

**片段来源**（`src/constants/prompts.ts:444-577`）：
- 静态段（cacheable）：`getSimpleIntroSection` / `getSimpleSystemSection` / `getSimpleDoingTasksSection` / `getActionsSection` / `getUsingYourToolsSection` / `getSimpleToneAndStyleSection` / `getOutputEfficiencySection`
- 动态段（通过 `systemPromptSection(name, compute)` 注册）：`session_guidance` / `memory` / `ant_model_override` / `env_info_simple` / `language` / `output_style` / `mcp_instructions` / `scratchpad` / `frc` / `summarize_tool_results`，外加 feature flag 条件段（`numeric_length_anchors` / `token_budget` / `brief`）

**合并机制**（`src/constants/prompts.ts:560-576`）：
```typescript
return [
  // --- Static content (cacheable) ---
  getSimpleIntroSection(outputStyleConfig),
  getSimpleSystemSection(),
  ... shouldUseGlobalCacheScope() ? [SYSTEM_PROMPT_DYNAMIC_BOUNDARY] : [],
  // --- Dynamic content (registry-managed) ---
  ...resolvedDynamicSections,
].filter(s => s !== null)
```
顺序写死在数组里，靠 `.filter(s => s !== null)` 去空段。**没有显式 reducer、没有 token 裁剪**（依赖 LLM context window + prompt cache）。

**可扩展性**：通过 `systemPromptSection(name, compute)` 工厂函数注册新段，**无插件机制**——是源码内静态注册（`src/constants/systemPromptSections.ts:20-25`）。

**cache 语义**（关键设计，`src/constants/systemPromptSections.ts:20-58`）：
- `systemPromptSection(name, compute)`：memoized，会话内计算一次，`/clear` / `/compact` 才清缓存
- `DANGEROUS_uncachedSystemPromptSection(name, compute, reason)`：每 turn 重算，**会 break prompt cache**，必须给 reason
- `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`（`src/constants/prompts.ts:114-115`）：cache 边界标记，之前是全局 cache 前缀，之后是动态段

**token 预算/裁剪**：无显式裁剪。仅在 `feature('TOKEN_BUDGET')` 下追加一段指令告诉模型「目标 token 数」（`src/constants/prompts.ts:545-549`），不裁剪 system prompt 本身。

### 1.2 OpenClaw — 单一模板函数 + 事件整串替换（最简陋）

**构建方式**：基本固定模板。`buildSystemPrompt(options)`（`src/agents/sessions/system-prompt.ts:28-179`）一个大函数，模板字符串拼接：

```typescript
let prompt = `You are an expert coding assistant...
Available tools:
${toolsList}
Guidelines:
${guidelines}
Embedded agent documentation...`;
if (appendSection) prompt += appendSection;
if (contextFiles.length > 0) { prompt += "\n\n<project_context>..."; }
if (hasRead && skills.length > 0) { prompt += formatSkillsForPrompt(skills); }
prompt += `\nCurrent date: ${date}`;
prompt += `\nCurrent working directory: ${promptCwd}`;
```

**片段来源**（全在函数体内，硬编码）：
- tools list（`toolSnippets`）
- guidelines（基于 `selectedTools` 派生 + `promptGuidelines` 参数 + 固定两条）
- docs 路径、`appendSystemPrompt`、`contextFiles`、`skills`
- `customPrompt` 模式下完全替换默认模板（`system-prompt.ts:53-81`）

**合并机制**：纯字符串拼接，无片段抽象、无排序、无去重。

**可扩展性**：两条出路：
1. **provider plugin 的 prompt overlay**（`src/plugins/provider-runtime.ts:215-239` + `src/agents/gpt5-prompt-overlay.ts`）：`resolveProviderSystemPromptContribution` 返回 `ProviderSystemPromptContribution`，内部 `mergeProviderSystemPromptContributions(base, override)` 合并（`provider-runtime.ts:241-249`）。这是**整段替换/追加**，不是片段叠加，且只针对特定 provider/model（如 GPT-5）。
2. **extension 的 `before_agent_start` 事件**（`src/agents/sessions/extensions/runner.ts:982-1045` + `types.ts:702-712`）：事件 payload 含 `systemPrompt: string`（已组装好的整串）+ `systemPromptOptions`，handler 返回 `{ systemPrompt?: string }`，runner 用 `currentSystemPrompt = result.systemPrompt` 整串覆盖（`runner.ts:1022-1025`），用 `systemPromptModified` flag 标记（`runner.ts:998, 1024, 1043`）。

**关键限制**：扩展点只能拿到**最终 string**做整串替换，**不能贡献片段、不能局部插入、不能控制顺序**。多个扩展之间是顺序覆盖（后者赢），无优先级仲裁。

**token 预算/裁剪**：无。

### 1.3 Hermes Agent — 三 tier 分层 + per-tier cache 语义（最成熟）

**构建方式**：动态。`build_system_prompt_parts(agent)` 返回 `Dict[str, str]`（`agent/system_prompt.py:113-465`），`build_system_prompt()` 再 join 成 string（`agent/system_prompt.py:468-491`）。

**三个 tier（对应 prompt cache 友好性）**（`agent/system_prompt.py:461-465`）：
```python
return {
    "stable":   "\n\n".join(p.strip() for p in stable_parts   if p and p.strip()),
    "context":  "\n\n".join(p.strip() for p in context_parts  if p and p.strip()),
    "volatile": "\n\n".join(p.strip() for p in volatile_parts if p and p.strip()),
}
```

**片段来源**（按 tier）：
- **stable**（`system_prompt.py:148-400`）：SOUL.md identity / `HERMES_AGENT_HELP_GUIDANCE` / `TASK_COMPLETION_GUIDANCE` / `PARALLEL_TOOL_CALL_GUIDANCE` / tool-aware guidance（`MEMORY_GUIDANCE` / `SESSION_SEARCH_GUIDANCE` / `SKILLS_GUIDANCE` / `KANBAN_GUIDANCE`）/ `STEER_CHANNEL_NOTE` / `COMPUTER_USE_GUIDANCE` / nous subscription / `TOOL_USE_ENFORCEMENT_GUIDANCE` + per-model operational guidance（Google/OpenAI）/ skills prompt / Alibaba model workaround / env hints / coding posture / env probe / active profile / platform hints
- **context**（`system_prompt.py:403-419`）：caller `system_message` + `build_context_files_prompt`（AGENTS.md / .cursorrules 等）
- **volatile**（`system_prompt.py:422-459`）：memory snapshot / USER.md profile / external memory provider block / timestamp + session_id + model + provider line

**合并机制**（`system_prompt.py:483-484`）：
```python
parts = build_system_prompt_parts(agent, system_message=system_message)
joined = "\n\n".join(p for p in (parts["stable"], parts["context"], parts["volatile"]) if p)
```
每个 tier 内部 `\n\n` join，tier 之间再 `\n\n` join。**顺序固定（stable → context → volatile），无 reducer 抽象、无去重**（靠 `if p and p.strip()` 过滤空段）。

**可扩展性**：无插件机制。tool guidance 靠 `if name in agent.valid_tool_names` 条件分支（`system_prompt.py:188-217`）；per-model guidance 靠 `if "gemini" in model_lower` 分支（`system_prompt.py:245-256`）；platform hints 靠 `_resolve_platform_hint`（`system_prompt.py:64-110`）支持 config 层 `replace` / `append`。所有扩展点都是源码内 if 分支或 config 字段，**无统一的片段注册机制**。

**token 预算/裁剪**（`agent/prompt_builder.py:999-1047`）：仅 context_files 有动态 cap：
```python
CONTEXT_FILE_MAX_CHARS = 20_000  # 历史地板
_CONTEXT_FILE_CHARS_PER_TOKEN = 4
_CONTEXT_FILE_WINDOW_FRACTION = 0.06  # 占 context window 6%
_CONTEXT_FILE_DYNAMIC_CEILING = 500_000

def _dynamic_context_file_max_chars(context_length):
    budget = int(context_length * 4 * 0.06)
    return max(20_000, min(budget, 500_000))
```
解析顺序：config `context_file_max_chars` > 动态 cap（按 model context_length）> 20K 默认（`prompt_builder.py:1029-1047`）。截断按 head 0.7 / tail 0.2 比例（`prompt_builder.py:1000-1001`）。截断警告通过 ContextVar 收集后由 `drain_truncation_warnings()` 上报（`prompt_builder.py:1049-1070`、`system_prompt.py:488-489`）。

**diagnostic 工具**（`hermes_cli/prompt_size.py`）：`hermes prompt-size` 命令，离线构建一个 inspection agent，输出 system prompt / skills index / memory / user profile / tool schemas 的 byte/char breakdown（`prompt_size.py:52-109, 116-138`）。不裁剪，仅观测。

**cache 策略**（`agent/system_prompt.py:1-22, 468-491`）：system prompt 整串缓存于 `agent._cached_system_prompt`，会话内不重建，**只在 context compression 后 invalidate**（`invalidate_system_prompt`，`system_prompt.py:494-502`）。timestamp 用日期精度（非分钟）以保 byte-stable（`system_prompt.py:446-452`）。

## 2. 综合比较表

| 维度 | Claude Code | OpenClaw | Hermes Agent |
|------|-------------|----------|--------------|
| **构建方式** | 动态：静态段 + 动态 section 列表 | 基本固定：单一大模板函数 | 动态：三 tier 分层 |
| **片段抽象** | `string[]` 数组 + `systemPromptSection(name, compute)` 工厂 | 无（裸字符串拼接） | `Dict[str, str]`（stable/context/volatile） |
| **片段来源** | 身份/规则/工具说明/输出风格/MCP/memory/env/language/feature flag 段 | tools/guidelines/docs/contextFiles/skills | identity/tool guidance/skills/env/coding/memory/profile/timestamp（约 20+ 类） |
| **合并机制** | 数组拼接 + `.filter(s => s !== null)`（`prompts.ts:560-576`） | 模板字符串 `+=`（`system-prompt.ts:28-179`） | per-tier `"\n\n".join` → tier 间 `"\n\n".join`（`system_prompt.py:461-484`） |
| **排序** | 写死在数组字面量里 | 写死在函数体里 | tier 内 `stable_parts.append` 顺序固定，tier 顺序固定 |
| **去重** | 无（靠 filter null） | 无 | 无（靠 `if p and p.strip()`） |
| **可扩展性** | 源码内 `systemPromptSection()` 注册，无插件 | 两条出路：① provider plugin `resolveSystemPromptContribution` 整段合并 ② extension `before_agent_start` 事件**整串替换** | 无统一机制：if 分支 + config 字段（`platform_hints` replace/append） |
| **cache 友好** | 强：section 分 memoized / DANGEROUS_uncached，有 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 标记边界 | 弱：无 cache 概念 | 中：tier 分层对应 cache 稳定性，timestamp 用日期精度，会话内整串缓存 |
| **token 裁剪** | 无 | 无 | 仅 context_files 动态 cap（按 model context_length 6%，20K-500K） |
| **观测工具** | 无（有 cache break detection） | 无 | `hermes prompt-size` 命令输出 byte breakdown |

### 共同点
1. **顺序写死在代码里**，都不依赖外部 priority/order 配置
2. **无显式 token 裁剪**（Hermes 仅对 context_files 裁，不对 system prompt 整体裁）
3. **去重都靠 filter null/empty**，无内容级去重

### 差异点 / 优劣
- **Claude Code** 最接近 map-reduce：section 工厂 + cache 语义明确，但仍是源码内静态注册，扩展靠改源码
- **OpenClaw** 最简陋：模板字符串 + 整串替换事件，扩展只能做粗粒度整串覆盖，无法片段叠加
- **Hermes** tier 分层最清晰（直接对应 cache 稳定性），有 token budget 概念（但仅 context_files），有观测工具

## 3. Propose 方案

基于三竞品调研 + 我们的 mapper/reducer 基线，给出**保留 / 调整 / 砍掉**清单。设计原则：扩展点架构（`group=context`、ordered ext impl）保持不变，让竞品的成熟设计反哺 mapper/reducer 的契约细节。

### 3.1 保留（基线正确，竞品验证）

| 项 | 理由 |
|----|------|
| **mapper / reducer 双 ordered 扩展点** | 三竞品都隐含 map（片段产生）+ reduce（合并）两阶段，但都硬编码在单函数里。我们的双扩展点是**比竞品更优的抽象**——竞品扩展只能整串替换（OpenClaw）或源码内注册（Claude Code / Hermes），我们能做到插件级片段叠加 |
| **ordered cardinality（priority 排序）** | 竞品顺序全写死在代码里，我们要支持插件扩展就必须可排序。`priority` 单一原语（`specs/tech/plugin_system/[P0]extension_point_interface.md:65-68`）正确 |
| **`group: "context"`** | 与 `context_ingest_handler` 同分区，符合现有分区设计 |

### 3.2 调整（用竞品经验细化基线占位项）

基线 `[P0]system_prompt.md §4` 列了 4 个「后续完善」占位，调研给出明确答案：

#### 调整 1：`PromptFragment` 形状 — 引入 tier 字段（借鉴 Hermes）

```typescript
type PromptTier = "stable" | "context" | "volatile";

interface PromptFragment {
  id: string;            // 唯一标识，reducer 用于去重
  tier: PromptTier;      // 决定 cache 稳定性 + reducer 默认排序
  priority: number;      // tier 内排序（与 ext impl priority 解耦，允许 mapper 产多片段不同优先级）
  content: string;       // 片段正文
}
```

**理由**：Hermes 的三 tier 分层直接对应 prompt cache 稳定性（stable 最稳，volatile 每变都破缓存），是三竞品里最成熟的设计。我们的 reducer 默认行为应按 tier 分组聚合 → tier 间固定顺序（stable → context → volatile）→ tier 内按 priority。mapper 只声明 tier，reducer 负责按 tier 分桶。

#### 调整 2：mapper 契约 — 返回 `PromptFragment[]`（允许单 mapper 产多片段）

```typescript
interface SystemPromptMapper {
  /** 贡献 0-N 个片段；返回空数组表示本 turn 不贡献 */
  map(ctx: PromptCtx): PromptFragment[] | Promise<PromptFragment[]>;
}
```

**理由**：Claude Code 单个 `getSystemPrompt()` 产 10+ 段，Hermes 单 `build_system_prompt_parts` 产 20+ 段。一个 mapper 产多片段（如「tool guidance mapper」一次产出 memory/session/skills 三段）是合理需求，不应强制 1:1。

#### 调整 3：reducer 契约 — 末个产 string，前面的可返回 fragments

基线设计正确（`reduce(...) => PromptFragment[] | string`），补充**默认内置 reducer**：

```typescript
interface SystemPromptReducer {
  reduce(fragments: PromptFragment[], ctx: PromptCtx): PromptFragment[] | string;
}

// 内置 reducer 1：tier 分桶 + tier 内 priority 排序（默认行为）
// 内置 reducer 2：按 fragment.id 去重（同 id 后者覆盖前者，或丢弃——见下文「坑」）
// 内置 reducer 3（末个）："\n\n".join 转 string
```

**理由**：OpenClaw 的 `mergeProviderSystemPromptContributions`（`provider-runtime.ts:241-249`）证明合并逻辑需要明确语义（base + override）。我们默认 reducer 应内置 Hermes 的 tier 分桶 + `\n\n` join，避免每个项目都重写。

#### 调整 4：触发时机 — 会话内构建一次，context compression 后重建

**理由**：三竞品一致——Claude Code 会话内 memoized（`/clear` `/compact` 清缓存，`systemPromptSections.ts:42-58`），Hermes 整串缓存于 `_cached_system_prompt` 仅 compression 后 invalidate（`system_prompt.py:468-502`）。我们应同样：**session 创建 / compression 后构建一次，缓存到 snapshot.system**（与 `context_engine.md` 的 snapshot 语义一致）。

#### 调整 5：token 预算 — 仅对动态来源（context_files / memory）裁剪，不裁身份/规则段

**理由**：竞品共识——**不对 system prompt 整体裁**（身份/规则是固定开销，裁了破坏行为）。Hermes 只对 context_files 动态 cap（按 model context_length × 4 chars/token × 6%，20K-500K，`prompt_builder.py:999-1047`）。我们应在 reducer 内提供「token budget per tier」钩子：
- `stable` / `context` 规则段：不裁
- `context` 文件段（如 AGENTS.md 等价物）+ `volatile` 记忆段：按 model context_length 动态 cap

具体阈值复用 Hermes 经验值（6% window fraction、20K floor、500K ceiling）作为默认，可在 reducer 配置里覆盖。

### 3.3 砍掉（基线过度设计或竞品证明无价值）

无。基线 `[P0]system_prompt.md` 的设计都被竞品验证为合理方向，且比竞品更灵活。需要砍的是**过度复杂化倾向**：

- ❌ **不要**引入「内容级去重」（如片段文本相似度去重）——三竞品都只 filter null/empty，内容去重会破坏可预测性，且 mapper 不应产出重复片段
- ❌ **不要**引入「reducer 链 N>2」的复杂中间变换——默认 reducer 三件套（分桶/去重 by id/join）已足够，超过就是过度设计
- ❌ **不要**让 mapper 能修改其他 mapper 的片段（无 cross-mapper 依赖）——OpenClaw 整串替换的混乱根源就是扩展可覆盖彼此，我们保持 mapper 之间**只贡献、不修改**

### 3.4 落地映射（直接对接扩展点架构）

```typescript
// specs/tech/plugin_system 下的扩展点定义
const SystemPromptMapperPoint = {
  id: "system_prompt_mapper",
  group: "context",
  cardinality: "ordered",   // ext impl 按 priority 串联
};

const SystemPromptReducerPoint = {
  id: "system_prompt_reducer",
  group: "context",
  cardinality: "ordered",
};

// 内置 ext impl（随 core 发布，priority 给保守值让插件可覆盖）
// mapper 侧：
//   - identity_mapper (priority 1000, tier=stable)  → 身份段
//   - tool_guidance_mapper (priority 800, tier=stable) → 工具说明
//   - rules_mapper (priority 600, tier=stable)      → 行为规则
//   - context_files_mapper (priority 500, tier=context) → AGENTS.md 等
//   - dynamic_context_mapper (priority 400, tier=context) → 动态上下文
//   - memory_mapper (priority 300, tier=volatile)  → 记忆快照
//   - timestamp_mapper (priority 100, tier=volatile) → 时间戳（日期精度，借鉴 Hermes）
// reducer 侧：
//   - tier_bucket_reducer (priority 1000)  → 按 tier 分桶 + tier 内 priority 排序
//   - dedup_reducer (priority 800)         → 按 fragment.id 去重
//   - token_budget_reducer (priority 500)  → 仅裁 context/volatile 段
//   - join_reducer (priority 100, 末个)    → "\n\n".join → string
```

### 3.5 边界与坑（从竞品踩坑提炼）

1. **timestamp 用日期精度**（Hermes `system_prompt.py:446-452`）——分钟级会每 turn 破缓存
2. **cache 边界标记**（Claude Code `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`）——如果对接的 LLM provider 支持 prompt cache，reducer 应在 stable/context 与 volatile 之间插入边界标记
3. **去重语义要明确**——同 `fragment.id` 冲突时，priority 高的赢（与 ext impl priority 语义一致），不要「累加拼接」（OpenClaw `mergeProviderSystemPromptContributions` 的 base+override 是整段替换，不是拼接）
4. **token 裁剪只裁动态段**——身份/规则段裁了会破坏 LLM 行为，只对 context_files / memory 这类动态来源裁
5. **mapper 不能 break 整个构建**——Hermes 用 `try/except` 包裹 coding_context / env_probe（`system_prompt.py:327-329, 344-346`），单个 mapper 失败应降级为「不贡献片段」而非抛异常中断整个 system prompt 构建
6. **观测工具**——参考 Hermes `hermes prompt-size`（`prompt_size.py`），提供 per-fragment / per-tier byte breakdown 命令，让用户知道固定 prompt 预算花在哪
