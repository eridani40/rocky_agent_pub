# v0.0.34 调研：chrome-devtools-mcp 1.4.0 connect vs launch 行为（attach 自启根因）

> 调研方式：直接读 `node_modules/.bun/chrome-devtools-mcp@1.4.0/build/src/{index,browser}.js` 源码
> + 实测（`reqs/v0.0.34/diag-process-tree.mjs`）。ground truth，非推测。

## 核心结论（决定性）

**chrome-devtools-mcp 的「连接 vs 自启 chrome」由启动 flag 决定，三条路泾渭分明：**

| flag | 行为 | 连不上目标时 | 是否会自启 chrome |
|------|------|------------|-----------------|
| `--wsEndpoint ws://...` | puppeteer.connect(browserWSEndpoint) | **抛错** | ❌ 绝不 launch |
| `--browserUrl http://...` | puppeteer.connect(browserURL) | **抛错** | ❌ 绝不 launch |
| `--autoConnect`（无 url，仅 channel/userDataDir） | 走 channel 分支 | **puppeteer 用 channel 自己 launch** | ✅ **会静默自启** |

### 源码证据

`build/src/index.js:75-99` —— 分叉入口：
```js
const browser = serverArgs.browserUrl || serverArgs.wsEndpoint || serverArgs.autoConnect
  ? await ensureBrowserConnected({ browserURL, wsEndpoint, channel: autoConnect ? channel : undefined, userDataDir, ... })
  : await ensureBrowserLaunched({ ... });
```

`build/src/browser.js:34-114` —— `ensureBrowserConnected` 内部三分支：
```js
if (options.wsEndpoint)      connectOptions.browserWSEndpoint = options.wsEndpoint;   // 纯 attach
else if (options.browserURL) connectOptions.browserURL = options.browserURL;          // 纯 attach
else if (channel || userDataDir) {
  if (userDataDir) { /* 读 DevToolsActivePort 文件，没有则抛 "Could not connect" */ }
  else { connectOptions.channel = (channel==='stable' ? 'chrome' : `chrome-${channel}`); }  // ← channel 分支
}
const connected = await puppeteer.connect(connectOptions);  // channel 模式连不上 → puppeteer launch 一个
```

**关键**：`autoConnect` 且**无 userDataDir** 时落到 `connectOptions.channel='chrome'`。puppeteer 的 `connect({channel})` 在找不到运行中的 chrome 时会**自己启动一个**——这就是实测看到的「不开目标 chrome，list_pages 仍返回 5 页」的来源（5 页是 autoConnect 自启的空 chrome）。

## 对 rocky 的影响（治理1 根因定位）

rocky `chrome-mcp-driver.ts buildChromeMcpArgs`：**无 cdpUrl 时默认加 `--autoConnect`**（`chrome-mcp-driver.ts` buildChromeMcpArgs：`if (input.browserUrl) {...} else { args.push('--autoConnect') }`）。

→ 用户在「连接器→浏览器」开 attach 但**没填 cdpUrl** 时，rocky 用裸 `--autoConnect` → 落 channel 分支 → **目标 chrome 没开时静默自启一个空 chrome**，破坏 attach 语义。

**修复不需要改 chrome-devtools-mcp，也不需要复杂的 connect 后校验**：attach 模式改用**不会 launch 的连接方式**即可：
- 用户填了 cdpUrl → 已走 `--browserUrl`/`--wsEndpoint`（纯 attach，本就不自启）✅ 现状正确
- 用户没填 cdpUrl → **不能用裸 `--autoConnect`**。可选：
  - (a) attach 模式**要求显式 cdpUrl**（默认 `http://127.0.0.1:9222`），永远走 `--browserUrl` 纯 attach；
  - (b) 传 `--autoConnect` 时**同时传 userDataDir** → 落 DevToolsActivePort 分支（读文件，没有则抛 "Could not connect"，**不 launch**）——但要求用户提供 userDataDir，体验差；
  - (c) 保留 autoConnect 但 connect 后**校验真连上目标**（治理1 的 pageReady 方案）——能兜底但治标。

**推荐 (a)**：attach 模式默认 `cdpUrl=http://127.0.0.1:9222`（loopback，已 SSRF 豁免），走 `--browserUrl` 纯 attach。连不上→chrome-devtools-mcp 抛 "Could not connect to Chrome. Check if Chrome is running and remote debugging is enabled..."（browser.js:108），rocky 捕获转 attach_failed 引导用户。**根治自启，无需自启校验。**

## 治理2（失败熔断）关联发现

- bootstrap 只在 **app 启动时调一次**（`bootstrap.ts:427 createAndBootstrapConnectorManager`），**无周期探测/重连循环**（connector-manager.ts 无 setInterval）。
- 「杀一个生一个」根因：**dev server 热重载 = 进程重启 = 每次重新 bootstrap → intent=on → 又 connect → autoConnect 又自启**。即治理2 的现象其实由治理1（autoConnect 自启）放大；治理1 修好后，热重载也不会再启空 chrome（连不上直接 error）。
- 治理2 本身（spec §3.3）：connect 失败 → error 态，**intent 保持 on 但不自动重连**（用户手动 toggle 或 app 重启才再试）。当前 `tryConnect` 已设 error 态，缺的是「确保 bootstrap 失败不进重试循环」——现状本就一次性，符合；治理2 主要是**确认 + 明确文档化**「失败即停」语义，外加 connect 判据真实化（避免假成功掩盖失败）。

## 决策（用户已确认）

- 治理1：**禁止自启**，attach 目标没开时明确报错引导用户 → 采用推荐方案 (a)：attach 默认走 `--browserUrl`（cdpUrl 缺省 `http://127.0.0.1:9222`），不再用裸 `--autoConnect`。
- 治理2：connect **失败即停**，intent 保持 on 但不自动重连（对齐 spec §3.3 手动重试）。

## 撤回项重申

进程树杀**不做**：实测 watchdog 随父进程死（SDK `StdioClientTransport.close` 阶梯杀够用）。详见 `reqs/v0.0.34/req.md`。
