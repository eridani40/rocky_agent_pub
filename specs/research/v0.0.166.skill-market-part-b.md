# v0.0.166 调研 Part B — 有 API 的 registry 生态（后端接口 + 市场形态参考）

> 目的：我们的 skill 源本身是 **git-backed（无中心 API、无下载量）**，但要参考「有 search/install API + 应用内市场 UX」的成熟生态，来设计我们的**后端 REST 接口**与**应用内市场页形态**。
> 方法：限时聚焦 web 调研（≤12 次工具调用）。以下结论均带关键 URL，供 PRD/架构阶段引用。

---

## 结论先行（TL;DR — 5 条核心）

1. **REST 接口有成熟范式可抄**：官方 MCP Registry = `GET /v0/servers?search=&limit=&cursor=`（游标分页 + 全文 search）+ 按 name 取详情；Smithery = `GET /servers?q=&page=&pageSize=`（语义搜索 + 布尔 filter `verified/isDeployed/remote`）。**我们的 search 接口直接对齐这套：`q` + 分页 + 若干布尔/枚举 filter**。
2. **元数据 schema 的权威模板 = MCP `server.json`**：`name`（反向域名命名空间 `io.github.owner/repo`）、`description`、`repository{url,source,subfolder}`、`version`、`packages[]`（installType/identifier/transport/args）。**我们的 skill manifest 可平移这套**（git repo + subfolder + 版本 = 天然适配 git-backed 源）。
3. **市场 UX 通用骨架 = 搜索框 + 分类 tab + 排序下拉 + 卡片列表 + 详情页**。卡片字段收敛为：图标/名称/作者/一句话描述/信号徽章（verified）/关键指标。排序维度业界标配 = 相关性 / 安装量 / 评分 / 更新时间。
4. **质量/策展分三档做法**：① 命名空间所有权验证（GitHub OAuth/OIDC/DNS/HTTP，防冒名）② verified/官方徽章（Smithery `verified`+`bySmithery`、VS Code「验证发布者」）③ 内容质量分（Glama 的 Tool Definition Quality Score + Firecracker microVM 沙箱扫恶意/prompt-injection）。
5. **git-backed 现实下的取舍**：下载量/评分这类「中心化遥测」维度**天然缺失**，硬抄会做成空字段。**能直接做的**：全文搜索、分类/tag、更新时间（git commit time）、star（读 GitHub API）、verified（所有权校验）。**要自建的**：安装量/使用量遥测（我们后端记录 install 事件）、我们自己的策展「精选/官方」标记。

## 1. 官方 MCP Registry（modelcontextprotocol/registry）

### 接口形态（可直接抄的 REST 范式）
- **List/Search**：`GET https://registry.modelcontextprotocol.io/v0/servers`
  - `search=` — 全文过滤（例 `?search=sql&limit=1`）
  - `limit=` — 每页条数
  - `cursor=` — **游标分页**（推荐，稳定）；示例里也见 `offset=` 手动分页
- **详情**：按 `name`（命名空间）定位；官方主打「list + search 参数」而非独立 by-name 端点。
- **状态**：已进入 **API freeze (v0.1)**，接口趋稳，适合作为参考基线。

### server.json schema（元数据模板 — 强烈建议平移）
| 字段 | 说明 | 对我们的映射 |
|------|------|-------------|
| `name` | 反向域名命名空间，如 `io.github.dba-i/mssql-dba` | skill 唯一 ID，用 `owner/repo` 天然去重 |
| `description` | 功能一句话 | 卡片副标题 |
| `repository{url,source,subfolder}` | 源码位置 + 子目录 | **git-backed 完美契合**：url+subfolder 直接定位 skill 源 |
| `version` | 版本 tag（如 `1.0.0`） | skill 版本（可映射 git tag） |
| `packages[]` | `registryType`/`identifier`/`transport(stdio\|sse\|streamable-http)`/`packageArguments` | 我们的「install 语义」参考：安装类型 + 标识 + 参数 |

### 质量/策展
- **命名空间所有权验证**：发布前强制校验 —— GitHub OAuth / GitHub OIDC / DNS 验证 / HTTP 验证。认领 GitHub 命名空间须账号匹配或在该用户 CI 中执行；自定义域名走 DNS/HTTP 挑战。**防冒名的黄金标准，我们的 verified 徽章可照此设计**。
- 官方定位是「元注册中心」，下游有 aggregator（Smithery/Glama 等）二次索引增强。

URL：
- https://github.com/modelcontextprotocol/registry
- https://nordicapis.com/getting-started-with-the-official-mcp-registry-api/

## 2. Smithery（smithery.ai）— 语义搜索 + 部署型市场

### 接口形态（我们 search 接口最直接的参照）
- **Search**：`GET https://api.smithery.ai/servers`
  - `q=` — **文本 + 语义匹配**（不止关键词）
  - 布尔 filter（字符串 toggle）：`verified`、`isDeployed`、`remote`
  - 结构化 filter：`namespace`、`ownerId`、GitHub repo 信息
  - **分页**：`page` + `pageSize`（上限 100）；`seed` 整数保证多次请求排序稳定
- **响应 schema 字段**：
  - `displayName` / `description`
  - `useCount` —— **连接/使用量指标**（注意：是使用量，非下载量）
  - `remote` / `isDeployed` —— 托管/部署状态
  - `score` —— 相关性分
  - `verified` + `bySmithery` —— **信任双徽章**（第三方验证 + 官方出品）
  - ⚠️ schema **没有显式 category 字段**、也无 download 计数
- **CLI**：`smithery-ai/cli` 提供 install/manage MCP servers（一键装到各 client 配置）。

### 启发
- `q + page/pageSize + seed(稳定序) + 布尔 filter` 是很干净的 search 契约，**seed 保证分页稳定**这一点值得抄（避免翻页乱序）。
- `useCount` 印证「使用量是自建遥测」——Smithery 因为托管连接才拿得到；**我们 git-backed 拿不到，须自建 install 遥测**。

URL：
- https://smithery.ai/docs/concepts/registry_search_servers
- https://github.com/smithery-ai/cli
- https://workos.com/blog/smithery-ai

## 3. Glama（glama.ai）— 质量分 + 安全沙箱型目录

### 接口 / 元数据
- **公开 API**：入口 `glama.ai/mcp/reference`（具体格式文档未详列，但确有公开 API 可查 MCP servers）。
- **抓取的元数据**：每个 server 的**完整 JSON Schema**（所有 capability）、MCP annotation hints、行为数据、**change history（变更历史）**、**last-scanned timestamp（最后扫描时间）**。

### 质量与安全（策展最硬核的一家 — 强参考）
- **Tool Definition Quality Score (TDQS)**：从 6 个维度评分（如 Purpose Clarity 目的清晰度、Conciseness 简洁度）+ 评估「tool-set coherence 工具集连贯性」「server cohesiveness 服务内聚性」。→ **一个「内容质量分」而非「人气分」的范例，适合 git-backed 无下载量场景**（质量分不依赖遥测，靠静态分析 manifest 就能算）。
- **所有权验证**：GitHub OAuth。
- **恶意内容防护**：开源 build 在 **Firecracker microVM** 中执行以标记 malicious/risky 行为；远程连接器做 **prompt-injection detection**。

### 启发
- **git-backed 也能做质量信号**：TDQS 思路 = 对 skill manifest / 定义做静态质量打分（描述完整度、字段齐全度、示例有无），不依赖任何遥测。这是我们「无下载量时的替代质量维度」的最佳答案。
- change history + last-scanned timestamp = 「新鲜度/活跃度」维度，我们可用 git 最近 commit 时间平替。

URL：
- https://glama.ai/mcp/methodology
- https://github.com/glama-ai/tool-definition-quality-score
- https://glama.ai/blog/2025-03-24-mcp-discord （API for searching MCP servers）

## 4. Cline MCP Marketplace — 应用内「一键安装」市场 UX

### UX / 安装流
- **应用内市场**（Cline 编辑器内 App Store 形态），浏览可用 servers → 找到目标。
- **一键安装（single click）**：app 读取该 server 的**安装说明文件自动配置环境**，需要凭证时才向用户索要。
- **卡片信息**：显示 **ratings（评分）、downloads（下载量）、descriptions（描述）**。
- **提交/审核**：开发者在 `cline/mcp-marketplace` 仓库开 issue，提供 源链接 + 一张正方形图标 + 收录理由，并附 **`llms-installation.md`**（列依赖 + 安装步骤，供 AI 可靠自动安装）。
- **质量机制**：无重型人工 vetting；靠标准化的 `llms-installation.md` 让 AI 可靠完成安装（安装可靠性 > 内容审核）。

### 启发（对我们「应用内 skill 市场 + 一键安装」最贴近）
- **一键安装的关键 = 标准化安装清单文件**（Cline 的 `llms-installation.md`）。我们 skill 应有等价的「安装 manifest」让后端/前端机械执行安装（git clone/checkout subfolder + 声明依赖 + 凭证提示）。
- **提交走 GitHub issue/PR + 收录理由** = 轻量策展流，适合 git-backed 生态起步期。

## 5. VS Code 扩展市场 / npm（成熟应用内市场类比 — 只取 UX + 元数据维度）

### 搜索 / 排序维度（业界标配）
- **排序**：Relevance（相关性，默认）/ Installs（安装量）/ Rating（评分）/ Name / Published & Updated（发布/更新时间）。
- **过滤 DSL**：`@category:`、`@tag:`、`@sort:installs`、`@popular`、`@recommended` 等前缀过滤（编辑器内 Extensions view）。
- **卡片字段**：图标、名称、发布者（+**「验证发布者」蓝勾徽章**）、安装量、星级评分、一句话描述。
- **详情页结构**：README（Details）、Feature Contributions、Changelog、Version History、Ratings & Reviews、Q&A、Resources（repo/license/issues）、Categories、Tags、依赖大小。
- npm 类比：search 结果卡 = 名称/版本/描述/周下载量/最后发布时间/维护者/关键词；排序 = 相关性/流行度/质量/维护度（npms.io 的三维分）。

### 启发
- **排序维度可裁剪**：我们能做 相关性 + 更新时间 + star + 我们自建的安装量；评分需自建评价系统（起步期可缓）。
- **详情页信息架构成熟**：README + 版本历史 + 源仓库链接 + 分类/tag + 依赖，直接照搬即可。
- **验证发布者徽章** = verified 的成熟 UX 表达（蓝勾 + 悬浮说明）。

## 汇总：给我们的三条设计启发

### ① REST 后端接口草案维度
**Search 端点**（对齐 MCP Registry + Smithery）：
```
GET /skills?q=<全文/语义>&category=<枚举>&tag=<多值>&sort=<relevance|updated|stars|installs>
          &verified=<bool>&limit=<n>&cursor=<游标>[&seed=<稳定序>]
```
- `q` 全文（起步先关键词，后续可加语义）；分页优先**游标 cursor**（比 offset 稳），可选 `seed` 保证翻页序稳定（抄 Smithery）。
- filter：`category` / `tag` / `verified`（布尔 toggle 抄 Smithery 风格）。
- `sort`：relevance（默认）/ updated（git commit time）/ stars（GitHub）/ installs（**自建遥测**）。

**详情端点**：`GET /skills/{namespace}`（namespace = `owner/repo[/subfolder]`，抄 MCP `name` 反向域名去重）。

**Install 端点 + 语义**（抄 MCP `packages[]` + Cline 安装清单）：
```
POST /skills/{namespace}/install   body: { version?, ... }
```
- 后端按 skill 的「安装 manifest」执行：定位 git repo url + subfolder + version(tag) → clone/checkout → 声明依赖/凭证提示。
- **install 事件落库 = 我们的安装量遥测来源**（弥补 git-backed 无中心下载量）。

**元数据 schema（skill manifest，平移 MCP server.json）**：
`name`(namespace) / `description` / `repository{url,source,subfolder}` / `version` / `installType+args` / `category` / `tags[]` / `author` / 派生字段(stars, updatedAt, installCount, qualityScore)。

### ② 市场页可借鉴的 UX 结构
- **顶部**：搜索框 + 排序下拉（相关性/更新/star/安装量）+ 分类 tab / filter chips（category、verified）。
- **卡片**：图标 + 名称 + 作者 + 一句话描述 + 信号徽章（verified 蓝勾）+ 关键指标（star / 安装量 / 更新时间）+ 一键安装按钮。
- **详情页**：README + 版本历史 + 源仓库链接 + 分类/tag + 依赖/凭证要求 + 安装按钮（一键，缺凭证时才提示）。
- **一键安装**：依赖标准化「安装清单文件」（抄 Cline `llms-installation.md`），前端点一下、后端机械执行。

### ③ git-backed（无下载量）现实下的维度取舍
| 维度 | 能否直接做 | 来源 / 做法 |
|------|-----------|------------|
| 全文/关键词搜索 | ✅ 能 | 索引 manifest 的 name/description/tags |
| 分类 / tag | ✅ 能 | manifest 声明（MCP 官方 schema 也无 category，需我们自定义 taxonomy） |
| 更新时间 / 新鲜度 | ✅ 能 | git 最近 commit time（平替 Glama 的 last-scanned/change history） |
| star / 人气 | ✅ 能（间接） | 读 GitHub API 的 repo stars |
| verified / 官方徽章 | ✅ 能 | 命名空间所有权校验（抄 MCP: GitHub OAuth/OIDC/DNS/HTTP）+ 我们自己的「精选/官方」策展标记 |
| 质量分（不依赖遥测） | ✅ 能 | **抄 Glama TDQS 思路**：静态分析 manifest 完整度/描述清晰度/示例齐全度打分 |
| 恶意内容防护 | ⚠️ 视投入 | 起步可轻量（人工收录 + issue 理由，抄 Cline）；进阶抄 Glama 沙箱扫描 |
| **下载量 / 使用量** | ❌ 天然缺失 | git 源无中心遥测 → **必须自建**：后端记录 install 事件累计 installCount |
| 用户评分 / 评论 | ❌ 需自建 | 起步期可缓；要做得自建评价系统（VS Code/Cline 都有，但依赖中心化用户库） |

**一句话**：搜索/分类/更新时间/star/verified/质量分**都能做**（多数不依赖遥测）；**下载量与评分是唯二要自建中心化数据**的维度——起步阶段用「star + 更新时间 + 静态质量分 + 自建 installCount」组合，足以撑起排序与信任信号，无需硬造空的下载量字段。
