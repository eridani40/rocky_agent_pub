# openclaw Computer Use / Canvas / Browser 调研

- **调研范围**: openclaw 的 computer use / 屏幕控制 / canvas 实现（action 集合、OS 抽象层、macOS 实现、Canvas 范式、截图/grounding、browser vs computer-use 分层、集成架构）
- **调研对象**: refs/openclaw
- **调研日期**: 2026-07-10

## 一句话总览

openclaw **不自己实现 OS 级 computer use**——`computer-use.ts` 纯粹是 Codex Computer Use MCP 插件的「安装/就绪检查」管理器，真正控制 macOS 的动作（点击/键盘/截屏）全在 Codex 那个不透明的 MCP 服务器里。openclaw 自己用 TS 控制屏幕靠的是**两层**：自实现的 CDP 浏览器层（web 级）和自创的 **Canvas 范式**（在配对设备的 WebView 上渲染可受控 UI）。三层并存，各司其职。

## action 集合 + 参数

### Tier A: Codex Computer Use（代理，openclaw 不定义 action）

openclaw **不暴露任何 computer-use action**。`CodexComputerUseStatus.tools` 只是从 MCP 服务器列出工具名（`Object.keys(server.tools)`，computer-use.ts:332），具体 click/type/screenshot 的 schema 全在 Codex Computer Use 插件内部，对 openclaw 是黑盒。openclaw 能配置的只有「安装/启用」类参数（config.ts:267-296）:

| 配置键 | 默认值 | 作用 |
|--------|--------|------|
| `enabled` | 隐式 false（autoInstall/marketplace* 任一为真则隐式 true） | 总开关 |
| `autoInstall` | false | 缺插件时自动装 |
| `pluginName` | `"computer-use"` | Codex 插件名 |
| `mcpServerName` | `"computer-use"` | MCP 服务器名 |
| `marketplaceSource/Path/Name` | - | 从哪个 marketplace 装 |
| `marketplaceDiscoveryTimeoutMs` | 60000 | curated marketplace 轮询超时 |

注意：openclaw **不能改 Codex computer use 工具的参数**，只能确保它装上、启用、把 MCP server 暴露给 codex 子进程。

### Tier B: Browser（CDP，openclaw 自实现）

browser-tool.ts:165-192 的 `LEGACY_BROWSER_ACT_REQUEST_KEYS` + browser-tool.actions.ts:62-76 的 `supportsBrowserActTimeout` switch，可得 act 的 `kind` 集合:

| action kind | 关键参数 | 说明 |
|-------------|----------|------|
| `click` | `ref`/`x`/`y`, `doubleClick`, `button`, `modifiers` | 点击 |
| `type` | `text`, `ref`, `submit`, `slowly`, `delayMs` | 输入文本 |
| `hover` | `ref`/`x`/`y` | 悬停 |
| `scrollIntoView` | `ref`/`selector` | 滚动到可见 |
| `drag` | `startRef`, `endRef`（或坐标） | 拖拽 |
| `select` | `ref`, `values` | 下拉选择 |
| `fill` | `fields` | 批量填表 |
| `evaluate` | `fn` | 执行 JS |
| `wait` | `timeMs` 或 `textGone`/`selector`/`loadState` | 等待条件 |

外加顶层 action（非 act）: `snapshot`（`format=ai|aria`, `refs=aria|role`, `targetId`, `maxChars`, `labels`, `depth`, `selector`, `frame`）、`tabs`、`console`、`open/close/focus tab`、`navigate`、`screenshot`、`pdf_save`。

### Tier C: Canvas（openclaw 自创，tool-schema.ts:13-46）

| action | 参数 | 作用 |
|--------|------|------|
| `present` | `url`/`target`, `x/y/width/height`(placement), `node` | 在配对设备 WebView 显示 |
| `hide` | `node` | 隐藏画布 |
| `navigate` | `url`/`target` | WebView 打开新 URL |
| `eval` | `javaScript` | 在 WebView 里跑 JS，返回 `result` |
| `snapshot` | `outputFormat=png/jpg`, `maxWidth`, `quality` | 截 WebView |
| `a2ui_push` | `jsonl` 或 `jsonlPath` | 推 A2UI JSONL 渲染 UI |
| `a2ui_reset` | - | 重置 A2UI |

## OS 抽象层

**结论：openclaw 在 TS 层没有 OS 抽象层，因为它根本不在 TS 里控制 OS。**

- `grep CGEvent|AXUIElement|osascript|screencapture` 在 `extensions/ src/ skills/` 全是 test/命令分析/可执行文件探测的噪声，**没有任何真正的 OS 控制原语**。
- TS 怎么「控制 macOS」的真相：它**不控制**。它 spawn `codex app-server` 子进程（config.ts:657 默认 args `["app-server","--listen","stdio://"]`），computer use 的实际执行全在 codex 子进程里。openclaw 只通过 JSON-RPC（`requestCodexAppServerJson`）跟 codex 子进程通信，computer-use.ts:660-685 的 `createComputerUseRequest` 就是构造这种请求函数。
- 所以「TS 控制本机」对 openclaw 而言是个伪命题——它把 OS 控制外包给 codex 的 Rust 二进制（codex 是 Rust）。

## macOS 实现

**openclaw 侧：无 macOS 实现。** computer use 在 macOS 上怎么落地（CGEvent/screencapture/Accessibility）完全取决于 Codex 的 Computer Use MCP 插件，openclaw 既不实现也不关心。openclaw 唯一的「本机 macOS 操作」是 browser 层：通过 CDP（Chrome DevTools Protocol）连本地 Chrome 进程（cdp.ts），这是 web 进程级控制，不是 OS 级。

## Canvas 范式（重点 — 对「agent 控制屏幕」的不同思路）

这是 openclaw 最值得借鉴的一层。Canvas 不是「控制真实 OS 屏幕」，而是**给 agent 一个它完全掌控的渲染画布**：

- **架构**（skills/canvas/SKILL.md + host/a2ui.ts）: Gateway HTTP 端口（默认 18789）跑一个文件服务器（`/__openclaw__/canvas/<file>.html`，host/a2ui.ts:84-150）+ 一个 A2UI bundle（host/a2ui/index.html）。配对的 Mac/iOS/Android 节点 app 在 WebView 里加载这些 URL。Node bridge 把 canvas URL 推给配对设备。
- **A2UI = Agent-to-UI 协议**（a2ui-jsonl.ts:5-9）: JSONL 每行一个动作（`surfaceUpdate`/`beginRendering`/`dataModelUpdate`/`deleteSurface`/`createSurface`）。组件是声明式的（a2ui-jsonl.ts:32-44）: `{Column:{children:{explicitList:[...]}}}`, `{Text:{text:{literalString:...}}}`。Agent 用 `a2ui_push` 推 JSONL，画布就渲染出结构化 UI。
- **与 OS computer use 的关系**（这是关键洞察）: Canvas 是 OS computer use 的**更高层替代/补充**，不是同一层。
  - OS computer use = agent 控制「别人造的、agent 看不懂像素含义的」UI → 脆弱，靠坐标 grounding + 截图识别。
  - Canvas = agent 控制「自己刚渲染的、结构已知的」UI → 稳健，**无需 grounding**（agent 按 component id 寻址，因为 UI 是它自己推的）。
  - README:22 的 "render a live Canvas you control" = 字面意义，agent 真的在控制一个它从头渲染的画布。截图（`snapshot`）只用于「给用户/agent 看效果对不对」的 proof，不用于 grounding。
- **对我们设计的启发**: 如果「让 agent 控制屏幕」的本质是「让 agent 达成视觉任务」，不一定非要走 OS 像素控制。给 agent 一个它能完全渲染+eval+snapshot 的 WebView 画布，能覆盖一大批「展示/操作结构化内容」的场景，且远比 OS computer use 稳定。

## 截图 + 坐标 grounding

**截图**:
- Browser: cdp.ts:68-179 `captureScreenshot`，调 CDP `Page.captureScreenshot`，PNG/JPEG（quality 0-100），全页靠 `Emulation.setDeviceMetricsOverride` 临时扩 viewport + `captureBeyondViewport:true`，捕获后恢复原 viewport（含 devicePixelRatio）。
- Canvas: tool.ts:172-199 `snapshot`，通过 node bridge 的 `canvas.snapshot` 命令，节点返回 base64 → 写临时文件 → `imageResultFromFile`（带 `imageMaxDimensionPx` sanitization）。

**Grounding**:
- Browser: **aria refs + role refs** 双轨（cdp.ts:462 `snapshotAria` 用 CDP `Accessibility.getFullAXTree`；cdp.ts:930 `snapshotRoleViaCdp`）。refs 形如 `e12`（Playwright aria-ref id）或 role+name。browser-tool.ts:501-503 明确指引: "keep the same tab: pass targetId from snapshot into subsequent actions"、"use snapshot with refs='aria' for stable self-resolving refs"。交互落地用 Playwright locator（pw-tools-core.interactions.ts:1169 `locator.scrollIntoViewIfNeeded` 等）。坐标 `x/y` 也可用但 ref 优先。
- Canvas: **不需要 grounding** —— agent 按自己推的 component id 寻址，或用 `eval` 跑 JS 直接操作 DOM。
- Computer Use: grounding 不透明（在 Codex 插件里）。

## browser(CDP) vs computer-use 分层（对我们已有 browser/connector 的启发）

openclaw 同时有 CDP browser 和 OS computer use，边界清晰:

| 维度 | CDP Browser（自实现） | OS Computer Use（代理 Codex） |
|------|----------------------|------------------------------|
| 控制对象 | web 进程（Chrome tab） | 整个 OS 桌面 |
| 落地方式 | CDP + Playwright locator | Codex MCP 插件（黑盒） |
| Grounding | aria/role ref（结构化，稳定） | 坐标 + 截图（脆弱） |
| openclaw 投入 | 全自研，967 行 cdp.ts + 大量 pw-* | 仅 ~700 行 install/readiness 管理器 |
| 适用场景 | 浏览器内任务（占绝大多数 agent 场景） | 必须操作原生 app 时（兜底） |

**启发**: openclaw 把 95% 的工程投入了 browser 层（因为 agent 任务绝大多数在浏览器内），OS computer use 只做「能装上+能启用」的最薄胶水。我们项目已有 browser/connector，**应当把 browser 层做厚**，computer use 作为「browser 搞不定时的兜底」。openclaw 甚至把 computer use 的 action 定义权都让给了 codex（不自定义 schema），说明它认为 computer use 是低频兜底，不值得自己再包一层 action 语义。

## agent loop + 集成架构

**computer use 挂载点**（attempt-startup.ts:156-219）:
1. `run-attempt.ts:421` `resolveCodexComputerUseConfig` 读配置 → 传 `computerUseConfig` 给 startup。
2. `attempt-startup.ts:156` `computerUseMcpElicitationDelegationRequired = params.computerUseConfig.enabled` —— **computer use 一旦启用，就强制开 MCP elicitation 委托审批**（`withMcpElicitationsApprovalPolicy`，config.ts:1001）。这是安全耦合：computer use 能控 OS，其 MCP 调用必须走审批。
3. `attempt-startup.ts:214-219` 在 codex app-server client 启动后、buildAttemptParams 前，调 `ensureCodexComputerUse({client, pluginConfig, timeoutMs, signal})` —— 纯就绪门禁，不传 action。
4. `run-attempt.ts:1918` 把 `computerUseMcpServerName` 传进 attempt 参数，让 codex 子进程知道该信任哪个 MCP server。
5. 之后 codex 子进程跑 agent loop，computer use 工具由 codex 自己调度，openclaw 只在审批回调（elicitation-bridge）上介入。

**browser/canvas 挂载点**: 作为标准 agent tool（`AnyAgentTool`，tool.ts:93 `createCanvasTool`），注册进 agent 的工具集，LLM 直接 tool_call。

## 对本项目的可借鉴点

1. **不要在 TS 里实现 OS 控制**。openclaw 路线证明：TS 项目做 computer use，最务实的是**代理给一个有 OS 能力的子进程/MCP**，TS 层只管 install/readiness/审批。我们自己实现 CGEvent/osascript 是重复造轮子且易踩权限坑。若要 OS 级，优先评估能否接入现成 computer use provider（如 Codex CU MCP / Anthropic CU API）。

2. **三层「屏幕控制」分级，按频率分配工程投入**:
   - 高频：browser/CDP（我们已有 connector，做厚）—— aria ref grounding，稳定。
   - 中频：Canvas 式受控画布（可选创新）—— agent 渲染+eval+snapshot，零 grounding，适合展示/结构化任务。
   - 低频兜底：OS computer use（代理外部，薄胶水）。

3. **安全耦合 computer use 启用 ↔ 审批门禁**。openclaw 把 `enabled` 直接接到 MCP elicitation 审批策略（attempt-startup.ts:156-170），computer use 能控 OS 必须默认走人工/自动审批。我们设计时同样不能让 computer use 裸跑。

4. **Canvas 范式值得单独评估**。如果我们的「computer use」需求里有相当部分是「agent 展示/操作结构化视觉内容」（而非操作用户已开的原生 app），A2UI 式「agent 渲染 → WebView 显示 → eval/snapshot」比 OS 像素控制稳健得多，且天然跨平台（WebView 哪都有）。这是 openclaw 给「agent 控制屏幕」提供的不同于 Anthropic CU API 的第三条路。

5. **grounding 优先级**: browser 用 aria/role ref（结构化）> 坐标；computer use 退到坐标是无奈（OS 无结构树）。我们 browser 层应坚持 ref-first。

## 3-5 条最关键发现

1. **openclaw 的 `computer-use.ts` 是「安装管理器」不是「动作实现」**——它不定义 click/type/screenshot，只确保 Codex 的 computer-use MCP 插件装上+启用+审批门禁开。真正的 OS 控制在 Codex 子进程里（黑盒）。TS 项目做 OS computer use，openclaw 选择全外包而非自研。

2. **TS 控制本机的真相：openclaw 不在 TS 里控制 macOS**。grep 全仓零 CGEvent/AXUIElement/osascript/screencapture 原语。它 spawn codex 子进程走 JSON-RPC，OS 操作发生在 codex 的 Rust 二进制里。

3. **Canvas 是 openclaw 对「agent 控制屏幕」的独创第三条路**：A2UI JSONL 声明式渲染 → 配对设备 WebView 显示 → eval/snapshot 控制/取证。因为 UI 是 agent 自己造的，**完全不需要 grounding**（按 component id 寻址），这从根本上避开了 OS computer use 的坐标脆弱性。README 的 "render a live Canvas you control" 是字面属实。

4. **三层屏幕控制 + 投入倒挂**：browser(CDP, 自研, 重投入) > Canvas(自创范式, 中) > OS computer use(纯代理, 最薄)。openclaw 判定 agent 任务绝大多数在浏览器内，OS computer use 是低频兜底——这指导我们也应把 browser connector 做厚、computer use 做薄。

5. **安全硬耦合**：computer use 一启用就强制开 MCP elicitation 审批（attempt-startup.ts:156-170），能控 OS 的工具不能裸跑——这是我们必须照搬的红线。
