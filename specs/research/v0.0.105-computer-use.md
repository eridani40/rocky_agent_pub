## 1. 三竞品对比矩阵

| 维度 | e2b open-computer-use | iFurySt open-codex | openclaw |
|---|---|---|---|
| **运行模型** | 云沙箱（E2B Linux VM, Ubuntu）+ 本地仅 VNC 显示 | 100% 本地 macOS 原生（Linux/Windows 实验） | TS 层不控 OS，外包给 Codex 子进程（Rust 二进制） |
| **语言栈** | Python（poetry） | Swift 6.2（主线）+ Go+Python/PowerShell（实验 OS） | TypeScript（仅 install/审批/CDP browser/Canvas） |
| **action 粒度** | 多个独立工具（7 个） | 多个独立工具（9 个，对齐官方 CU 1.0.755） | 不定义（OS 层黑盒）；browser/canvas 自定义 |
| **action 参数风格** | `click(query)` 自然语言 → grounding 模型 → 坐标 | `click(app, element_index \| (x,y))`，AX 索引优先 | browser: aria/role ref 优先；CU 黑盒；canvas: 自推 component id（零 grounding） |
| **macOS 支持度** | 完全不支持（N/A） | 主线，完整（AX+CGEvent+ScreenCaptureKit） | 依赖 Codex CU MCP（黑盒，是否 macOS 透明） |
| **截图机制** | e2b-desktop PNG（1024×768 固定） | ScreenCaptureKit 单窗口 + ImageIO PNG（900KB/1280px 压缩） | browser: CDP captureScreenshot；canvas: node bridge snapshot；CU 黑盒 |
| **Retina 处理** | 无（云沙箱固定逻辑分辨率） | **标准答案**：backingScaleFactor 放大像素 + screenshotPixelScale 缩放链（见 iFurySt §坐标） | browser: devicePixelRatio；CU 黑盒 |
| **grounding 方式** | **独立 grounding 模型**（OS-Atlas / ShowUI HF Space），LLM 不碰坐标 | **AX tree**（element_index）优先 + 截图像素坐标兜底，无 grounding 模型 | browser: aria/role ref（CDP Accessibility.getFullAXTree）；CU 黑盒；canvas: 零 grounding |
| **权限要求** | 仅云 API key（本地无 TCC） | Accessibility（AX+postToPid）+ Screen Recording（ScreenCaptureKit），**不需 Input Monitoring** | CU 黑盒（在 codex 进程）；openclaw 自身不需 |
| **OS 抽象层** | SandboxBase（X11+远端 GUI agent，云沙箱专属） | **无统一抽象**——三平台各实现，只共享 tool schema+JSON-RPC 协议 | TS 层无 OS 抽象（不控 OS） |
| **后台输入（不抢前台）** | N/A（云沙箱独占） | **CGEvent.postToPid**（核心创新，实证不切走前台 app） | 无（osascript/AppleScript 必抢前台，故 openclaw 走 browser+canvas 替代） |
| **agent loop** | 内置（vision→action→grounding→exec→observe 线性循环，LLM 主动 stop 终止） | 外置（agent loop 在 Codex/Claude 侧，本服务仅响应 tool call） | 外置（codex 子进程跑 loop，openclaw 仅审批回调） |
| **对本项目的可借鉴度** | **低**（运行模型完全不适用，仅语义层可借：三模型分工、人类化输入、结构化 vision prompt） | **高**（macOS 原生控制直接对照、postToPid 后台输入、Retina 缩放、Unicode chunking、AX tree 渲染格式，全是现成答案） | **中**（TS 项目做 CU 的"代理外包"思路、安全审批硬耦合、三层屏幕控制分级——但路线本身我们不采纳） |

**核心分歧点**：三者代表了"让 agent 控制屏幕"的三条根本不同路线。
- e2b：**LLM 不碰坐标**，靠外部 grounding 模型翻译（云沙箱+视觉定位）。
- iFurySt：**LLM 选元素（AX index）或给坐标**，靠 macOS 原生 AX+CGEvent（本地原生控制，postToPid 后台）。
- openclaw：**TS 层不控 OS**，外包给 Codex 子进程；自研 browser/canvas 作为主战场（web 进程级控制）。

我们项目的位置：TS+Bun + anthropic_messages 协议（原生有 computer_use tool）+ 已有 browser/connector。**最接近 openclaw 的栈（TS），但需要 iFurySt 的能力（原生 AX+CGEvent+postToPid）**。

## 2. 针对 req 三问的设计方向建议

### 问 1：action 集合 + 每个 action 参数

#### 推荐 action 清单（聚合 tool，action 枚举参数）

| action | 必填参数 | 可选参数 | 说明 / 参考 |
|---|---|---|---|
| `screenshot` | — | `windowId?`, `maxWidth?`(默认 1280) | 截图，返回 image block。参考 iFurySt 900KB/1280px 压缩 |
| `click` | `coordinate: {x, y}` | `button`(`left`/`right`/`middle`, 默认 left), `clickCount`(默认 1), `pid?` | 左/右/双击统一入口；clickCount=2 即 double_click，clickCount=3 即 triple_click |
| `type` | `text: string` | `coordinate?`(先点后输), `chunkSize?`(默认 64 UTF-16), `delayMs?`(默认 12) | Unicode extended grapheme cluster 聚合（iFurySt §type_text 必抄） |
| `press_key` | `key: string` | `coordinate?`, `pid?` | xdotool 语法：`Return`/`super+c`/`Up`/`KP_0`（iFurySt KeyMapping.swift） |
| `scroll` | `coordinate: {x, y}`, `direction`(`up`/`down`/`left`/`right`) | `pages?`(默认 1, 支持小数), `pid?` | 补 e2b 缺；delta = 12.0 * pages（iFurySt `scrollWheelDelta`） |
| `drag` | `from: {x,y}`, `to: {x,y}` | `pid?`, `steps?`(默认 10) | 补 e2b 缺；10 步线性插值 leftMouseDragged（iFurySt `dragTargeted`） |
| `mouse_move` | `coordinate: {x, y}` | `pid?` | 补 e2b 缺；单独移动（hover 语义） |
| `wait` | — | `durationMs?`(默认 1000, 上限 10000) | 补 e2b 缺；等动画/加载 |
| `get_app_state` | `app: string` | `textLimit?`(默认 500), `maxTreeNodes?`(默认 1200), `maxTreeDepth?`(默认 64) | **AX 路线核心**：返回 key window 截图 + AX tree（参考 iFurySt）。每个 turn 开头建议调 |
| `list_apps` | — | — | 列运行中 + 近期用过的 app（参考 iFurySt Spotlight metadata） |
| `disconnect` | — | — | 释放 owner 锁（参考 browser tool），LLM 完成后主动释放 |

#### 关键决策点 1：聚合 tool（Anthropic 原生）vs 独立工具集（iFurySt）

| 方案 | 优势 | 劣势 |
|---|---|---|
| **A. 聚合 computer_use tool + action 枚举**（Anthropic 原生） | • Anthropic Messages API 原生支持，模型已训练（beta）<br>• 协议层零成本复用<br>• schema 统一，一个 tool 入口 | • 单 tool schema 庞大<br>• 跨协议（openai/minimax）需自定义适配<br>• Anthropic 原生 schema 不含 get_app_state/list_apps |
| **B. 独立工具集**（iFurySt 9 tool 风格） | • 每 tool schema 简洁，LLM prompt 干净<br>• 细粒度权限（policy 可单独 bound）<br>• 跨协议天然一致 | • 不能直接复用 Anthropic 模型训练<br>• tool 数量多（10+），assemble 后 tools 列表臃肿 |

**推荐：方案 A（聚合 tool，对齐 Anthropic 原生 computer_use）+ 内部 action 实现借鉴 iFurySt**

理由：
1. 本项目主协议是 `anthropic_messages`，Anthropic Messages API 有原生 computer_use tool（beta），模型直接输出坐标 action——**协议层和模型层零成本复用**。
2. 跨协议（openai-compat / minimax）时，在 llm-provider 层做 schema 适配（这些协议本就需要自定义 tool 协议转换，加一个 computer_use 适配无额外架构成本）。
3. iFurySt 的能力（element_index 优先 / postToPid / Retina 缩放）**在 action 实现层借鉴**，而非暴露为独立 tool。`get_app_state` 作为补充 action（扩展 Anthropic 原生集合），LLM 在 AX-rich 场景调用它拿 element_index，再把 index 喂给 click。

#### 关键决策点 2：坐标系

- **推荐：绝对像素（截图像素）+ Retina 2x scale 处理**，对齐 Anthropic 原生 computer_use（`coordinate: {x, y}`）和 iFurySt。
- **不推荐归一化 [0,1]**：Anthropic 原生不支持，且 iFurySt 的 `screenshotPixelScale = screenshotPixelSize / windowBounds` 三段式缩放链（见 iFurySt §坐标）是 Retina 场景的标准答案，直接抄。
- 归一化仅在 e2b ShowUI 备选实现里出现，且它本身就要 `*image.width` 还原回像素——多此一举。

### 问 2：OS 协议抽象层

#### 推荐：ComputerDriver / ComputerSession 接口（仿 BrowserDriver/BrowserSession），三层切分

参考 iFurySt「三平台不共享 OS 抽象、只共享 tool schema+协议」+ 本项目「ComputerDriver/ComputerSession 范式（仿 BrowserDriver）+ platform/screenshot.ts + platform/input.ts」(见 project-tool-system §4.2.1/§7.3)，推荐结构：

```typescript
// app/server/src/platform/computer/types.ts
interface ComputerSession {
  // 截图（返回带尺寸+scaleFactor，供坐标换算）
  screenshot(opts?: { windowId?, maxWidth?, quality? }): Promise<{
    mime: 'image/png'; data: string;  // base64
    width: number; height: number;    // 像素尺寸
    scaleFactor: number;              // Retina 2x 时为 2
    windowBounds?: { x: number; y: number; width: number; height: number };  // point 坐标系
  }>;
  // 鼠标（pid 可选，postToPid 路线）
  click(point: {x,y}, opts?: { button?, clickCount?, pid? }): Promise<void>;
  drag(from: {x,y}, to: {x,y}, opts?: { pid?, steps? }): Promise<void>;
  mouseMove(point: {x,y}, opts?: { pid? }): Promise<void>;
  scroll(point: {x,y}, direction: 'up'|'down'|'left'|'right', pages?: number, opts?: { pid? }): Promise<void>;
  // 键盘
  type(text: string, opts?: { pid?, chunkSize?, delayMs? }): Promise<void>;
  pressKey(keySpec: string, opts?: { pid? }): Promise<void>;
  // AX（高级，macOS 首发，其他平台可选）
  getAppState?(app: string, opts?): Promise<{ screenshot, axTree, windowBounds, scaleFactor }>;
  listApps?(): Promise<AppInfo[]>;
}

interface ComputerDriver {
  readonly platform: 'macos' | 'linux' | 'windows';
  connect(opts: { ownerSessionId: string; pid?, windowId? }, signal?): Promise<ComputerSession>;
  isAvailable(): Promise<boolean>;               // 权限预检
  requestPermissions?(): Promise<PermissionStatus>;
  close(): Promise<void>;
}
```

#### 三层切分边界

| 层 | 文件归属 | 职责 |
|---|---|---|
| **工具层（Tool 协议适配）** | `app/server/src/tools/computer-use/tool.ts` | Tool 接口（definition+run），action 路由，坐标换算（截图像素↔window point↔global point），Anthropic computer_use schema 对齐，image block 包装入 ToolRunResult.content |
| **Driver 层（OS 原生操作）** | `app/server/src/platform/computer/macos.ts`（首发）+ 预留 `linux.ts`/`windows.ts` | 实现 `ComputerDriver`/`ComputerSession`；每平台一套；macOS 首发（CGEvent+AXUIElement+ScreenCaptureKit 或 screencapture CLI） |
| **连接治理** | `app/server/src/tools/computer-use/connector-manager.ts`（仿 browser ConnectorManager） | owner 锁（sessionId 全局唯一，**比 browser 更刚需——一台机器一套鼠标**）+ lazy connect（首次调 screenshot 才接管）+ switch flag（用户开关"允许 agent 控制本机"）+ 三态门禁（`not_enabled`/`in_use_by_other`/`connect_failed`）+ disconnect action |

**req 说"1 和 2 可以是 1 套——每个 OS 分别实现这些 action"**：本设计正好契合——`ComputerSession` 接口就是那"一套 action"，每 OS 一个 `ComputerDriver` 实现（macOS 首发，Linux/Windows 预留接口签名）。

### 问 3：macOS 实现（本版本只 macOS，最关键决策）

#### 方案对比

| 方案 | 描述 | 优势 | 劣势 |
|---|---|---|---|
| **A. Bun:ffi 直调 CoreGraphics+ApplicationServices** | FFI 调 CGEventCreateMouseEvent / CGEventPostToPid / AXUIElement* C 函数 | 全 TS 栈，单进程，无外部构建依赖 | FFI 复杂：CGEvent struct marshal、AXUIElement 大量 CFTypeRef/CFArray/CFDictionary（FFI 地狱）；**ScreenCaptureKit 是 Swift/ObjC API 不可 ffi**（需 screencapture CLI 兜底截图）；Bun:ffi 对 callback 有限制 |
| **B. Swift helper binary（复用 iFurySt Kit）** | 编译 iFurySt 式 OpenComputerUseKit 成小 CLI，TS 经 subprocess+JSON IPC 驱动（仿 NodeWorkerDriver 模式） | **复用 iFurySt 逆向成果**（权限/AX/CGEvent/坐标/Unicode chunking 全现成）；postToPid 后台输入、ScreenCaptureKit 单窗口截图都是现成；项目已有 NodeWorkerDriver 子进程模式，再加 Swift helper 性质相同 | 加 Swift 构建依赖（需 Xcode）；.app bundle 分发复杂（TCC 权限挂 bundle，需 Unix socket proxy）；增加打包流程 |
| **C. 纯 osascript/AppleScript + screencapture CLI** | 用 osascript 模拟键鼠 + screencapture 截图 | 无构建依赖，项目已有 osascript 范式（workspace-dialog.ts、chrome-discover.ts）；最快 MVP | **不能后台输入**（osascript 必抢前台，iFurySt 架构文档明确"避免回退 AppleScript"）；AX 控制差；坐标精度问题；截图只能全屏或按 windowId（不能精确控制）；慢 |
| **D. 外部 computer use provider/MCP（openclaw 路线）** | 接 Codex CU MCP / 其他 CU provider，TS 层做 install/审批胶水 | TS 层零 OS 控制，最薄；openclaw 实证可行 | 强依赖外部黑盒二进制（Codex 是 OpenAI 产品，发布受限）；无 postToPid 定制；Anthropic CU 是协议层（模型出 action），仍需本地 executor，没有现成"Anthropic CU executor 服务"；黑盒不可控 |

#### 推荐：方案 B（Swift helper binary，MVP 子集），osascript+screencapture 仅作开发期 fallback

**核心理由**：
1. **复用 iFurySt Kit 的逆向成果是最大杠杆**——权限引导（TCC.db 直读 + preflight 合并）、CGEvent.postToPid 后台输入、ScreenCaptureKit 单窗口截图、Retina backingScaleFactor 缩放、Unicode extended grapheme cluster chunking、xdotool key parser，全是现成且经过官方对比验证的（artifacts/tool-comparisons 实证 postToPid 不抢前台）。
2. **本项目已有 NodeWorkerDriver 子进程模式**（为绕 Bun playwright hang，spawn node worker + 三流分离 JSON IPC）——再加一个 Swift helper 性质完全相同，**无架构破坏**。
3. **方案 A 的 FFI 地狱不可低估**：AXUIElement API 大量用 CFTypeRef/CFArray/CFDictionary，CFType marshal 在 TS FFI 里极脆弱；ScreenCaptureKit 是 Swift-only API，纯 C FFI 调不了，必须 screencapture CLI 兜底——那不如直接走方案 B 用 ScreenCaptureKit。
4. **方案 C 天花板太低**：osascript 必抢前台（用户在用机器时 agent 不能操作），不能 postToPid 后台输入——iFurySt 的核心价值就是这个，缺了就达不到"真正可用"。
5. **方案 D 强依赖黑盒**：Codex 是 OpenAI 闭源产品，我们不能把核心能力挂在它可用性上。

**MVP 子集（本版本）**：Swift helper 第一版只做 3 件事，后续版本扩展：
1. `screencapture --window-id` 或 ScreenCaptureKit 单窗口截图（带 scaleFactor 回传）
2. CGEvent click/type/scroll/drag via `postToPid`（pid 可选，无 pid 走全局 event tap）
3. 简化 AX tree（get_app_state，可选——MVP 可先省，后续补）

**权限模型**（必抄 iFurySt）：
- **Accessibility**（AX + postToPid 键鼠）+ **Screen Recording**（ScreenCaptureKit），**不需 Input Monitoring**（postToPid 的关键优势）。
- TCC 授权挂 `.app` bundle：Swift helper 打包成 `Rocky Computer Use.app`（LSUIElement agent-style，无 Dock 图标），CLI/TS 主进程通过 Unix domain socket proxy 转发请求（iFurySt `MacOSAppAgentProxy.swift`），避免每个 launcher（IDE/Node/Bun）各自授权。
- 权限预检合并：`granted = (TCC.db auth_value==2) || AXIsProcessTrusted() || CGPreflightScreenCaptureAccess()`（iFurySt `Permissions.swift:67-86`）。

**osascript/screencapture 开发期 fallback 用途**：
- 开发期无 Swift helper 时，用 `screencapture -x -t png <tmp>` + `osascript -e 'tell app "X" to ...'` 跑通全链路（image block / tool schema / ConnectorManager / 坐标换算）。
- 但**生产路径必须是 Swift helper**，osascript 不作为正式 implementation（因抢前台缺陷）。

## 3. 集成进本项目（基于 project-tool-system findings）

### 3.1 ImageBlock GAP 必须先打通（P0 前置）

(见 v0.0.105-cu-project-tool-system.md §6) 当前 `message/types.ts:174-180` ContentBlock 联合不含 ImageBlock（标 future 删了），但协议层 `protocol-encode.ts:255` 已就绪 image encode，spec §4.2 也定义了。

打通点（5 个，P0）：
1. `message/types.ts:174-180 ContentBlock` 加 ImageBlock（`{type:'image', source: ImageSource, mediaType}`，`ImageSource = {kind:'url',url} | {kind:'base64',data}`）
2. 两套 image 形态对齐：spec/message 用 `{kind:'base64',data}` + 顶层 `mediaType`；协议层 `{type,media_type,data}` 嵌 source 内——在 encode/translate 处适配
3. `ToolResultBlock.content: ContentBlock[]` 承载 image，CrudStore 序列化 base64（DB 行大小评估，PNG 常 1-2MB base64 字符串）
4. context engine assemble 不过滤 image（实现时跑 typecheck + UT 验证无 drop 逻辑）
5. 前端渲染 image content block（chat UI 展示截图，最小化：显示 `[screenshot]` 占位 + click 展开）——P1，不阻塞工具本身

**这是 computer use 接入的最大前置工作量**。建议本版本拆为独立 Task（ImageBlock 打通）作为 P0，computer use 工具实现依赖它。

### 3.3 截图回灌 LLM 链路（核心闭环）


### 3.4 安全红线（参考 openclaw）

**能控 OS 的工具不能裸跑**。openclaw 把 `computer_use.enabled` 硬耦合到 MCP elicitation 审批策略（`attempt-startup.ts:156-170`，见 v0.0.105-cu-openclaw.md §安全耦合）。

本项目复用现有机制：
- **tool-approval pending（v0.0.101 HITL 蓝图）**：computer use 工具可挂 `interaction()` 钩子，首次截图/点击前转 pending，用户确认才执行（复用 ask-question 通用 pending 机制）。
- **TOOL_POLICY bound 分级**：`playground-rocky` 默认加；`subagent` 不加（subagent 控制 OS 风险高）；`studio-*` 视场景。
- **switch flag（ConnectorManager）**：用户可在配置开关"允许 agent 控制本机"，默认 off。
- **破坏性动作单独审批**：`click`/`type` 在敏感 app（如 Finder 删除、Mail 发送）前可加二次确认——参考 iFurySt MCPServer instructions：「Ask the user before taking destructive or externally visible actions such as sending, deleting, or purchasing」。

### 硬约束
- memory `test-no-real-spawn-system-gui`：测试禁真实 spawn 系统命令（screencapture 会截 IDE、osascript 会弹 dialog）。

| 层 | 策略 |
|---|---|
| **UT（白盒，主要）** | • deps/spawnFn 注入 mock Swift helper（不真 spawn）<br>• mock ComputerDriver（implementations 一个 fake，返固定 screenshot bytes + 坐标回执）<br>• 验证：tool→driver 调用序列、坐标换算（截图像素→window point→global point，含 Retina 2x case）、image block 包装入 ToolRunResult、ConnectorManager owner 锁状态机（owner/in_use_by_other/disconnect 流转）、TOOL_POLICY bound 过滤、schema 校验（action 枚举/必填） |

## 附：关键综合洞察（3 条）

1. **我们项目的位置是"TS 栈 + anthropic_messages 协议 + 需要原生 macOS 控制"——必须把 openclaw 的 TS 外包路线（D）和 iFurySt 的原生能力（B）结合**：TS 层做 tool 协议适配 + 连接治理 + 审批（openclaw 思路），但 OS 控制不外包给黑盒，而是 spawn Swift helper（iFurySt 成果复用）。这条路 openclaw 没走（它选择纯代理），但我们能走——因为有 iFurySt 开源 Kit 现成可抄。

2. **ImageBlock 打通是 P0 前置，比 computer use 工具本身工作量还大**。当前 `message/types.ts:174-180` ContentBlock 砍了 ImageBlock（标 future），但协议层/spec 都已就绪。这个 GAP 不打通，截图回灌 LLM 的核心闭环就断——computer use 工具做得再好也白搭。建议拆为独立 Task 优先做。

3. **postToPid 后台输入是 iFurySt 最核心创新，必须抄**。它让 agent 操作时不抢前台（用户可继续用机器）、不需 Input Monitoring 权限（少一道 TCC 门）——这是 computer use 从"演示玩具"到"可用工具"的分水岭。osascript/AppleScript 路线（方案 C）天生缺这个，所以达不到生产可用。Swift helper（方案 B）是拿到 postToPid 的唯一路径。
