- **调研范围**: 现有 plugin system 能否承载 mention provider + 三场景输入区复用
- **调研对象**: 本项目 `app/server/src/plugin/`、`app/web/src/`、`specs/tech/plugin_system/`
- **调研日期**: 2025-07-15
- **前置调研**: `v0.0.45-mention-system.md`（输入区 / skill / workspace 现状，互补不重叠）

## Q1 — 现有 Plugin System 全貌

### 1.1 核心概念

| 概念 | 定义 | 代码位置 |
|---|---|---|
| **ExtensionPoint** | 有名字的契约槽位（`id` + `cardinality` + `group`），泛型 `TContract` 携带接口类型 | `app/server/src/plugin/extension-point.ts:21-38` |
| **ExtImpl** | 一条扩展实现（`implId` + `point` + `impl` 模块路径 + 可选 configSchema/description） | `app/server/src/plugin/manifest.ts:52-69` |
| **PluginManifest** | 插件清单（`id` + `extImpls[]` + 可选 configSchema/config/label/description） | `manifest.ts:17-30` |
| **Registry** | 全量代码树，按 `(point, implId)` 索引持有 impl 类引用 | `app/server/src/plugin/registry.ts` |
| **PluginManager** | 运行时 active 投影：`getExtensionImpls(point)` = Registry ∩ enabled，get 时实例化 | `app/server/src/plugin/plugin-manager.ts` |
| **两级 enabled 门** | ext impl 进 active 当且仅当 `plugin.enabled && impl.enabled` | spec `[P0]plugin_manager_interface.md` §3.4 |
| **cardinality 三态** | `exclusive`(<=1) / `list`(无序并存) / `ordered`(按 effective order 升序) | `extension-point.ts:25` |

### 1.2 注册 / 发现 / 加载链路

```
app/plugins/builtins/<pluginId>/plugin.json   (静态 manifest)
    ↓ BuiltinLoader.loadAll()
    ↓   扫描 app/plugins/builtins/*/plugin.json
    ↓   校验目录名 == manifest.id
    ↓   读 impl 模块 default export 的类
Registry.register(point, implId, implClass)   (按 point+implId 索引)
    ↓
PluginManager.getExtensionImpls(point)
    ↓   Registry ∩ (plugin.enabled && impl.enabled)
    ↓   按 cardinality 解析 + 按当前 config 实例化
    ↓
Consumer（agent/context/tools）
```

代码：`app/server/src/plugin/builtin-loader.ts`、`registry.ts`、`plugin-manager.ts`。
Spec：`[P0]builtin_plugins_directory.md` §3、`[P0]plugin_manager_interface.md` §3.4。

### 1.5 能力边界：plugin 能"贡献"什么

**当前 plugin 只能贡献 server-side 行为实现**——具体来说是向某个 EP 注册一个满足 `TContract` 接口的类，由 PluginManager 在 `getExtensionImpls` 时实例化返回给 consumer。

Plugin **不能**贡献：
- 前端 UI 组件（无 UI 扩展点概念）
- HTTP API 端点（端点由 `app/server/src/handlers/` 硬编码）
- 前端路由 / 页面
- 前端 store / state

### 1.6 Web 端 plugin 相关代码

`app/web/src/components/plugin-config-page/` 是 **plugin 管理 UI**（配置后台），不是 plugin 贡献的 UI：
- `page-plugin-config.tsx` — 2 tab（插件 / 扩展点）根组件
- `section-ext-point-area.tsx` — 按 cardinality 路由 radio/checkbox/ordered 控件
- `component-ext-impl-radio.tsx` / `-checkbox.tsx` / `-ordered.tsx` — 三种控件

数据源：`GET /config/plugin` → `PluginInventoryTree`（`inventory-builder.ts` 算出）。
这是宿主渲染的管理界面，plugin 本身不参与 UI 渲染。

## Q2 — 三场景输入区现状（v0.0.39 后更新）

| 维度 | playground | studio 单聊 | studio 群聊 |

| 组件 | `SectionChatDetail` | `MemberChatPage` | `SquadChatPage` |

| run 态 | `ComponentRunStateBar` + `AbortSlot` | 同（v0.0.39 P2 R3 共享） | **无**（群聊无 run 态） |
| 发送 API | `onSend` prop → `postMessage` | `postMessage` 直调 | `postMessage` 直调 |
| 消息流 | `ComponentMessageStream`（共享） | 同（共享） | 同（共享 + filter） |

### 2.2 共性抽象现状

**已共享**：
- `ComponentMessageStream`（消息渲染内核，三场景共用）
- `ComponentRunStateBar` / `ComponentRunStateAbortSlot`（playground + 单聊共用）
- `useSessionRunState` hook（playground + 单聊共用，群聊不用）

**未共享（三份独立实现）**：
- textarea + `useState('')` + `onKeyDown` 逻辑（各写一份）
- 发送逻辑（playground 经 prop 回调，studio 直调 `postMessage`）
- 输入区 wrapper 布局（各写一份 `div` + className）

**结论**：输入区（textarea + send）无共享 hook / 共享子组件。三处独立实现，结构相似但不互通。

## Q3 — 现有可扩展机制盘点

### 3.1 工具注册（`tools/registry.ts`）

模式：静态 import + 数组组装。

```typescript
// app/server/src/tools/registry.ts:50-51
export function defaultTools(_workdir?: string): Tool[] {
  return [fileReadTool, fileWriteTool, ... taskTool];  // 16 个
}
```

- 每个 tool 是 `{ definition, needsApproval?, run }` 对象（`tools/types.ts:157-167`）
- **不走 plugin system**——直接代码 import，无 manifest、无 EP
- 过滤：`filterToolDefinitionsBySessionType()` 按 sessionType 裁剪（`scope-allowed-tools.ts:121-134`）

### 3.2 Squad 工具（4 个）

`teamTool` / `goalTool` / `requirementTool` / `taskTool`——与基础工具同模式（静态 import → `defaultTools` 数组），非 plugin。
权限三层门控：config.tools 白名单 + schema 层裁剪 + 工具层 action 判权。

### 3.3 Skill 系统

独立的三层目录扫描 + frontmatter 解析机制（`skills/resolver.ts`），与 plugin system 完全独立。
- 有自己的 HTTP API（`handlers/skill.ts`）
- 有自己的前端 API 封装（`web/src/lib/api-client.ts`）
- **不走 plugin system**——无 EP、无 manifest

### 3.4 "按名字注册 → 运行时列出 → UI 渲染" 的现成模式

| 模式 | 注册 | 列出 | UI 渲染 |
|---|---|---|---|
| Plugin EP | manifest + 代码类 | `getExtensionImpls(point)` | plugin-config-page（管理 UI） |
| Tool | 代码 import 数组 | `defaultTools()` | 无 UI（LLM 消费） |
| Skill | 三层目录扫描 | `SkillResolver.resolve()` | skill 列表页 |

**最接近 mention provider 需求的是 Plugin EP**——有「注册 → 按类型列出」的完整机制。
**但都没有「注册 → 前端渲染 tab/列表」的模式**。

## Q4 — Plugin 能否贡献前端 UI

### 4.1 现有 plugin 贡献 UI 的先例

**无。** 翻遍 `app/plugins/builtins/` 下三个 plugin（`llm_anthropic`、`rocky_context`、`zhipu_web_search`），全部只贡献 server-side 行为类（provider / protocol / mapper / reducer / reminder）。无 plugin 包含前端组件。

### 4.2 Plugin system 是纯 server-side

**确认：plugin system 是纯 server-side 机制。**

证据：
1. `ExtImpl.impl` 字段是 `.ts` 模块路径（`manifest.ts:57-58`），指向 server-side 类
2. `BuiltinLoader` 用 server-side `import()` 加载 impl 模块（`builtin-loader.ts`）
3. `PluginManager.getExtensionImpls` 返回 server-side 实例
4. 无 web-side Registry / PluginManager 对等物
5. `plugin-config-page` 是宿主代码，非 plugin 贡献

### 4.3 如果要让 plugin 贡献前端 UI，需要扩展的能力

| 缺失 | 说明 |
|---|---|
| 前端 EP 概念 | 当前 EP 只在 server-side 定义，web 端无对等的 EP 注册表 |
| 前端组件注册 | 无机制让 plugin 声明"我贡献一个 React 组件" |
| manifest 扩展 | 当前 `ExtImpl.impl` 指向 server-side 类，无 `frontendComponent` 字段 |
| 前端 discovery | web 端无 builtin-loader 等价物扫描 plugin manifest |
| 跨边界通信 | server plugin 产出的数据如何实时推到前端 mention popup |

## Q5 — 可行性判断（摆事实）

### 5.1 用现有 plugin system 承载 mention provider

**server-side 部分——够用。** 新建一个 `mention_provider` EP（cardinality=`list`，group=`mention`）即可：
- `FileMentionProvider` 贡献文件搜索
- `SkillMentionProvider` 贡献 skill 列表
- consumer（mention HTTP handler）调 `getExtensionImpls(MentionProviderPoint)` 获取 active providers

**前端部分——完全不够用。** 现有 plugin system 无法：
- 注册前端 popup 的 tab / 列表渲染组件
- 让 plugin 贡献前端可渲染的 provider icon / label / 搜索逻辑
- 在前端发现和加载 plugin

### 5.2 项目内更合适的现成机制

| 机制 | 匹配度 | 差距 |
|---|---|---|
| Plugin EP | server 侧匹配，前端缺失 | 无前端 EP / 组件注册 / discovery |
| Tool 注册 | 不匹配（tool 给 LLM，不给人） | 无前端 UI 层 |
| Skill 三层扫描 | skill provider 可复用扫描 | 仅限 skill，不通用 |
| sessionType 过滤 | 可借鉴 per-scene 可见性 | 仅 server-side 工具过滤 |

**无一个现成机制能完整承载 mention provider 的全栈需求。**

### 5.3 需要新建什么

无论最终选哪条路，以下能力都需要新建：

1. **共享 mention 输入组件**（`ComponentMentionComposer`）：替换三处独立 textarea
2. **Mention popup 原语**：popover + tab 切换 + 列表 + 键盘导航（项目无 Popover/Combobox 原语）
3. **Provider 注册 + 前端路由**：至少需要一种机制让前端知道"有哪些 mention provider、各自渲染什么"

可能的路径（列事实，不推荐）：
- **路径 A**：扩 plugin system 到全栈（加前端 EP + 组件注册 + web-side discovery）
- **路径 B**：mention provider 不走 plugin，走独立的轻量注册（类似 tool 的静态数组模式 + HTTP API 暴露给前端）
- **路径 C**：首版硬编码 2 provider（file + skill），架构层预留 EP 扩展点但不实现 plugin 化

## 事实摘要

| 维度 | 事实 |
|---|---|
| Plugin system server 侧 | 成熟的 EP + Registry + PluginManager + cardinality 三态，11 EP 运行中 |
| Plugin system 前端侧 | 仅有管理 UI（inventory 消费），无 plugin 贡献 UI 的能力 |
| 输入区复用 | 三场景独立实现 textarea + send，共享 `ComponentMessageStream` 但输入区不共享 |
| 工具/skill 注册 | 不走 plugin，静态 import 或目录扫描，无前端 UI 层 |
| 现有 Popover/Combobox | 不存在，需新建 |
| Plugin 贡献 UI 先例 | 零 |

## 未解问题

1. **mention provider 是否需要 server-side 行为**？如果仅是前端搜索（file tree API + skill list API），server-side EP 的价值有限。如果涉及 server-side 上下文注入（mention 解析 → 注入 prompt），则 server EP 有价值。
2. **三场景的 mention provider 可见性是否需要差异化**？如群聊不出现 @file（workspace 归属问题）、单聊不出现 @user（当前无 user 概念）。这决定了是否需要 per-scene provider 过滤（类似 sessionType 工具过滤）。
3. **plugin system 全栈扩展的战略优先级**？mention provider 是第一个需要"前端 UI + server 行为"全栈扩展的场景。如果未来有更多类似需求（如 @dashboard 插件、@chart 插件），全栈 plugin 化的 ROI 更高。如果仅此一个，轻量方案更合理。
4. **首版硬编码 vs plugin 化的分界线**？如果首版只做 file + skill 两个 provider，硬编码的开发成本远低于扩展 plugin system。但后续加 provider 时需要重构。分界线在哪取决于 provider 扩展频率预期。
5. **前置调研中的 6 个未解问题**（editor 升级 / workspace 搜索 / .gitignore / 触发字符 / 编码方式 / studio 单聊覆盖）仍然开放，与本调研互补。
