## 1. Kimi（kimi-coding-plan）

### 地址与模型
- anthropic 兼容 baseUrl：`https://api.kimi.com/coding/`（cc-switch `src/config/claudeProviderPresets.ts:119`）
- 官方文档交叉验证：kimi.com/code/docs/third-party-tools/claude-code.html 明确 `export ANTHROPIC_BASE_URL=https://api.kimi.com/coding/` ✅
- 模型：`kimi-for-coding`（cc-switch 预设，显式端点别名，避免非 claude- 前缀模型 id 的窗口限制）；官方文档另有 `k3` / `k3-256k`（256K）/ `kimi-for-coding-highspeed` 按会员档位
- 注意区分：`https://api.moonshot.cn/anthropic` 是 Kimi **按量 API**（MaaS 站），非 coding plan——不要混用
- cc-switch 预设额外钉 `CLAUDE_CODE_MAX_CONTEXT_TOKENS=262144`（256K 窗口）——我们若做 native 类型可类似给出 contextWindow 默认值

### 额度查询（cc-switch 权威）
- 端点：`GET https://api.kimi.com/coding/v1/usages`（`src-tauri/src/services/coding_plan.rs:109`）
- 鉴权：`Authorization: Bearer {api_key}` + `Accept: application/json`，超时 15s
- 401/403 → 凭证失效（Expired），提示 Invalid API key

### 响应形状（coding_plan.rs:151-197）
```json
{
  "limits": [ { "detail": { "limit": 100, "remaining": 80, "resetTime": "..." } } ],
  "usage":  { "limit": 5000, "remaining": 4200, "resetTime": "..." }
}
```
- `limits[]` 每条 → **five_hour** tier：已用 = (limit - remaining)，百分比 = 已用/limit*100
- `usage` 对象 → **weekly_limit** tier：同公式
- `resetTime` 兼容字符串（ISO）与数字（秒 <1e12 判秒、否则毫秒；≤0 视为无重置时间）——`extract_reset_time`（coding_plan.rs:67-81）
- limit/remaining 兼容数字与字符串（parse_f64）

### 窗口语义
- `limits` = 5 小时滚动窗口（多条时逐条都进 five_hour tier）；`usage` = 周限额。重置时间直接由 API 给出，无需本地计算。

### UI 建议
- 两行 tier：`5小时 已用 X%（HH:mm 重置）`、`本周 已用 Y%`；resetTime 做倒计时需本地时钟 30s 级 tick（cc-switch SubscriptionQuotaFooter 模式：查询 5 分钟一次、倒计时每 30s 重渲染）。

## 2. 智谱 GLM（glm-coding-plan）

### 地址与模型
- 国内站：`https://open.bigmodel.cn/api/anthropic`（claudeProviderPresets.ts:902）；国际站：`https://api.z.ai/api/anthropic`（:920，Zhipu GLM en 预设）
- 官方文档交叉验证：docs.bigmodel.cn/cn/coding-plan/quick-start + faq 均给出同地址；claude-code-router issue #1047 确认实际请求地址 `https://open.bigmodel.cn/api/anthropic/v1/messages` ✅
- 模型：cc-switch 预设 `glm-5.1`（haiku/sonnet/opus 全指同名）

### 额度查询（cc-switch 权威）
- 端点：`GET {quota_base}/api/monitor/usage/quota/limit`，quota_base 按 baseUrl 路由：含 `bigmodel.cn` → `https://open.bigmodel.cn`，否则 `https://api.z.ai`（coding_plan.rs:313-326）
- **鉴权特殊：`Authorization: {api_key}`——裸 key，不加 Bearer 前缀**（coding_plan.rs:330 注释显式强调）
- 另带 `Accept-Language: en-US,en`；401/403 → 凭证失效

### 响应形状（coding_plan.rs:378-411）
```json
{
  "success": true, "msg": "",
  "data": {
    "level": "GLM Coding Plan 标准版",
    "limits": [
      { "type": "TOKENS_LIMIT", "percentage": 35.0, "nextResetTime": 1755100000000, "unit": 3 },
      { "type": "TOKENS_LIMIT", "percentage": 60.0, "nextResetTime": 1755500000000, "unit": 6 }
    ]
  }
}
```
- 业务错误：`success == false` → 读 `msg`
- `percentage` **直接就是已用百分比（0-100）**，无需 limit/remaining 换算
- `nextResetTime` 毫秒时间戳；`level`（套餐名）可展示
- 条目过滤：type 大小写不敏感匹配 `TOKENS_LIMIT` 或 `CREDIT_LIMIT`

### 窗口语义（关键陷阱）
- **必须按 `unit` 字段分桶**：`unit:3` → five_hour（`number:5`=5 小时滚动窗）；`unit:6` → weekly（`number:7` 与 `number:1` 两种取值都实测过，只锚 unit 不锚 number）（coding_plan.rs:213-233）
- **禁止按 nextResetTime 排序代替 unit**：周期末尾周窗口会比 5h 窗口更早重置，时间排序必然把两桶标反（cc-switch issue #3036 实证，coding_plan.rs:237-243）
- unit 缺失兜底启发式：无 nextResetTime 的优先归 5h，其余按 reset 升序补位；老套餐（2026-02-12 前订阅）只回 1 条 TOKENS_LIMIT → 自然降级为只展示 5h
- **团队版（zhipu_team）**：同路径 + `?type=2`，额外 header `bigmodel-organization` / `bigmodel-project`（+ api_key 三者缺一不可）；仅存于国内站；响应 shape 与个人版完全一致（coding_plan.rs:1190-1266）。团队版与个人版 baseUrl 相同，**无法靠 baseUrl 自动区分，必须显式类型路由**（coding_plan.rs:1285-1295）——印证老板「provider 要选类型」的设计。

### UI 建议
- 两行 tier + 套餐名（level）徽标。类型选择器若含团队版，需动态展示组织 ID/项目 ID 两个额外字段。

## 3. MiniMax（minimax-coding-plan）

### 地址与模型
- 国内站：`https://api.minimaxi.com/anthropic`（claudeProviderPresets.ts:1087）；国际站：`https://api.minimax.io/anthropic`
- 官方文档交叉验证：platform.minimaxi.com/docs/api-reference/text-anthropic-api（Anthropic SDK 兼容页）+ token-plan/claude-code 页 ✅
- 模型：cc-switch 预设 `MiniMax-M2.7`（官方文档已上 M3，支持 extended thinking）；预设带 `API_TIMEOUT_MS: 3000000`（长推理超时）

### 额度查询（cc-switch 权威）
- 端点：`GET https://{api.minimaxi.com | api.minimax.io}/v1/api/openplatform/coding_plan/remains`（coding_plan.rs:415-431，按 baseUrl 判断 CN/EN 域）
- 鉴权：`Authorization: Bearer {api_key}`；401/403 → 凭证失效

### 响应形状（coding_plan.rs:468-484, 644-697）
```json
{
  "base_resp": { "status_code": 0, "status_msg": "" },
  "model_remains": [
    {
      "model_name": "general",
      "current_interval_remaining_percent": 80.0,
      "end_time": 1755100000000,
      "current_weekly_status": 1,
      "current_weekly_remaining_percent": 40.0,
      "weekly_end_time": 1755500000000
    }
  ]
}
```
- 业务错误：`base_resp.status_code != 0` → 读 `status_msg`
- 只取 `model_name == "general"` 的条目（编程套餐），跳过 `video` 等其他模型桶
- **`current_*_remaining_percent` 是剩余百分比，需反转为已用：used% = 100 - remaining%**

### 窗口语义
- 5h 桶：`current_interval_remaining_percent` + `end_time`（毫秒），**恒存在**
- 周桶：**仅当 `current_weekly_status == 1` 才展示**（=3 表示该套餐无周限额，remaining 恒 100 不应显示）；重置时间 `weekly_end_time`
- cc-switch 有成套单测覆盖边界（status=3 跳过、general 任意位置、负百分比透传等，coding_plan.rs:1573-1716）——实现时可对照抄用例

### UI 建议
- 5h 桶必显；周桶按状态条件渲染。CN/EN 站按 baseUrl 自动判定，同一类型两条 preset。

## 4. DeepSeek（deepseek-api，按量付费）

### 地址与模型
- anthropic 兼容：`https://api.deepseek.com/anthropic`（claudeProviderPresets.ts:857；官方 api-docs.deepseek.com 首页声明「使用与 OpenAI/Anthropic 兼容的 API 格式」✅）
- 模型列表端点独立挂在根路径：`https://api.deepseek.com/models`（cc-switch 预设注释：anthropic 兼容层在 /anthropic 子路径，/models 是根上独立端点）
- 预设模型：`deepseek-v4-pro`（haiku 用 `deepseek-v4-flash`）

### 余额查询（双官方：cc-switch 实现 + DeepSeek 官方文档）
- 端点：`GET https://api.deepseek.com/user/balance`（balance.rs:74-78；官方文档 api-docs.deepseek.com/zh-cn/api/get-user-balance ✅✅）
- 鉴权：`Authorization: Bearer {api_key}`；401/403 → 凭证失效

### 响应形状（balance.rs:110-139）
```json
{
  "is_available": true,
  "balance_infos": [
    { "currency": "CNY", "total_balance": "110.00",
      "granted_balance": "10.00", "topped_up_balance": "100.00" }
  ]
}
```
- `total_balance` 等是**字符串**（parse_f64_field 兼容）
- `is_available == false` → 展示「余额不足」；每条 balance_info 一行（币种 + 总余额）

### 窗口语义
- **无窗口概念**——这是预付费余额（货币），不是套餐额度 tier。与前三渠道的展示形态不同：显示 `¥110.00（余额不足?）` 而非 5h/周百分比。

### UI 建议
- 余额型与额度型两种展示模板：额度型（kimi/glm/minimax）= 百分比 + 重置倒计时；余额型（deepseek）= 货币余额 + 可用状态。

## 6. 我们的接入点（读 spec 得出，不涉产品代码细节）

### 6.1 类型扩展：`llm_provider` 扩展点新增 per-type impl
- 现状（specs/tech/agent/providers_and_models/[P0]llm_provider_interface.md）：`LlmProvider` 行为契约 = per-type、无状态，仅 `buildAuthHeaders(config)`；现有 impl 三种——`anthropic_compatible`（`x-api-key` + `anthropic-version`）、`openai_compatible`（Bearer）、`glm`（JWT 签名）。
- **ProviderInstance（= app_config providers 组一条 record 的 data）无独立 `type` 字段，靠 `pluginId` 指向 impl**——「provider 需要选择类型」落地方式 = 在 `llm_provider` 扩展点下新增 4 个 impl（kimi_coding_plan / glm_coding_plan / minimax_coding_plan / deepseek_api），类型选择器 = pluginId/impl 列表。这与 web_search 的 `data.type` 路由（[P0]app_config.md §3.6）是两种既有范式，providers 走前者（pluginId）更贴合现有模型。
- **protocol 固定 `anthropic_messages`** 完全兼容现有「1 provider : 1 protocol 锁定」（v0.0.53 起 protocolId 在 provider 实例层、必填）——四渠道类型创建时 protocolId 预置且不可改即可。
- 额度/余额查询能力是新增行为：现有 `LlmProvider` 契约只有 `buildAuthHeaders`，需扩展点层面新增能力接口（如 `queryQuota(config)`），仅这 4 个 impl 实现——架构设计时定契约形状。

### 6.2 展示挂载点：provider 列表外
- UI 契约（specs/ui/components/providers/section-providers.md）：`section-providers.tsx` 持 providers 列表（GET /provider items）+ view 状态机（list|detail）。老板要求「列表外展示」= **list 视图层**、provider 卡片之外的列表级汇总区（cc-switch 对应 SubscriptionQuotaFooter/UsageDashboard 的 footer/dashboard 模式）。
- 刷新：cc-switch 用 react-query `REFETCH_INTERVAL = 5*60*1000`（src/lib/query/subscription.ts:12）+ 失败保留上次成功值（LastGoodSnapshot 模式 + 失败占位合成，不整块消失）。我们 5 分钟刷新直接对齐此节奏；倒计时文本每 30s 重渲染即可（不必 5 分钟内多次拉 API）。

### 6.3 风险与待证
- **R1（必须核实）鉴权 header 形态**：coding plan 三渠道走 ANTHROPIC_AUTH_TOKEN 语义（Bearer），智谱额度查询却**不加 Bearer**（裸 api_key）。需确认四渠道 `/anthropic/v1/messages` 调用各自接受的 header（x-api-key vs Authorization Bearer vs 裸 key）——这决定 4 个新 impl 的 buildAuthHeaders 差异。cc-switch 全部用 ANTHROPIC_AUTH_TOKEN（Bearer 系）推测试用可通，但智谱额度端点的裸 key 是实测差异点，标注「高置信/待启动时用真 key 实测」。
- **R2 智谱团队版**：与个人版同 baseUrl，无法靠 baseUrl 区分——若类型列表要含团队版，需显式类型路由 + 组织/项目 ID 两个额外字段（cc-switch zhipu_team 先例，coding_plan.rs:1285-1295）。老板需求列的 glm-coding-plan 未细分，建议 v0.0.350 先个人版、团队版留扩展位。
- **R3 响应形状漂移**：三个 coding plan 查询端点无官方文档，字段以 cc-switch 2026-08-13 快照为准；实现须按 cc-switch 的防御式解析（字段缺失降级、业务错误码分支）+ 保留原始错误文案透出，便于上游变更时定位。
- **R4 窗口语义陷阱**（实现必修项）：智谱按 `unit` 分桶（禁按重置时间排序，issue #3036）；MiniMax 剩余百分比需反转 + 周桶 status==1 才显示；Kimi resetTime 秒/毫秒双兼容。cc-switch 均有成套单测（coding_plan.rs:1573-1716）可直接对照移植用例。
- **R5 硬编码域名 vs 用户 baseUrl**：cc-switch 额度查询端点从固定域名发起（仅智谱按 baseUrl 路由 CN/EN）。我们实现建议统一从 provider 实例 baseUrl 推导查询域（保持用户可改 baseUrl 的灵活性），推导规则 = detect_provider 的子串匹配表（coding_plan.rs:26-49 + codingPlanProviders.ts:22-55 前后端同构路由表）。
