## 1. 产品概述与目标

### 1.1 背景与问题

当前国产 coding plan 渠道（kimi/glm/minimax/deepseek）只能用通用「Anthropic 格式兼容」类型硬拗：地址手填、无额度查询，用户看不到套餐用量。老板需求：原生类型支持 + 额度/余额查询。

### 1.2 产品目标

- **P0**：provider 新增 4 个 native 类型（类型选择 → 地址自动填充 → protocol 固定 anthropic_messages）；
- **P0**：额度/余额查询——providers 列表外展示（列表级汇总区）+ 每 5 分钟自动刷新；
- **P0**：额度型（kimi/glm/minimax）与余额型（deepseek）两种展示模板。

### 1.3 非目标（见 §6）

volc（火山方舟）v1 不做（额度查询需 AK/SK 双凭据）；glm 团队版不做（留扩展位）。

## 2. 功能需求

### 2.1 provider 类型选择（4 个 native 类型）[P0]

**描述**：添加/编辑 provider 时类型选择器在既有「Anthropic 格式兼容」外新增 4 个 native 类型。
**用户故事**：作为用户，我希望选「Kimi Coding Plan」类型后地址自动填好，不用查文档抄 URL。

**用户行为链路**：设置 → 模型 → providers → 添加提供商 → 类型选择 → 填 API Key → 保存。

**功能交互细节**：
- 类型落地方式 = `llm_provider` 扩展点新增 4 个 per-type impl（既有概念，[P0]llm_provider_interface.md）；类型选择器选项 = 现有 impl 列表（pluginId 路由），**不发明新概念**；
- **用户可见类型名（友好词）**：「Kimi Coding Plan」「智谱 GLM Coding Plan」「MiniMax Coding Plan」「DeepSeek（按量付费）」；
- **协议固定**：4 类型 protocolId 预置 `anthropic_messages` 且不可改（1 provider : 1 protocol 锁定，v0.0.53 既有规则）——表单 protocol 控件对此 4 类型只读；
- **地址自动填充**：选类型时 baseUrl 自动填 preset 默认值（可改，用户保留自定义自由）：

| 类型 | 默认 baseUrl（官方文档背书） | 默认模型名（仅默认值，不锁定） |
|---|---|---|
| Kimi Coding Plan | `https://api.kimi.com/coding/` | `kimi-for-coding` |
| 智谱 GLM Coding Plan | `https://open.bigmodel.cn/api/anthropic` | `glm-5.2` |
| MiniMax Coding Plan | `https://api.minimaxi.com/anthropic` | `MiniMax-M2.7` |
| DeepSeek（按量付费） | `https://api.deepseek.com/anthropic` | `deepseek-v4-pro` |

- 协议行为：4 类型 buildAuthHeaders 与 `anthropic_compatible` 完全一致（`x-api-key` + `anthropic-version: 2023-06-01`，四渠道实测全通）；
- 模型名会随厂商上新滚动（实测 glm 请求 5.2 回显 5.3、minimax 已上 M3）——默认值不锁定，UI 不得用响应回显 model 反推/校验请求模型。

**Use Cases**：

| ID | 用户操作链路 | 预期结果 |
|---|---|---|
| UC-1 | 添加 provider → 类型选「Kimi Coding Plan」 | baseUrl 自动填 `https://api.kimi.com/coding/`，protocol 锁定 anthropic_messages 不可改 |
| UC-2 | 选「DeepSeek（按量付费）」→ 改 baseUrl 为自定义代理 | 地址可改，保存成功，额度查询域随 baseUrl 推导 |
| UC-3 | 4 类型 provider 各发一条消息（模型选默认） | 4 渠道均 200 正常回复（anthropic 协议） |

### 2.2 额度/余额查询（列表外展示 + 5 分钟刷新）[P0]

**描述**：providers 列表页 provider 卡片之外，加「额度总览」列表级汇总区；每 5 分钟自动刷新。
**用户故事**：作为用户，我希望一眼看到各 coding plan 套餐用量和 deepseek 余额，不用去各家官网查。

**用户行为链路**：设置 → 模型 → providers 列表页 → 底部「额度总览」区自动展示。

**功能交互细节**：
- **位置**：providers 列表视图（list 状态）底部、provider 卡片之外（cc-switch SubscriptionQuotaFooter 模式）；仅列表页展示，detail 页不展示；
- **范围**：仅上述 4 类型的 provider 实例参与（通用 anthropic 兼容类型不出现）；
- **刷新**：每 5 分钟自动拉取（页面停留期间）；**失败保留上次成功值**（不整块消失），显示「上次更新 HH:mm」；
- **重置倒计时**：文本每 30s 重渲染（「约 3 小时后重置」），不重复拉 API；
- **两种展示模板**：
  - **额度型（kimi/glm/minimax）**：两行——「5 小时额度 已用 X%（HH:mm 重置）」「本周额度 已用 Y%」；
  - **余额型（deepseek）**：「余额 ¥9122.69」+ 不可用时显示「余额不足」；
- **可折叠/展开（boss 铁律，展开后内容定义）**：额度总览每渠道默认紧凑两行；点击展开后显示完整明细，内容**来源 = 该渠道额度查询 API 本次响应**，**渲染 = 纯文本 + 百分比徽标**（无 markdown/富文本），**格式 = 整数百分比、货币两位小数、本地时间**：
  - kimi：会员档位（如「高级会员」，来自 `user.membership.level`）+ 5h/周两桶明细 + 完整重置时间 + 并发额度；
  - glm：套餐名（`data.level`，如「max」）+ 5h/周两桶明细 + 完整重置时间；
  - minimax：5h 桶明细 +（若有周限额）周桶明细；
  - deepseek：分币种余额（赠送/充值拆分）+ 账户可用状态；
  - 各渠道展开区底部：「上次更新 HH:mm」。

**Use Cases**：

| ID | 用户操作链路 | 预期结果 |
|---|---|---|
| UC-4 | providers 列表页（已配 4 类型 provider） | 底部额度总览区 4 条目：kimi/glm/minimax 各两行百分比 + deepseek 余额行 |
| UC-5 | 停留列表页超 5 分钟 | 数值自动刷新；重置倒计时文本持续走动 |
| UC-6 | 断网期间到刷新点 | 保留上次成功值 + 「上次更新 HH:mm」，不整块消失 |
| UC-7 | 点击某渠道条目展开 | 显示套餐名/会员档位 + 两桶明细 + 完整重置时间 + 上次更新时间 |
| UC-8 | deepseek 余额耗尽（is_available=false） | 显示「余额不足」 |

### 2.3 各渠道数据规则（实测消化，供架构/实现）[P0]

**查询端点与鉴权**（四渠道全部真调实证）：

| 渠道 | 查询端点 | 鉴权 |
|---|---|---|
| kimi | `GET {baseUrl推导}/v1/usages` | Bearer |
| glm | `GET {推导域}/api/monitor/usage/quota/limit` | **裸 api_key（无 Bearer，实证）** |
| minimax | `GET {推导域}/v1/api/openplatform/coding_plan/remains` | Bearer |
| deepseek | `GET {推导域}/user/balance` | Bearer |

查询域统一从 provider 实例 baseUrl 推导（子串匹配路由，采纳预研 R5：保持用户改 baseUrl 的灵活性；glm 按 baseUrl 含 bigmodel.cn → 国内站 / 否则 z.ai；minimax 按 minimaxi/minimax.io 同理）。

**分桶/解析规则**（全部实测实证，cc-switch 对照）：
- **kimi**：`limits[]` 每条 → 5h 桶；`usage` 对象 → 周桶；已用优先直读 `usage.used`，缺失时 `limit - remaining` 换算兜底；数值可为字符串（兼容解析）；`resetTime` ISO 字符串；
- **glm**：条目过滤 `type ∈ {TOKENS_LIMIT, CREDIT_LIMIT}`；分桶**只锚 `unit`**（unit:3→5h、unit:6→周；number 不锚定）；`percentage` 直接是已用百分比（0-100 无需换算）；`nextResetTime` 毫秒；**禁按重置时间排序代替 unit**（周期末尾必然标反，cc-switch issue #3036）；套餐名 `data.level` 展示；
- **minimax**：只取 `model_name == "general"` 条目；已用% = **100 − remaining%**（反转）；周桶**仅当 `current_weekly_status == 1` 才展示**（=3 无周限额跳过，remaining 恒 100 不可展示）；毫秒时间戳；
- **deepseek**：无窗口概念；`balance_infos[]` 每条（币种+金额字符串）+ `is_available`。

**时间口径**：glm/minimax 毫秒时间戳、kimi ISO 字符串——统一转本地时间展示。

**调研形状 diff 三点显式消化**（live-verify 报告）：
1. **kimi 字段演进（字符串值 + used 直读 + membership 新字段）→ 采纳**：兼容字符串数值解析 + used 优先 + membership.level 进展开区（增强展示，成本低）；向后兼容不破坏防御解析。
2. **glm 发现第三类 TIME_LIMIT（unit:5，Web 工具分项额度）→ 不采纳进本期展示**：按 cc-switch 口径忽略（不进 5h/周两桶，避免混桶）；留作后续版本增强展示（search-prime/web-reader 分项），不进 v0.0.350。
3. **glm 周桶 unit:6/number:1 变体 → 采纳**：再次实证 cc-switch「只锚 unit 不锚 number」规则，实现必须照此（禁按 number 或重置时间分桶）。

### 2.4 错误与降级 [P0]

- 401/403 → 该渠道显示「凭证已失效，请检查 API Key」（不隐藏其他渠道条目）；
- 业务错误（glm `success==false` / minimax `base_resp.status_code != 0`）→ 透出原始错误文案（便于上游变更定位）；
- 字段缺失/形状漂移 → 防御式解析降级（缺哪段展示哪段，不整块失败）；
- 响应超时 15s（cc-switch 同款）。

## 4. 验收标准

1. 类型选择器含 5 项（1 既有 + 4 新增），4 新类型选中即自动填充 baseUrl、protocol 锁定不可改（UC-1）；
2. 4 类型 provider 可保存、可发消息、行为与 anthropic 兼容类型一致（UC-3/P-D）；
3. 额度总览区在 providers 列表外（卡片外、列表页底部），仅 4 类型实例参与（UC-4）；
4. 额度型两行模板 + 余额型货币模板正确展示实测数值（百分比整数、金额两位小数、本地时间）（UC-4/P-B）；
5. 5 分钟自动刷新 + 失败保留上次值（UC-5/6）；
6. 展开区含套餐名/会员档位 + 完整明细 + 上次更新时间（UC-7，boss 铁律）；
7. glm 周桶仅 status==1 展示；kimi used 直读；数值字符串兼容；TIME_LIMIT 忽略（§2.3 全规则）；
8. 401/403 凭证失效友好提示，不影响其他渠道（UC-8 + §2.4）；
9. 用户可见文案全友好词（无 unit/TOKENS_LIMIT/base_resp 等内部术语）；
10. volc 不出现在类型列表。

## 6. 非目标（明确不做）

- ❌ volc（火山方舟）类型与额度查询——需 AK/SK 双凭据（与推理 key 两套，复用被网关拒，cc-switch 实证）；表单/类型列表 v0.0.350 不含，后续支持时加 AK/SK 可选字段；
- ❌ glm 团队版（zhipu_team）——同 baseUrl 无法自动区分，需显式类型 + 组织/项目 ID 字段，留扩展位；
- ❌ 国际站 preset（z.ai / minimax.io / moonshot 按量 API）——baseUrl 可改即达（查询域随 baseUrl 推导自动路由），不做独立类型；
- ❌ 手动刷新按钮、额度告警、用量历史曲线（cc-switch 亦无）；
- ❌ TIME_LIMIT（Web 工具分项额度）展示（留后续增强）。
