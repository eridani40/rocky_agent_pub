## 1. 背景与问题

### 1.1 当前结构性缺陷

v0.0.45 上线 mention 子系统、v0.0.68 扩 workitem + member provider，决策「核心=地址，不嵌 name」——mention tag 只存 `type`+`path`，pill 显示文本靠 `deriveMentionLabel` 取 path **末段推导**。由此产生的连锁缺陷：

| 症状 | 根因 |
|---|---|
| **workitem pill 显示裸 ID**（`workitem/task/T-0001` → `T-0001`，title 丢失） | path 末段是 ID 不是 title，推导 hack 失败 |
| **member pill 显示裸 ULID**（`01J...`，人名丢失） | memberId 是 ULID，path 末段推导出无意义串 |
| **名字在 `handleSelect` 选中那步就被丢** | composer 只透传 `{type, path}`，`listView.title` 弃用 |
| **workitem kind+id 塞进 path**（`workitem/task/T-0001`） | 违背结构化原则，XML flat 属性可扩展性未被利用 |
| **LLM 收到 `<mention type="member" path="01J..."/>` 是无意义 ULID** | address 只管编址、不携带任何可读语义，LLM 无法利用 |

### 1.2 目标（两条不变量）

1. **INV-1：provider search 产出即完整内容**——address + display 全在 search 时构建好。前端拿到什么存什么、渲染什么，**不做推导 / 补全 / 二次查询**。
2. **INV-2：前端完全类型无关**——只透传 + 只按统一 display 渲染，代码里**无 `if (type === ...)` 分支**。加新 type = provider 给新 icon key + registry 加 glyph，渲染逻辑零改动。

## 2. 锁定设计摘要（照搬 req，不重新发明）

### 2.1 Address / Display 强制分离（核心不变量）

| 关注点 | 字段 | 消费者 | 前端是否解释 |
|---|---|---|---|
| **Address（语义/地址）** | `type` + 地址属性（`path` / `kind`+`id` / `id`） | LLM + 下游解析 | ❌ 透传不解释 |
| **Display（呈现）** | `display`：`{ icon, label, badge? }` | pill 渲染 | ✅ 唯一渲染依据 |

### 2.2 Address 字段（按 type 拆开，不再往 path 里塞东西）

| type | address 字段 |
|---|---|
| `file` | `path`（workspaceDir 下相对路径） |
| `skill` | `path`（skill 绝对目录） |
| `workitem` | `kind`（`goal`/`kr`/`requirement`/`task`）+ `id`（G-0001/T-0001 等） |
| `member` | `id`（memberId / ULID） |

> 纠正过去 `workitem/task/T-0001` 塞 path：workitem 拆 `kind`+`id`，XML flat 属性各占一格。

### 2.3 Display 字段（全类型统一闭集合 `{ icon, label, badge? }`）

| 字段 | 含义 | file | skill | workitem | member |
|---|---|---|---|---|---|
| `icon` | glyph key | `file` | `skill` | `goal`/`kr`/`requirement`/`task` | `member` |
| `label` | 主文本 | basename | skill 名 | title | 成员名 |
| `badge` | 徽标（可空） | — | — | — | `leader`（mate 留空） |

> `detail` 字段**已删**（用户判定冗余）。workitem 的 id 只留 address，不进呈现。

### 2.4 XML flat 属性报文（方案 A，display 写进 tag 持久化）

```xml
<mention type="file"     path="src/utils/helper.ts"            icon="file" label="helper.ts"/>
<mention type="skill"    path="/Users/.../drama-script-writer" icon="skill" label="drama-script-writer"/>
<mention type="workitem" kind="task" id="T-0001"               icon="task" label="接口联调"/>
<mention type="workitem" kind="goal" id="G-0001"               icon="goal" label="提升DAU"/>
<mention type="member"   id="01J..."                           icon="member" label="张三" badge="leader"/>
<mention type="member"   id="01HXYZ..."                        icon="member" label="李四"/>
```

- 单行、self-closing `/>` 结尾
- 空字段省略（不写空串）；属性顺序无关
- 值做标准 XML 转义（名字/title 可能含 `"` `<`）
- 正则泛化：整段匹配 `<mention ... />` + 抽全部 `k="v"` 属性（顺序无关）

### 2.5 持久化 = 渲染源自洽（硬约束，用户强调）

display 跟 address 一起序列化进**同一条字符串**，server 原样落库 / 原样发 SSE / 原样发 LLM / 原样回显。读取回显：renderer 解析**同一字符串**取 display → pill，**零 provider/store 调用、零重解析**。

- **display 是发送时刻快照**（实体改名后旧消息保留旧名——可接受，换来自洽回显）
- address 仍留 tag 内作稳定句柄
- **禁止 display 走 metadata 旁路存储**——整个报文（address+display 全属性）作为 message content 字符串的一部分落库，server 零处理透传

### 2.6 统一渲染器 + Glyph registry

- renderer 只读 `icon/label/badge` → 删除 `deriveMentionLabel`（path 末段 hack）+ `MentionIcon` 的 `if (type===...)` 分支
- 新增 `Glyph` registry：icon key → SVG，一次性注册 **7 个 glyph**（`file` / `skill` / `member` + workitem 的 `goal`/`kr`/`requirement`/`task`）
- `handleSelect` 直接透传整条 item（含 display），零推导

### 2.7 不向后兼容

- 旧消息里的旧 tag（`<mention type="..." path="..."/>` 两属性）直接降级为纯文本显示（不 crash）
- **不做数据迁移**

## 3. 功能需求（4 type × search/prefill/render + read-back 自洽）

### 3.1 F1 — File mention（基线，最简）

**期望行为**：
1. 用户在 ChatComposer 输入 `@` → popover 弹出，tab 选 `file`，输入关键词
2. provider search 返回 `MentionItem { type:'file', path, display:{icon:'file', label:basename} }`
3. 选中 → `handleSelect` 透传整条 item → ChatComposer 序列化为 `<mention type="file" path="..." icon="file" label="..."/>` 内嵌 content
4. 发送 → server 原样落库 + 原样发 LLM
5. 读取回显 → renderer 正则扫 tag 取 display → pill `[file-icon] helper.ts`

**验收**：basename 正确显示；server 零处理（content string 端到端一致）。

### 3.2 F2 — Skill mention

同 F1，type='skill'，icon='skill'，label=skill name，path=skill 绝对目录。

### 3.3 F3 — Workitem mention（squad 群聊 + leader/mate 单聊）

**期望行为**（squad 群聊场景）：
1. 用户在看板或对话区输入 `@` → tab 选 `workitem`，搜 goal/KR/requirement/task title
2. provider search 返回 `MentionItem { type:'workitem', kind, id, display:{icon:kind, label:title} }`
3. 选中 → pill 显示 `[kind-icon] <title>`（**无裸 ID**）
4. 发送 → tag `<mention type="workitem" kind="task" id="T-0001" icon="task" label="接口联调"/>` 落库 + 发 LLM
5. 读取回显 → pill 正确显示 title + kind icon

**验收**：4 kind（goal/kr/requirement/task）各覆盖一条；pill 显示 title 不显示 ID；tag 含 `kind`+`id`+display 四属性。

### 3.4 F4 — Member mention（squad 群聊独占）

**期望行为**：
1. 用户在 squad 群聊输入 `@` → tab 选 `member`，搜成员 name
2. provider search 返回 `MentionItem { type:'member', id:memberId, display:{icon:'member', label:name, badge?:'leader'} }`
3. 选中 → pill 显示 `[member-icon] <name>`，leader 加皇冠徽标
4. 发送 → tag `<mention type="member" id="01J..." icon="member" label="张三" badge="leader"/>` 落库 + 发 LLM
5. 读取回显 → pill 正确显示 name + leader 徽标

**验收**：leader + mate 各一条；leader 有皇冠徽标、mate 无；LLM 收到 memberId（可解析为 AgentRef）+ display.name 双信息。

### 3.5 F5 — @按钮回路（看板 → leader 单聊 prefill）

**期望行为**（沿用 v0.0.68 R3 回路）：
1. 用户在看板卡片 hover @ 按钮 → 切到 leader 单聊 + 输入区 prefill pill
2. prefill pill 携带 `{type:'workitem', kind, id, display:{icon:kind, label:title}}`
3. 发送 → 同 F3 路径 4-5

**验收**：prefill pill 立即显示 title（无裸 ID）；发送后落库 + 回显正确。

### 3.6 F6 — Read-back 自洽（核心不变量 INV-1 落地）

**期望行为**：
1. 消息落库后，重新打开会话
2. pill 从存储字符串的 display 渲染，**零 store / provider 调用**
3. 即使 workitem title 已改 / member name 已改，旧消息仍显示**发送时刻**的名字快照

**验收**：发送后改 workitem title → 重开会话 → 旧 pill 仍显示旧 title（自洽回显），新消息用新 title。
