## 1. 背景与定位

**用户诉求**：让飞书用户在 IM 内直接绑定并对话 Rocky agent（playground / studio session），无需打开 web。

**核心定位**：channel = IM 渠道接入层，与 client（web/app 直连）**对等并列**。client 怎么用 session，channel 就怎么用——`base.deliverTo(sid,msg)` = `agentManager.deliverTo`，进同一个 agent loop；不创建 channel 专属 session；`MessageSender` user 变体加 channel 来源标记。

**架构形态（D7）**：channel 是 EP（`point:'channel'`, `cardinality:'list'`），飞书是它的 impl（`app/plugins/builtins/feishu/plugin.json` manifest 声明）。和 provider EP 完全同构（provider 多 LLM 厂商 / channel 多 IM 平台，未来加微信/钉钉 = 加 impl 不动核心）。

**与现有概念辨析**：
- **channel ≠ connector**（方向相反：connector=agent→外部工具/浏览器，channel=IM↔agent）
- **channel ≠ SseChannel**（SseChannel 是 web 推送桥 server→browser SSE；IM channel 是飞书 IM↔agent。代码层用 `FeishuChannel` 避免命名混淆）
- **agent loop 本体零改**——channel 只是又一条 inbound 路径 + 又一个 outbound 订阅者

## 2. 功能需求

### 2.1 channel EP 注册 + FeishuChannel ExtImpl [P0]

**描述**：channel 作为新 EP 注册进 plugin_system；飞书作为首个 ExtImpl 通过 manifest 声明。

**用户故事**：作为架构，我希望新 IM 渠道通过「写一个 impl + manifest 声明」即可接入，不动核心代码——可扩展性与 provider 一致。

**功能交互细节**：
- `app/server/src/plugin/extension-point.ts` 的 `BUILTIN_EXTENSION_POINTS` 加 `{ id:'channel', cardinality:'list', description:'...' }`。
- `app/plugins/groups.json` 新增 group「渠道」（label/description/extPoints:['channel']），UI 入口据此渲染。
- `app/plugins/builtins/feishu/plugin.json` manifest：`{id:'feishu', extImpls:[{implId:'feishu', point:'channel', impl:'./feishu-channel.js', configSchema:{appId:string, appSecret:secretInput}}]}`。
- **configSchema 单一源**（plugin_system 不变量 8）：飞书 impl 的 `{appId, appSecret}` schema 驱动配置页表单渲染 + 校验 + default。
- 启动校验 registry ↔ groups.json 双向一致（plugin_system 不变量 D6 第 5 条）。

**约束**：channel EP 与 provider EP 同构，**禁止**引入 channel 专属的注册/解析机制（破坏 EP 单一抽象）。

### 2.2 ChannelManager + ChannelBase（EP 消费方 + 管家）[P0]

**描述**：新建 `app/server/src/channel/` 子系统——`ChannelBase`（EP 契约 TContract 抽象类，含 req 指定的 base 方法）+ `ChannelManager`（消费 EP + instance/binding/连接管家 + outbound 累积管线）+ `ChannelConfigService`（独立域 `channel_config`）+ `ChannelBindingStore`（双向唯一）。

**用户故事**：作为系统，channel 配置多实例（同一飞书可配多 token）独立 enabled/connect，每条绑定关系持久化、可恢复。

**功能交互细节**：
- `ChannelBase`（base 提供给 impl 调用）：`getBindedSession(conversationId)` / `deliverTo(sid,msg)` / `bind(conversationId,sid,by)` / `unbind(conversationId)` / `listPlaygroundSessions()` / `listStudioLeaders()`。
- impl 必须实现（Channel 接口，req 指定 5 个）：`connect()` / `disconnect()` / `onInboundMessage(raw)` / `onOutBoundMessage(msg)`（D3 收完整 Message）/ `onUpdateInputState(state)`。
- `ChannelManager`：`bootstrap(dataDir)` 扫 instance → 按 implId 取 impl 类 → new + connect；`getAllStates()` 供 GET；`subscribeOutbound(sid,channel)` / `unsubscribeOutbound(sid,channel)`（累积管线）。
- bootstrap 调用点：**agent_loop bus 就绪后**（`bootstrap.ts:328` 之后）调 `createAndBootstrapChannelManager(dataDir)`；`connect()` fire-and-forget 不阻塞启动（失败转 error 态）。
- **多 instance**：一个 feishu impl 可多份配置实例（多 token），每 instance 独立 enabled/connect。instance 多份配置的存储形态，架构期对照 **provider 多凭证池**机制落地。

**约束**：遵守 memory `runtime-no-ext-policy-write`——运行时不写/清 ext impl policy，只在配置面写。

### 2.3 数据结构 [P0]

- `ChannelInstance`：`{id:ulid, implId:'feishu', name, enabled, config:{appId, appSecret}, createdAt/updatedAt}` —— 持久化于 `{dataDir}/channel_config/<id>.json`（list 形态，每 instance 含 implId+config）。
- `ChannelBinding`：`{instanceId, conversationId, sessionId, boundBy:'slash'|'manual', boundAt}` —— 唯一键 `(instanceId, conversationId) → sessionId`（一对一，/bindp·/binds 覆盖）；**双向唯一**：sessionId 也唯一（D6，一个 session 只被一个 (instance,conv) 绑定，违反报错「该 session 已被绑定」）—— 持久化于 `{dataDir}/channel_bindings/<instanceId>__<conversationId>.json`。
- `ChannelState`（运行时派生，推前端）：`{id, implId, switch:'on'|'off', connection:'disconnected'|'connecting'|'connected'|'error', errorDetail?, lastConnectedAt?, bindingCount?}`。
- **MessageSender 扩展（D5）**：user 变体加可选 `channel?: {instanceId, conversationId, imUserId, imUserName}`。**不新建 source 类型**（channel=user 身份）。req 指定：若 message sender=user 且是本 channel 发送的，channel 侧自己过滤（不发回声）。

### 2.4 双状态机（复用 connector 同构，3 次×5s 重试） [P0]

**描述**：channel 复用 connector 双状态机模型——switch 持久化 + connection 运行时派生。

**用户故事**：作为用户，我在配置页打开 channel 开关后，系统自动尝试连接飞书（最多 3 次，每次失败等 5s）；状态实时反馈到 UI；关掉开关立即断开。

**功能交互细节**：
- `switch=on` → `connect()`，3 次 × 5s 间隔重试，仍失败 → `connection=error(errorDetail)`（不再自动重连，等 switch off→on 重置）。
- `switch=off` → `disconnect()` + `connection=disconnected`。
- **启动自动恢复**：bootstrap 对每个 `enabled=true` instance 执行 connect（fire-and-forget 不阻塞启动，失败转 error）。
- HTTP：`GET /config/channels` 返 ChannelState[]；`PUT /config/channels/:id {enabled}` 返 202（异步驱动 connect/disconnect）。

**约束**：3 次×5s 是 req 指定上限（不去 openclaw 指数退避无限重连——避免刷日志）。

### 2.5 配置页 UI（新「渠道」入口） [P0]

**描述**：在技能↔连接器之间插入新 nav 入口「渠道」（testid `nav-channel`，view id `'channel'`），仿 connector-page 模式新建 `app/web/src/components/channel-page/`。

**用户故事**：作为管理员，我打开「渠道」页新建一个飞书 instance，填 appId/appSecret（密钥用 secret-input mask），保存即默认 on 自动连接，列表轮询看到连接状态。

**功能交互细节**（对齐 nav-rail.md / app-shell.md / connector-page 模式）：
- **nav-rail 插入点**：NAV_BOTTOM 三入口之间——位置 `nav-skill` 与 `nav-connector` 之间插 `nav-channel`（tooltip「渠道」）。需同步更新 nav-rail 几何顺序断言 ET。
- **view-store**：`ViewId` 加 `|'channel'`；**app-shell** switch 加 `case 'channel' → <PageChannel/>`。
- **页面结构**：标题 + 描述 + 列表（名称/implId 类型/switch/connection+errorDetail/bindingCount/编辑删除）+「新建」→ **类型列表**（从 `getExtensionImpls('channel')` 来，当前只飞书 1 项）→ 填该 impl 的 configSchema 字段（飞书：appId 普通 input + **appSecret 用 `secret-input` 组件 mask**，v0.0.90 已有）→ 保存默认 enabled=true → 自动连接 → 5s 轮询 `GET /config/channels`。

- **i18n**：`nav.channel` / `channel.header.title` 等 key 加入双 locale（护栏 UT `groups-locale-coverage`）。
- **布局稳定性 MANDATORY**（沿用 §2.3）：编辑/删除按钮 hover 出现预留空间，禁止位移。

**约束**：复用 connector-page 同构模式（同 card / toggle / status dot / feedback 组件），不发明独立视觉系；类型列表数据源 = EP inventory（不硬编码「飞书」）。

### 2.6 IM 侧斜杠指令（拦截不进 agent，D1/D2） [P0]

**描述**：飞书用户在 IM 内发 `/` 前缀消息，channel 拦截处理不进 agent，回复结果到该 conversation。

**用户故事**：作为飞书用户，我在群里 @bot 发 `/listp` 看到 playground session 列表，`/bindp 3` 绑定第 3 个，之后我的消息就发给该 session。

**功能交互细节**：
- 入站先剥离 @bot mention（保留 `/` 前缀，openclaw 修复 #35994）。
- `text.startsWith('/')` → 拦截不进 agent，**命令跳过去抖**（openclaw `isControlCommandMessage`）。
- 指令集（D1/D2 已锁定）：
  - `/listp` → 列 playground sessions（`sessionStore.listSessions({biz:'playground'})`），格式 `"1 {title}\n2 {title}"`
  - `/lists` → 列 studio leaders（`sessionStore.listSessions({biz:'studio', role:'leader'})`，store 需加 role 过滤参数）
  - `/bindp N` → 绑 playground session N（listPlaygroundSessions 取第 N 个 → `base.bind(...)`；检查 sessionId 占用 D6 → `ChannelBindingStore.upsert` 覆盖 + `subscribeOutbound` 建累积管线 → 回飞书「已绑定到 {title}」）
  - `/binds N` → 绑 studio leader session N（同上，池换 listStudioLeaders）
  - `/unbind` → `base.unbind(conversationId)` → `ChannelBindingStore.delete` + `unsubscribeOutbound`（清累积管线防泄漏）→ 回「已解绑」
  - `/status` → `base.getBindedSession(conversationId)` → 回「当前绑定：{title}」或「未绑定」（可选）

### 2.7 inbound 链路（去重+去抖+顺序队列，飞书 at-least-once 重发） [P0]

**描述**：飞书 `im.message.receive_v1` 事件 → `FeishuChannel.onInboundMessage` → 三件套 → 解析 → deliverTo。

**功能交互细节**：
1. **去重**：`tryBeginProcessing(message_id)` 幂等（内存 LRU + TTL）。
2. **去抖**：per `conversationId` debounce timer，同对话连发短文本合并。
3. **顺序队列**：per `conversationId` 串行处理，保序。
4. 解析：`{conversationId=chatId(群)/openId(私聊), text, imUserId, imUserName}`。
5. `sessionId = base.getBindedSession(conversationId)`（未绑 → UC-G3 提示）。
6. 构造 `Message{role:'user', content:[{type:'text',text}], sender:{source:'user', channel:{...}}}`（D5 身份=user）。
7. `base.deliverTo(sid,msg)` = `agentManager.deliverTo` → 进 agent loop（同时进 bus，web 也看见 → 联动）。

### 2.8 outbound 累积（D3：channel 收完整 Message） [P0]

**描述**：ChannelManager subscribe `agent_loop` 该 sid → 累积 text delta → run_end 组装完整 Message → `channel.onOutBoundMessage(完整msg)` → channel 格式化发飞书。

**功能交互细节**：
- bind 时 `subscribeOutbound`：`agentManager.subscribe(sid,'current')` → `for await AgentEvent`。
- `message_start(role:assistant)` → 开 buffer；`text_block_delta/end` → 拼 delta；`tool_call_*` → **忽略**（工具过程不发飞书，D3）。
- **`run_end`** → 组装完整 assistant Message(content blocks) → channel 格式化（content→飞书文本/图片，超长按 markdown 边界分块 ~4000） → 清 buffer。
- **typing indicator**：`run_start` → `channel.onUpdateInputState('typing')`（飞书无原生 typing API，openclaw reaction emoji hack 或先 no-op）；`run_end` → `onUpdateInputState('idle')`。

### 2.9 客户端↔IM 联动（D5 对等 = 单源多消费） [P0]

**描述**：web 和 channel 共享同一个 agent_loop bus，inbound 双向可见，outbound 各收一份不重复发。

**用户故事**：作为同时在 web 和飞书使用同一 session 的用户，我在飞书发的消息 web 也看得见（标来源），agent 的回复两边都收到。

**功能交互细节**：
- inbound：deliverTo 进 bus 后，所有订阅者收到——web `SseChannel`（已有）订阅该 session → web 看到「飞书用户 X 说了 Y」（sender.channel 标来源）；ChannelManager 也订阅 → 但 channel 是发送方，识别 `source=self` 忽略（不发回声，req 指定 channel 侧过滤）。
- outbound：agent 产出 → bus → web `SseChannel` 收一份（web 展示）+ ChannelManager 收一份（发飞书）→ 各自渲染，web 不发飞书、飞书不发 web。
- **关键**：agent loop 单源，web 和 channel 都是消费者 → 天然联动，无额外同步代码（D5 对等的直接体现）。

### 2.10 解绑与清理（防泄漏） [P0]

- `/unbind` 或配置页手动解绑：`ChannelBindingStore.delete` + `ChannelManager.unsubscribeOutbound`。
- **session 删除**：钩子清孤儿 binding（`ChannelBindingStore` 清 `sessionId` 匹配项 + 对应 channel unsubscribe）。
- **instance 删除**：先 `disconnect` → `ChannelBindingStore.deleteByInstance(instanceId)` → `ChannelManager.unregister`。

| UC-G2 | agent busy 时飞书连发 | deliverTo 入队 + 去抖合并 |
| UC-G3 | 未绑定对话发消息 | 回飞书固定提示「未绑定，请先 /listp 或 /lists」 |

## 5. 边界 / 不做什么

**不做**（已锁定，避免范围蔓延）：
- ❌ 流式卡片（D3：累积到 run_end 发完整；流式 patch 卡片留未来增强）
- ❌ webhook 模式（D4：只 WS；去 encryptKey/verificationToken 整条）
- ❌ conversationId scope 自动路由（D2：去 openclaw group_sender/group_topic 编码，只显式绑定）
- ❌ 飞书用户↔系统用户映射（D1：信任模型先简化，/listp /lists 全给）
- ❌ outbound fan-out（D6：双向唯一简化）
- ❌ 指数退避无限重连（req：3 次×5s 上限）
- ❌ 本期不含微信/钉钉等其他 IM（飞书 only，但 EP 框架预留）

**范围红线**：本期只 channel（IM 接入）+ 飞书 impl；不碰 squad/角色/团队层；不重构 agent loop 本体。
