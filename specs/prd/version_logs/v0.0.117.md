## 2. 产品语义裁决（MANDATORY — 每点给建议方案，标注待确认）

### 2.1 摘要（description/detail）vs 正文（body）统一语义 [建议：采纳，全实体口径一致]

**裁决**：两个内容字段职责分工固定，**所有实体口径一致**：
- **摘要**（Goal=`description` / Requirement=`detail`）：一句话概括，**列表/卡片展示**用；控件=多行 `<textarea>`（2-3 行高）。
- **正文**（`body`，全实体统一命名）：长 markdown，详细说明；控件=`component-board-body-editor`（markdown 编辑器）；**列表不展示**（弹层/详情专属，合理）。

**编辑弹层布局**：摘要在上（紧接 title）、正文在下，二者并列并存（Goal 已按此实现，0f4ce6de）。KR/Task 无独立摘要字段（title 即概括），只有 body。

**命名不对称说明**：Goal 用 `description`、Requirement 用 `detail`——这是既有 store schema（`squad_store_projection.md §1.1/§1.2`），本版本**不重命名**（避免数据迁移），仅在产品语义上统一为「摘要」概念。

**待确认**：是否接受 Goal=description / Req=detail 的字段名不对称（产品语义统一即可，不改 schema）？建议接受。

### 2.2 KR.status 产品语义 [建议：保留独立状态 + 终态 UI 入口]

**问题**：KR 有独立 `status` 字段（store schema 有），但三方全不可达——UI 无入口、KrRow 不渲染、agent edit 白名单无 status、update_progress 不改 status。KR 恒 pending，无法标 done/cancelled（仅裸 HTTP PATCH 可改）。

**两方案**：
- **A（建议）保留独立状态**：KR.status 是真实状态（pending/in_progress/blocked/done/cancelled），与进度（current/target）正交。理由——KR 可能「进度 100% 但仍在验收」或「进度未满但已 cancelled（目标调整）」，进度派生无法表达终态。三方打通：UI 弹层加 status 下拉（含 done/cancelled 终态）+ KrRow 渲染 status badge；agent edit 白名单加 status + WorkStatus 状态机校验。
- B（不建议）纯进度派生：status 由 current/target 算（100%=done）。删 KR.status 字段。**问题**：无法表达 cancelled 终态、无法区分「达标待验收」与「已完成」；且要改 schema + 数据迁移，破坏 v0.0.60 已落的字段。

**裁决**：采纳 A。KR.status 保留为独立状态，补齐三方入口（含 done/cancelled 终态）。

**待确认**：是否同意保留 KR 独立 status（方案 A）？

### 2.3 status 编辑入口交互形态 [建议：编辑弹层下拉]

**裁决**：status 编辑入口统一走**编辑弹层内的下拉**（choice 卡 ≤4 / 自定义下拉），不引入卡片快捷操作/拖拽。理由——① 与既有弹层编辑范式一致（`component-board-entity-modal` 已是全字段编辑入口）；② 状态机跃迁需 reason（blocked/cancelled），弹层能容纳 reason 输入，卡片下拉无处填 reason；③ 拖拽换列改动大、易误触，本版本聚焦对齐不做重交互。

- Goal/Requirement/Task/KR 弹层均加 `status` 字段（下拉，选项按 WorkStatus 状态机当前态可跃迁项过滤 + blocked/cancelled 展开 reason 输入）。
- 后端 PATCH 端点已全支持 status（`board-write-*.ts`），前端补入口即可。

**待确认**：status 编辑仅走弹层下拉（不加卡片拖拽/快捷操作）——是否同意？

### 2.4 Requirement.triage 用户入口 [建议：弹层内 triage 决策区]

**问题**：triage 决策（accept/defer/reject/promote）目前仅 agent leader 工具可做，user 角色（HTTP 全写权）无 UI 入口。

**裁决**：Requirement 编辑弹层加 **triage 决策区**——一组 4 选项（接受/延后/驳回/晋升）+ reason 输入，仅 pending 状态可操作（与工具 `triage` 约束一致：仅 pending 可 triage）。promote（晋升为 Goal）交互较重，本版本 user 入口**仅支持 accept/defer/reject 三项**；promote 仍走 agent 或后续版本 UI 向导。

**待确认**：user triage 入口仅 accept/defer/reject（promote 留 agent/后续版本）——是否同意？

### 2.5 agent 读面策略 [建议：query 加 detail 参数，reminder 不注入长文本]

**问题**：UI 用户写的 body/detail/摘要，agent 经设计的读面（query + reminder）完全看不见（query 只返 title/status/health/进度；reminder 同样精简）。若全量注入长文本 → token 成本爆炸。

**裁决**：
- **query 加 `detail?: boolean` 参数**（默认 false，保持现状精简）：`detail=true` 时返长文本字段（goal.description/body + KR 明细 + req.detail/body/triage + task.priority/deadline/body/reason）。agent 按需拉取，非默认全返。
- **reminder 不变（不注入长文本）**：reminder 保持 title/status/health/进度精简，token 成本可控。agent 需长文本时主动调 `query(detail=true)`。这符合 `squad_reminder_providers.md` 「动态上下文按需，不膨胀」哲学。
- 取舍理由：detail 参数比新增 `get` action 更省 tool slot（复用 query 一个动作），与「filter 决定结果形态」既有模式一致。

**待确认**：query 加 detail 参数（而非新 get action）+ reminder 不注入长文本——是否同意？

## 6. 关键用户路径（MANDATORY — 测试最低覆盖要求）

> 每条路径至少一个 AT/ET case。「UI 通道」= ET；「agent 通道」= AT（真 LLM 调工具）；「双通道一致」= AT 对比。

- **路径1**：用户打开 Goal/Requirement 编辑弹层 → 看到摘要+正文并存且预填正确 → 改摘要 → 保存 → 列表摘要更新（所见即所得，S1-1/3.2）
- **路径2**：用户编辑弹层清空某字段（如 deadline/body）→ 保存 → 字段确实被清空（清空语义，3.4）
