## 1. 背景

现状：bash 工具 `runShell()` 直接 spawn 执行（`app/server/src/tools/bash.ts`），**零权限检查**——LLM 让删什么就删什么、让读什么就读什么。危险操作（`rm *` 通配删除）无人工确认关口；敏感目录（`~/.ssh`）无访问屏蔽；即便参数层拦得住，脚本里的间接危险操作（`bash -c 'cat ~/.ssh/id_rsa'`）也无兜底。

v0.0.101 已把 HITL 悬挂机制（pending 队列 / suspended 第六态 / SSE `require_human_input` / `tool_reply` 回填 / 同 id upsert 编辑占位）落地为 canonical，并**为 approval 分支预留了全链路留位**（`ToolHandleType='approval'`、`ToolInteraction.subType='need_approval'`、`ApprovalData`、`tool-reply-handler.ts` approval 分支存根、前端 `MessageSender.approval`）。本版本把这些留位**兑现实例化**，并新增策略层 + 执行层，形成完整的三层工具安全能力。

**抽象三层**（req.md 权威）：
1. **策略层**——执行前检查工具与参数，产出「直接通过 / 直接拒绝 / 请求审批」三态决策。
2. **审批层**——策略层判「请求审批」时，弹审批卡让用户选「同意 / 拒绝 / 永远同意」；决定回填后按选择补跑或拒绝。
3. **执行层**——即便前两层放行，实际执行仍在可信容器（seatbelt 沙箱）内，屏蔽脚本里的间接危险操作。

## 3. 功能需求

### 3.1 策略层 — bash checkPermission（两条策略）[v0.0.122.approval]

**描述**：bash 工具执行前，引擎调 `checkPermission` 检查命令，按内置策略列表产出 PermissionDecision。本版本 bash 挂两条策略。

**优先级**：P0

**用户故事**：作为用户，我希望 AI 执行 bash 时，危险的通配删除会先问我、访问我的私钥目录会被直接拒绝，以便我的机器不被 agent 误伤。

**功能交互细节**：

| 策略 | 命中条件 | 决策 | 用户可感知结果 |
|---|---|---|---|
| `ssh-read` | 命令文本引用 `~/.ssh` / `$HOME/.ssh` / `/Users/*/.ssh`（含 `ls`/`cat` 等任何形式） | **deny** + 理由「禁止访问 ~/.ssh 敏感目录」 | 不弹窗；bash 直接返回拒绝结果，LLM 收到理由可继续对话 |
| `rm-wildcard`（D1） | 命令名为 `rm` 且任一参数含字面 `*`（按 `;` `&&` `\|\|` `\|` 拆段取 token 判定） | **ask** + 理由「rm 通配删除，需用户批准」+ approvalKey=`bash:rm-wildcard` | 弹审批卡（§3.2），等用户决定 |

- **决策优先级**：deny 优先于 ask（同一命令若既命中 ssh-read 又命中 rm-wildcard，按 deny 处理）。
- **检测为 best-effort 参数级**（不做完整 shell AST 解析）；间接绕过由执行层（§3.4）兜底，两层有意重复（纵深防御）。
- **策略即列表可扩展**：未来加策略 = 往 bash 的策略列表加一条，不改引擎。
- **其他工具不受影响**：checkPermission 是可选钩子，未实现的工具视同 `allow`（现状行为不变）。

**验收标准**：`ls ~/.ssh` 类命令产出 isError 拒绝结果且不执行；`rm -rf *` 类命令触发审批卡；普通 bash（`ls`、`git status`）无任何额外关口。

### 3.2 审批层 — 审批卡 + 三选项回填 [v0.0.122.approval]

**描述**：策略层判 `ask` 且该 approvalKey 未被「永远同意」时，agent loop 悬挂（复用 v0.0.101 HITL），前端在 chat 输入区上方渲染审批卡；用户选「同意 / 拒绝 / 永远同意」后回填，按选择补跑或拒绝。

**优先级**：P0

**用户故事**：作为用户，当 AI 要执行危险 bash 时，我希望看到一张卡片清楚展示它要跑什么命令、为什么被拦，让我一键同意 / 拒绝 / 永远同意，而不是被动接受。

#### 用户行为链路

策略层 `ask` → 引擎查 ApprovalManager（该 key 是否已永远同意）→ 未同意则构造 `need_approval` pending 挂起 → SSE `require_human_input`（队首=该 pending）→ 前端 mount 审批卡 → 用户点三按钮之一 → `POST /messages` 带 `toolReply{handleType:'approval', payload:{decision}}` → 后端 pre-process 按 decision 编辑占位 block → 卡片 unmount → loop 续跑。

#### 审批卡界面要素（component-pending-approval-card）

- **挂载位置**：`chat-input-bar` 内、composer 上方（与提问卡 / enqueue-view 同位互斥）。`subState==='need_approval'` 时渲染（替换 v0.0.101 提问卡对 need_approval 的防御性 null）。
- **内容**：工具名 + 参数展示（bash 即 `command`，等宽字体展示）+ 拦截原因（reason）。
- **三按钮**：**同意**（allow）/ **拒绝**（deny）/ **永远同意**（allow_always）。
- **可见性门控**：`pendingToolCalls.length > 0`（非 `session.running`——suspended 排除 running，INV-2）；composer 提问态保持可用（INV-7），审批卡出现/消失不导致 composer 位移（布局稳定性：占位固定）。
- **recover**：切走切回 / 重启后 onInit 走 `GET /session/:id/pending-tool-call` peek 队首重渲染（复用 v0.0.101 d 路径）。

#### 三选项回填语义

| decision | 后端处理 | 用户可感知结果 |
|---|---|---|
| `allow` | pre-process 补跑原 `tool.run()`（经执行层沙箱），真实结果同 id upsert 编辑占位 block，status pending→success | 命令实际执行，结果回到对话 |
| `allow_always` | 同 allow + `ApprovalManager.recordAlways(sessionId, approvalKey)`（本会话内记住该 key） | 命令执行 + 本会话后续同类操作不再弹窗 |
| `deny` | 编辑占位为 isError 结果「用户拒绝执行：{reason}」，status pending→fail | 命令不执行，LLM 收到拒绝理由继续对话 |

**验收标准**：`rm *` 命中弹审批卡展示命令 + 原因；点同意 → 命令跑 + 结果回填；点拒绝 → isError 回填 LLM 继续；点永远同意 → 本会话内再次同类操作不弹窗直接执行。

### 3.3 永远同意 — 会话内记忆（D2）[v0.0.122.approval]

**描述**：ApprovalManager 记录「本会话内被选了永远同意的 approvalKey 集合」。同一会话内，命中同一 approvalKey 的操作免弹窗直接放行；新会话 / 重启后失效重新弹。

**优先级**：P0

**用户故事**：作为用户，我在一次会话里对某类危险操作点了「永远同意」后，希望这次会话里同类操作不再反复打扰我，但换个会话仍会重新问我，避免永久授权的风险。

**功能交互细节**：
- **按 approvalKey 记忆**（req：被拦截原因一致才免弹）：approvalKey = `{toolName}:{policyId}`（如 `bash:rm-wildcard`）。会话内命中同一 key → 策略层 `ask` 被 ApprovalManager 短路为 `allow`，不再挂起。
- **仅会话内记忆（D2）**：内存 Map（sessionId → Set&lt;approvalKey&gt;），**不落盘、不进 CrudStore**；重启 / 新会话重新弹。未来若要全局持久化再演进（不预建 store）。

**验收标准**：会话 A 内对 `bash:rm-wildcard` 点永远同意后，A 内再 `rm *xx` 不弹窗直接执行；另建会话 B 执行 `rm *` 仍弹审批卡。

### 3.4 执行层 — SecureBashEngine + seatbelt 沙箱（D3）[v0.0.122.approval]

**描述**：bash 实际执行收编进 `SecureBashEngine`，在 macOS seatbelt 沙箱内执行，屏蔽脚本里对敏感路径的间接访问（参数层漏网的兜底）。挂/改安全策略 = 改 engine 的 policy 挂载，bash tool 代码零改动。

**优先级**：P0

**用户故事**：作为用户，即便 AI 用脚本间接绕过参数检查去读我的私钥（`bash -c 'cat ~/.ssh/id_rsa'`），我希望系统级沙箱把它拦下来让命令失败，而不是让私钥泄漏。

**功能交互细节**：
- **抽象**：`BashEngine.exec(command, opts)` 提供 bash 执行能力，bash tool 只引用它；现有 `runShell()` 收编为 engine 实现细节。`BashSecurityPolicy` 声明式（`id` / `description` / `denyRead[]` / `denyWrite[]`），每次可加一条，命中即失败。本版本挂一条：`{id:'ssh-read-block', denyRead:['~/.ssh']}`（engine 负责把 `~` 展开为绝对路径）。
- **macOS 实现（D3）**：policies 编译成 seatbelt profile 字符串（`(allow default)` + 逐条 `deny`，黑名单制），经 `sandbox-exec -p <profile> <shell> -c <command>` 执行——系统自带二进制、profile 内联传参不写文件（兼容 packaged cwd=`/` 护栏、零新 npm 依赖）。
- **命中表现**：进程内读 `~/.ssh` 得 EPERM（Operation not permitted）→ 非零退出码 → bash 返回 isError（「返回失败」）。
- **非 darwin**：passthrough 普通执行（req：只考虑 mac）。超时 / abort / 输出截断语义与现 `runShell` 完全一致（`bash_tools.md §2` 不破）。

**验收标准**：seatbelt 可用平台上，`bash -c 'cat ~/.ssh/id_rsa'` 类间接读被 OS 拦截、命令非零退出返 isError；普通 bash 命令行为不变（输出 / 超时 / 后台一致）。

## 4. 关键用户路径（MANDATORY）

> **用户路径 = 测试最低覆盖要求**。以下 6 条以 design.md §5 为基础，每条给出链路 + 关键断言。本版本测试方案随 v0.0.120 测试框架重构后另定。

- **路径1（rm 同意）**：bash `rm *` → 策略层 ask → 审批卡（command + 原因）→ 点同意 → pre-process 补跑 tool.run（经沙箱）→ 真实结果同 id upsert 回填 → LLM 续跑。**断言**：审批卡渲染 command/reason；同意后 result block status pending→success 且含真实执行输出。
- **路径2（rm 拒绝）**：同上 → 点拒绝 → 占位编辑为 isError「用户拒绝执行：{reason}」→ LLM 收到继续对话。**断言**：result block status→fail、isError=true、命令未执行。
- **路径3（永远同意）**：同上 → 点永远同意 → ApprovalManager.recordAlways(sid, `bash:rm-wildcard`) → 本会话内再 `rm *xx` 命中同 key → 不挂起直接执行；新会话执行 `rm *` 仍弹。**断言**：第二次无 require_human_input 事件、直接产 success result；新会话仍产 pending。
- **路径4（ssh 直接 deny）**：bash `ls ~/.ssh` → 策略层 deny → 不挂起 → bash 产 isError 拒绝结果（含理由）→ LLM 可见。**断言**：无 require_human_input；result isError=true 含「禁止访问 ~/.ssh」。
- **路径5（间接读被沙箱拦）**：bash `bash -c 'cat ~/.ssh/id_rsa'`（参数层漏网）→ 执行层 seatbelt 拦截 → EPERM 非零退出 → isError。**断言**：命令非零退出、result isError=true（seatbelt 可用平台）。
- **路径6（审批挂起重启恢复）**：审批卡挂起时重启 app → reconcileOnStartup 保留 suspended + pendingToolCalls 落盘一致 → 切回 session 前端 GET /pending-tool-call peek 重渲染审批卡。**断言**：重启后 session.state=suspended；审批卡仍在、可继续决定（复用 v0.0.101 落盘回归）。

## 5. 范围与非目标

- ✅ **仅 bash 工具**接 checkPermission；其他工具不动（钩子可选，未实现=allow）。
- ✅ 兑现 v0.0.101 approval 留位（handleType='approval' / subType='need_approval' / ApprovalData）；HTTP 端点零新增（复用 POST /messages toolReply + GET /pending-tool-call + SSE require_human_input）。
- ❌ **不做规则配置 UI / settings 持久化规则**（claude-code 的 Tool(content) 规则库不在本版本；策略在代码内列表）。
- ❌ **不做规则持久化**（D2：永远同意仅内存会话内记忆，不落盘）。
- ❌ **不做 denyWrite 场景 / 网络隔离**（类型保留 `denyWrite` 字段，不挂策略）。
- ❌ **不做 EP 插件化策略挂载**（策略在代码内列表；未来需要再抽 EP）。
- ❌ **不对接 LSM / EndpointSecurity**（D3 已裁决用 sandbox-exec + seatbelt）。
