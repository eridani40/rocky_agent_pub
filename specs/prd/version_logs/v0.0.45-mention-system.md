# v0.0.45 PRD Change Log — @ Mention 系统（playground / studio / squad）

> version: 1.0 · 2026-07-15
> 一句话定位：三处输入区（playground / studio 单聊 / squad 群聊）统一接入 @ mention 系统——输入 `@` 唤起多 tab 搜索面板，选中结果插入 mention pill，消息以结构化 content 数组落库，LLM 收到 `<mention>` payload。
> 概念权威源：`specs/tech/` 需新增 mention 子系统（architect 落地）；`specs/ui/components/` 需新增 ChatComposer / MentionPopover / MentionPill 组件 spec（coder 前置落地）。
> 设计稿：无（本版本无视觉契约设计稿，视觉保真度门禁跳过）。

---

## 1. 背景与目标

### 1.1 背景

用户需要在对话中快速引用文件路径、skill 等上下文信息。当前三处输入区（playground `SectionChatDetail` / studio 单聊 `SectionMemberChat` / squad 群聊 `SectionSquadChat`）各自独立实现 `<textarea>` + `useState('')`，无 mention 能力、无共享 composer 组件。

### 1.2 目标

1. **统一输入区**：三处输入区迁移到共享 `ChatComposer` 组件，消除三份重复实现。
2. **@ mention 交互**：输入 `@` 唤起多 tab 搜索面板（文件 / skill），选中结果插入 mention pill。
3. **结构化消息**：消息 content 从纯 string 升级为结构化数组（text + mention 节点），pill 在会话区保持形态，LLM 收到语义化 payload。
4. **搜索范围正确**：不同会话类型（playground / studio leader / mate / squad）看到合理的文件范围和 skill 集合。

## 4. 功能需求

### 4.1 UI 层：共享 ChatComposer + MentionPopover [v0.0.45]

> **新概念，需同步落到 `specs/ui/components/`**：`ChatComposer`（共享输入组件）、`MentionPopover`（多 tab 搜索浮层）、`MentionPill`（内联 mention 节点）。coder 在编码前置阶段建组件 spec。

**描述**：三处输入区统一迁移到 `ChatComposer` 组件，取代各自的 `<textarea>` + `useState('')`。ChatComposer 内部包含 pill-aware 编辑器 + MentionPopover 浮层。

**优先级**：P0

**用户故事**：作为用户，我希望在三处对话入口都有一致的输入体验，能通过 `@` 快速引用文件和 skill。

**期望行为**：
- **ChatComposer props**：各场景传 `bizType` / `sessionType` / `sessionId` / `enabledProviders: string[]` / `onSend: (content: MessageContent[]) => void` 定制。
- **@ 触发**：用户在编辑器中输入 `@` 字符 → 弹出 MentionPopover。
- **MentionPopover 布局**：`tab1|tab2|...| search input` 顶栏 + 滚动结果列表。固定尺寸，结果过多时向下滚动，每次加载 20 条（分页 cursor）。
- **focus 管理**：唤起后 focus 在 mention search input；`Esc` 收起并恢复 focus 到主输入区；focus 失焦也收起。
- **选中行为**：用户选择结果（鼠标点击或回车）→ 关闭面板 → 将 `@...` 替换为 mention pill。
- **pill 显示**：默认以 `@` 开头（如 `@drama-script-writer`），视觉区分于普通文本。
- **pill 删除**：pill 后直接按 Backspace → 整颗 pill 删除（不逐字符删除）。
- **布局稳定性**：MentionPopover 用绝对定位浮层，不占常规流空间；pill 的出现/消失不导致其他元素位移。

**editor 能力要求**（不绑具体库，architect 评估选型）：
- 支持内联 pill 节点渲染（非纯文本）
- pill 节点作为原子单元（不可部分编辑，整颗删除）
- `@` 字符触发检测 + 键盘导航（上下箭头 + Enter + Esc）
- focus 管理（主输入区 ↔ mention search input 切换）

**E2E Use Cases**

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-M1 | playground 输入 `@` → 切 Skills tab → 搜索 → 选中 → pill 插入 → 发送 | 会话区显示 skill pill；LLM 收到 `<mention>` payload |
| UC-M2 | playground 输入 `@` → Files tab → 搜索文件名 → 选中 → pill 插入 → 发送 | 会话区显示 file pill |
| UC-M6 | 唤起 MentionPopover → 按 Esc | 面板收起 + focus 回到主输入区 |
| UC-M7 | pill 后按 Backspace | 整颗 pill 删除 |

### 4.2 API 层：mention search 端点 [v0.0.45]

> **新概念，需同步落到 `specs/api/`**：`GET /mention/search` 端点。architect 在 API 文档阶段落地。

**描述**：统一的 mention 搜索 API，前端传 provider 类型 + query + 会话上下文，server 路由到对应 provider 执行搜索。

**优先级**：P0

**端点**：`GET /mention/search?provider=file|skill&query=...&sessionId=...&limit=20&cursor=...`

**响应结构**：
```
{
  items: Array<{
    type: string;         // 'file' | 'skill'
    id: string;           // 唯一标识（文件路径 / skill name）
    label: string;        // 显示文本
    payload: string;      // 给 LLM 的内容
    description?: string; // 可选描述行
  }>;
  nextCursor?: string;    // 分页游标，无则到底
}
```

**E2E Use Cases**

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-M9 | `GET /mention/search?provider=file&query=foo&sessionId=xxx&limit=20` | 返回匹配文件列表，items[].type='file' |
| UC-M10 | `GET /mention/search?provider=skill&query=drama&sessionId=xxx&limit=20` | 返回匹配 skill 列表，items[].type='skill' |

### 4.3 Provider 层：MentionProviderRegistry [v0.0.45]

> **新概念，需同步落到 `specs/tech/`**：`MentionProviderRegistry`（轻量 Registry）、`MentionProvider` 接口、`FileProvider`、`SkillProvider`。architect 落地。

**描述**：server-side 轻量 Registry，内置 `FileProvider` + `SkillProvider`，不挂 plugin EP。单一 `search(ctx: SearchCtx)` 接口。

**优先级**：P0

**SearchCtx 结构**：
```
type SearchCtx = {
  query: string; limit: number; cursor?: string;
  bizType: BizType; sessionType: SessionType; sessionId: string;
  workspaceDir: string;
  memberId?: string; squadId?: string; parentSessionId?: string;
};
```

**FileProvider 搜索范围**（server 按 bizType/sessionType 解析 workspaceDir）：

| bizType | sessionType | workspaceDir 来源 |
|---|---|---|
| playground | rocky | session.workspaceDir |
| playground | subagent | 继承 parent |
| studio | leader | teamWorkspaceDir |
| studio | mate | member.workspaceDir |
| studio | squad | teamWorkspaceDir |
| studio | subagent | 继承 parent |

**SkillProvider 搜索范围**：按 bizType/sessionType 决定可见 skill 集合（不同会话看到合理的 skill 列表，architect 敲定具体过滤规则）。

### 4.4 消息 content 结构化 [v0.0.45]

> **新概念，需同步落到 `specs/tech/` + `specs/api/`**：`MessageContent` 数组类型。architect 落地。

**描述**：`POST /session/:id/messages` body 从 `{ content: string }` 升级为 `{ content: MessageContent[] }`，支持 text + mention 混合节点。兼容旧 string 形式（server 端归一化为单 text 节点数组）。

**优先级**：P0

**MessageContent 类型**：
```
type MessageContent = Array<
  | { kind: 'text'; text: string }
  | { kind: 'mention'; type: string; id: string;
      label: string;    // 显示：@drama-script-writer
      payload: string } // 给 LLM：<mention type=skill path="...">...</mention>
>;
```

**行为**：
- server 落库存结构化数组。
- 回放时前端按 `kind === 'mention'` 渲染 pill。
- 给 LLM 前 server 拼接：`content[].kind === 'mention' ? payload : text`。
- 兼容：`{ content: "plain string" }` → server 归一化为 `[{ kind: 'text', text: "plain string" }]`。

**E2E Use Cases**

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-M8 | 发送含 pill 消息 → 重新打开会话 → `GET /messages` | 返回 content 数组含 mention 节点；前端渲染 pill |
| UC-M11 | `POST /messages` body `{ content: "plain text" }` | server 归一化为 `[{kind:'text', text:'plain text'}]`，正常处理 |

### 4.5 全局 type 提取 + 新增值 [v0.0.45]

> **新概念，需同步落到 `specs/tech/`**：`BizType` / `SessionType` alias 提取。architect 落地。

**描述**：提取全局 type alias，新增 `'rocky'` session type，顺手收敛内联 union。

**优先级**：P0

**类型定义**：

## 5. 非目标（本版本明确不做）

| 排除项 | 理由 |
|---|---|
| `/` `#` 触发字符 | 仅做 `@`，其他触发字符后续版本按需扩展 |
| `.gitignore` 默认开启 | 走 dev config 开关，默认关；file provider 仅排除 `node_modules` + `.git` |
| 扩展 plugin system 到前端 | mention provider 走轻量 Registry，不挂 plugin EP |
| 第三方 mention provider 贡献机制 / manifest | 内置 FileProvider + SkillProvider 足够，扩展机制后续按需设计 |
| mention 渲染的 markdown 嵌套 | pill 是原子节点，内部不做 markdown 渲染 |

## 6. 风险与假设

### 6.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| editor 升级（textarea → contenteditable / rich text lib）bundle size 增大 | 首屏加载变慢 | architect 评估选型时权衡 bundle size vs 功能需求；优先考虑轻量方案 |
| 大 workspace 文件搜索性能（>10000 文件） | 搜索延迟高 | FileProvider 采用流式搜索 + limit/cursor 分页；不做全量索引 |
| 三处输入区迁移到共享 ChatComposer 的回归风险 | 原有发送/IME/快捷键行为可能回归 | 逐场景迁移 + 回归测试覆盖原有行为（Enter 发送 / Shift+Enter 换行 / IME guard） |

### 6.2 假设

1. 现有消息存储 schema 可扩展为结构化 content 数组（不需要 schema migration 或仅需轻量兼容）。
2. 三处输入区的发送逻辑差异（playground 走 prop 回调 / studio 直调 postMessage）可在 ChatComposer 的 `onSend` prop 统一收敛。
3. skill 数量预期小（数十个），SkillProvider 全量枚举 + 模糊匹配足够。
