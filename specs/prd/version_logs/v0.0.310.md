# v0.0.310 — send_message 信封化

> 2026-08-09 | PRD

## 1. 背景与目标

### 1.1 现状

当 agent 调用 `send_message` 工具向其他 agent 发消息时，UI 上和 read/write/bash 一样显示为常规工具调用 block（`component-tool-call-item`，可折叠参数+结果卡）。它混在一堆文件操作/搜索工具中间，视觉上无法区分，用户感知不到「agent 正在发消息」。

与此同时，接收方已有独立的**信封消息**展示（`component-a2a-envelope`）——信封 icon + `from {senderName}` + 可展开看正文，语义清晰。

### 1.2 目标

把 send_message 的 tool_use block **从工具调用序列里摘出来**，不再当工具渲染，提升为独立信封消息，与已有的 a2a inbox 信封视觉统一。形成完整的 in/out 对称信封体验：
- **in**（已有）：收到的 a2a 消息 — 信封 + ↙ + `from {senderName}`
- **out**（新增）：发出的 send_message — 信封 + ↗ + `to {targetName}`

### 1.3 范围

- **仅 Studio**（群聊 + member 单聊）。Playground 不变。
- **仅 send_message 工具**（`b.name === 'send_message'` 的 tool_call block）。其他工具不变。

## 1.5 全场景信封覆盖矩阵 [v0.0.310]

### 1.5.1 代码验证结论

grep 后端源码确认：

1. **所有 a2a 入站消息统一走 `sender.source === "agent"` + `sender.agent.ref`\*\*（`send-message-tool.ts` L118-126 构造 + `subagent-reply-fallback.ts` L113-123 系统代发 + `inbox-enrich.ts` 反查补全 type/name）。无论 leader→mate / mate→mate / subagent→parent，进 inbox 后 **`isA2aInbox(msg) = true`\*\*，UI 侧已有 in 信封全覆盖，**无遗漏**。

2. **send_message 是唯一 agent 间通信工具**（grep `app/server/src/tools` + `app/server/src/agent/tools`）。无 reply / forward / broadcast 等变体。subagent 回报靠两种途径：①LLM 自觉调 send_message（prompt 层约定）；②系统兜底代发（`subagent-reply-fallback.ts`，也走 sender.source="agent"）。两者 UI 侧都是 in 信封。

3. **ref.type 枚举**（`mapSessionTypeToAgentRefType`）：`leader` / `mate` / `squad` / `subagent` / `rocky`。UI 侧 `isA2aInbox` 不区分 type，统一渲染 in 信封。

### 1.5.2 场景覆盖矩阵

**in 方向（已有，无需改动，确认全覆盖）**：

| 场景 | 方向 | from 显示 | ref.type | 数据来源 | 当前状态 |
|------|------|----------|----------|---------|---------|
| mate 收到 leader 消息 | in | from {leader名} | leader | send_message → deliverTo → inbox | ✅ 已有 in 信封 |
| leader 收到 mate 消息 | in | from {mate名} | mate | send_message → deliverTo → inbox | ✅ 已有 in 信封 |
| mate A 收到 mate B 消息 | in | from {mateB名} | mate | send_message → deliverTo → inbox | ✅ 已有 in 信封 |
| parent 收到 subagent 回报（LLM 主动） | in | from {subagent名} | subagent | send_message → deliverTo → inbox | ✅ 已有 in 信封 |
| parent 收到 subagent 回报（系统兜底代发） | in | from {subagent名} | subagent | subagent-reply-fallback → deliverTo → inbox | ✅ 已有 in 信封 |
| leader/squad 收到任意 mate 消息 | in | from {mate名} | mate | send_message → deliverTo → inbox | ✅ 已有 in 信封 |

> **in 方向结论**：所有 `sender.source === "agent"` 的消息已被 `isA2aInbox(msg)` 统一兜底，现有 in 信封覆盖无遗漏。v0.0.310 对 in 方向零改动。

**out 方向（v0.0.310 新增）**：

| 场景 | 方向 | to 显示 | 触发方式 | target arguments 形态 | 备注 |
|------|------|--------|---------|---------------------|------|
| leader 发消息给 mate | out | to {mate名} | send_message | `{type:"mate", sessionId, name}` 或 member name 字符串 | 群聊/单聊均可见 |
| mate 发消息给 leader | out | to {leader名} | send_message | `{type:"leader", sessionId, name}` 或 `"leader"` 别名 | 群聊/单聊均可见 |
| mate A 发消息给 mate B | out | to {mateB名} | send_message | `{type:"mate", sessionId, name}` 或 member name 字符串 | 群聊/单聊均可见 |
| subagent 发消息给 parent | out | to parent | send_message | `"parent"` 别名字符串 | **Playground 场景** |
| mate 发消息到群聊 | out | to SquadChat | send_message | `"squadchat"` 别名 | 群聊可见 |

### 1.5.3 targetName 解析（out 信封）

send_message 的 `arguments.target` 有多种形态（`send-message-tool.ts` inputSchema + `resolveAgentRefWithSquad`）：

| target 形态 | 示例 | targetName 显示 |
|------------|------|----------------|
| AgentRef 对象 | `{type:"mate", sessionId:"01JZ...", name:"coder"}` | `name` 字段值（如 `coder`） |
| sessionId 字符串 | `"01JZA6D535N86AM008T34N1B82"` | 查 chrome.members 匹配 sessionId → member name；兜底显示 sessionId 前 8 位 |
| `"parent"` 别名 | `"parent"` | 显示 `parent` |
| `"leader"` 别名 | `"leader"` | 查 chrome.members 找 role=leader → name；兜底 `leader` |
| member name 别名 | `"coder"` | 直接用该字符串 |

> **解析策略**（UI 侧纯展示）：优先取 `target.name`（AgentRef 对象自带）；无 name 时查 `chrome.members` 按 sessionId/name/role 匹配取 member.name；都取不到时显示原始 target 字符串。架构阶段确定具体实现。

### 1.5.4 Playground 的 subagent send_message

Playground 中 agent spawn 了 subagent，subagent 调 send_message("parent") 向 parent 发消息。当前显示为 tool-call-item。

用户明确「Playground 不变」。但 subagent→parent 的 send_message 在 Playground 里**仍然是 out 信封语义**。

**裁决**：v0.0.310 send_message 信封化是 **flatten 层全局拦截**（不区分 Studio/Playground）。理由：
1. send_message 在任何场景都是 agent 间通信，信封比 tool-call-item 更准确
2. 用户说「Playground 不变」指的是 **a2a inbox 信封不在 Playground 显示**（in 方向），不是指 send_message 的渲染方式不能改
3. 全局拦截实现最简单，无需视图层条件分支

> **架构阶段确认**：如果 leader 裁决 Playground 也保持 tool-call-item，则 flatten 层需条件拦截（Studio 用新 kind，Playground 保留 tool-call-item）。PRD 默认全局拦截。

## 3. 功能设计

### 3.1 send_message 信封（out 方向）[v0.0.310]

**描述**：agent 调用 send_message 时，该 tool_call block 不再渲染为 `component-tool-call-item`，而是渲染为独立的信封消息。

**优先级**：P0

**用户故事**：作为 squad 成员，当 agent 向另一个 agent 发消息时，我希望能在消息流中一眼看到「agent 发了一条消息给 XXX」，而不是把它混在工具调用里，以便追踪 agent 间的通信。

#### 3.1.1 方向标识

- **out**（send_message 发出）：信封 icon + **↗ 箭头** + `to {targetName}`
- **in**（a2a inbox 收到，已有）：信封 icon + **↙ 箭头** + `from {senderName}`

方向箭头是 in/out 的核心视觉区分。两个方向复用同一个信封组件，通过 `direction` prop 区分。

#### 3.1.2 targetName 取值

send_message 的 tool_call `arguments` 含 `target` 字段（目标 agent 的 sessionId 或 name）。`to` 后显示的名字优先取 target 对应的 member name，兜底显示 target 原始值。

> **数据源**：tool_call.arguments.target（send_message 工具定义的参数）。架构阶段确定具体取 arguments 的哪个字段（target / sessionId / name 等）以及 member name 解析方式。

#### 3.1.3 信封交互（复用现有 a2a 信封）

- **收起态（默认）**：信封 icon + 方向箭头 + `to {targetName}` / `from {senderName}`，不显示正文
- **点击展开**：展开灰色气泡正文（`PrimitiveBubble variant='a2a'`），正文为 tool_result.content 的文本
- **再点击收起**：回到收起态
- 本地 state 控制（`useState<boolean>`），同现有 a2a 信封

---

### 3.2 工具状态设计（核心）[v0.0.310]

send_message 作为一个工具调用，有多个执行状态。摘出来变信封时，**每个状态必须有明确的信封展示**，不能只设计 done 态。

#### 状态判定逻辑

信封状态派生自 tool_call 的 `result` 绑定情况（同 `component-tool-call-item` 的 `statusOf` 逻辑）：

| 状态 | 判定条件 | 信封展示 |
|------|---------|---------|
| **pending** | `result === undefined` 且 runActive=false（tool_use block 已出现在消息中，但 tool_result 尚未到达） | 信封 + ↗ + `to {targetName}` + 灰色 muted 文字「待发送...」 |
| **running** | `result === undefined` 且 runActive=true（run 进行中，send_message 正在执行） | 信封 + ↗ + `to {targetName}` + 灰色 muted 文字「发送中...」 |
| **done** | `result !== undefined` 且 `result.isError === false` | 完整信封（收起/展开），展开后正文 = tool_result.content 文本 |
| **error** | `result !== undefined` 且 `result.isError === true` | 信封 + ↗ + `to {targetName}` + danger 色「发送失败」标签；展开后显示 error content |

#### 各状态视觉细节

**pending 态**：
- 收起态行：`[信封icon] ↗ to {targetName}` + 右侧 muted 文字「待发送...」
- 不可展开（无正文）
- 视觉同收起态，额外加状态提示

**running 态**：
- 收起态行：`[信封icon] ↗ to {targetName}` + 右侧 muted 文字「发送中...」
- 不可展开（无正文）
- 「发送中...」可用 muted 色 + 轻微 pulse 动画（可选，架构阶段定）

**done 态**：
- 完整信封交互（收起/展开），同 §3.1.3
- 收起态：`[信封icon] ↗ to {targetName}`
- 展开态：信封打开 icon + `to {targetName}` + 灰色气泡正文
- 正文从 `tool_result.content` 的 text block 取（可能有多个 text block，拼接渲染）

**error 态**：
- 收起态行：`[信封icon] ↗ to {targetName}` + danger 色「发送失败」标签（`text-[var(--danger)]` 小字 pill）
- 可展开：展开后显示 error content（tool_result.content 文本，danger 色渲染）
- 视觉区分：error 标签用 danger 色，让用户一眼看到失败

#### 状态流转

```
pending → running → done
                  → error
```

pending 和 running 的区别仅在于 runActive 上下文（run 是否进行中）。在冷读 seed（非 running）时，无 result 的 send_message 显示「待发送...」（pending）；在 live SSE running 时显示「发送中...」（running）。实际两者都是「tool_result 尚未到达」的中间态。

> **架构阶段需确定**：pending/running 是否合并为一个「sending」态（简化实现）。PRD 倾向合并为一个中间态「发送中...」，因为用户视角 pending 和 running 无实质区别（都是「还没发完」）。

### 3.3 组件扩展：component-a2a-envelope → 支持双向 [v0.0.310]

现有 `component-a2a-envelope` 只支持 in 方向（固定 from）。扩展为支持 in/out 双向：

#### Props 扩展

```ts
interface A2aEnvelopeProps {
  /** 正文内容（done 态展开后渲染） */
  children?: ReactNode;
  /** 对端名称（in=senderName, out=targetName） */
  senderName: string;  // 保持字段名不变，语义为「对端名字」
  /** 方向：in=收到（↙ from）, out=发出（↗ to）[v0.0.310 新增] */
  direction?: 'in' | 'out';  // 默认 'in'（零回归，现有 a2a 信封不传 = in）
  /** 发送状态 [v0.0.310 新增，out 专用] */
  status?: 'sending' | 'done' | 'error';
  /** error 正文 [v0.0.310 新增，status=error 时展开显示] */
  errorContent?: ReactNode;
}
```

#### 渲染逻辑

| direction | status | 收起态 | 展开 |
|-----------|--------|--------|------|
| in | （无 status） | 信封 + ↙ + `from {senderName}` | 正文（现有行为，零回归） |
| out | sending | 信封 + ↗ + `to {senderName}` + 「发送中...」 | 不可展开（无正文） |
| out | done | 信封 + ↗ + `to {senderName}` | 正文（tool_result content） |
| out | error | 信封 + ↗ + `to {senderName}` + danger「发送失败」 | error content |

#### 方向箭头

- ↙（in）：指向左下，表示「从外部收进来」
- ↗（out）：指向右上，表示「向外部发出去」
- 用文字字符 `↙` / `↗`（mono 字体，与 senderName 同级），不引入新 SVG（简化实现）

#### 零回归保证

- `direction` 默认 `'in'`：现有 a2a inbox 信封装配（`component-message-stream.tsx` 的 `isA2aInbox` 分支）不传 direction = 行为 100% 不变
- `status` 默认 `undefined`：不传 = in 方向无 status 逻辑，走现有收起/展开路径

### 3.4 flatten 层改造 [v0.0.310]

`message-flatten.ts` 的 `flattenMessages()` 目前对 assistant 消息的 `tool_call` block 统一产出 `tool-call-item`。v0.0.310 需在产出前判定：

```
if (b.type === 'tool_call') {
  if (b.name === 'send_message') {
    → 产出新 kind 'send-message-envelope'（不进 tool-call-item，不参与 batch 合并）
  } else {
    → 产出 'tool-call-item'（现有行为不变）
  }
}
```

新 view-element kind：
```ts
| {
    kind: 'send-message-envelope';
    key: string;
    messageId: string;
    toolCallId: string;
    arguments: Record<string, unknown>;  // 含 target 等
    result?: { content: ToolResultContentBlock[]; isError: boolean };  // 同 tool-call-item 的 result 绑定
  }
```

**tool-batch 影响**：send_message 信封不再是 `tool-call-item`，`groupToolBatches()` 天然跳过它（只合并连续的 tool-call-item）。如果 send_message 前后有其他工具调用，batch 会在 send_message 处断开——这是正确行为（信封是独立消息，不应和工具调用混在一起）。

### 3.5 渲染层改造 [v0.0.310]

`build-render-rows.ts` 需新增 `send-message-envelope` row 类型（与 agent-answer / user-text 同级，不进 tool-batch）。

`component-message-stream.tsx` 渲染分支新增：
```
if (row.type === 'send-message-envelope') {
  → 渲染 <ComponentA2aEnvelope direction="out" senderName={targetName} status={...}>
      {正文}
    </ComponentA2aEnvelope>
}
```

out 信封归 **assistant 侧左列**（与 in 信封同一列），使用 agent 头像列。

## 4. 关键用户路径

| 步骤 | 用户操作 | 预期结果 |
|------|---------|---------|

| 步骤 | 用户操作 | 预期结果 |

## 6. 视觉规范

### 6.1 信封样式（复用现有 + 扩展）

- **收起态**：`inline-flex items-center gap-1.5`，信封 SVG icon（`w-4 h-4 text-muted`）+ 方向箭头（↗/↙ mono `text-muted`）+ 名称（`text-xs text-muted font-mono`）
- **展开态**：同收起态 header（icon 换打开态）+ `PrimitiveBubble variant='a2a'`（灰色气泡）
- **hover**：`text-fg-2` 过渡（同现有）
- **配色**：全 token（`text-muted` / `bg-muted/40` / `border-border` / `text-[var(--danger)]`），零字面 hex

### 6.2 方向箭头

- ↗ out：`text-muted`，mono 字体，信封 icon 右侧、名称左侧
- ↙ in：`text-muted`，mono 字体，同位置
- 字符：`↗`（U+2197）/ `↙`（U+2199）

### 6.3 状态标签

- 「发送中...」：`text-[11px] text-muted font-mono`，名称右侧
- 「发送失败」：`text-[9px] font-bold font-mono uppercase px-1.5 py-0.5 rounded-full bg-[var(--danger-bg)] text-[var(--danger)] tracking-wider`（同 tool-call-item error pill 风格）

### 6.4 布局稳定性

信封状态变化（sending → done）不导致其他元素位移。状态文字出现/消失通过同一行内 inline 渲染，不改变行高。

1. **Playground 零影响**：Playground 的 send_message 仍走 tool-call-item 渲染（Playground 不传 group/member 渲染策略，但 flatten 层的 send_message 拦截是全局的——**架构阶段需确定**：是 flatten 层全局拦截 send_message，还是仅 Studio 视图拦截。PRD 倾向全局拦截，因为 Playground 里 send_message 同样应该展示为信封更清晰；但用户明确说「Playground 不变」，所以架构需确保 Playground 不受影响）
2. **tool-batch 断裂可接受**：send_message 前后如果有连续工具调用，batch 会断开。这是正确行为。
3. **复用优先**：尽量扩展 `component-a2a-envelope` 而非新建组件。
4. **零回归**：现有 a2a inbox 信封（in 方向）行为 100% 不变。
