## 1. 版本主题（产品语义）

三大块相互独立，共同交付：

- **块1 移除 OKR/requirement 漏出**：不删代码，靠「plugin 配置直接摘（①工具 ②prompt）+ feature gate 管代码呈现（③task 卡「所属 requirement」④全景 OKR/req tab）」隐藏；squad 侧 OKR/req 一起剔除（squad_board reminder 滤 OKR/req 只留 task）。gate = build-time 默认关、**长期保留**（代码/spec/测试全留，未来开 gate 即重启）。

## 2. 功能需求（用户可感知）

### 2.1 块1 — 移除 OKR/requirement 漏出（feature gate）[v0.0.223]

**优先级**：P0
**用户故事**：作为用户，我希望 OKR/requirement 功能从界面和 agent 能力中**彻底消失**（成本太大暂不去用），但代码保留以便未来重启——不要让我在 task 卡、全景 tab、agent 工具集里再看到任何 OKR/requirement 痕迹。

**产品规则**：

| 漏出项 | 隐藏方式 | 用户感知 |
|---|---|---|
| ① agent 工具集（goal/requirement 工具） | **plugin 配置直接摘** toolBound（leader/mate/squad profile 全摘） | agent 不再能调 goal/requirement 工具（不再 create/triage OKR） |
| ② system prompt 段（OKR/requirement 相关） | **plugin 配置直接摘**（leader/identity 等 prompt 段） | agent 不再被引导走 OKR/requirement 流程 |
| ③ task 卡「所属 requirement」 | **feature gate `__FEATURE_OKR__`**（默认关，前端条件渲染） | 全景/board task 卡不再显示 requirement 引用 |
| ④ 全景 OKR/req tab | **feature gate**（默认关，STATIC_TABS 只留 tasks） | 全景只见 tasks tab，不见 goals/requirements tab |
| ⑤ squad_board reminder（leader 注入的 OKR/req 全景） | **滤掉 goal/requirement 只留 task**（或停用，架构期定） | leader reminder 不再含 OKR/req 段 |

**feature gate 产品契约**：
- **默认关**（dev 默认关；packaged 默认不 export `FEATURE_OKR=true` → 用户拿到 dmg 看不到 OKR/req）。
- **长期保留代码/spec/测试**：OKR/req 后端代码、相关 spec、相关 UT/AT case 全留待命；未来开 gate 即重启（无代码改动）。
- **gate 仅管前端呈现（③④）**：①② 工具/prompt 走 plugin 配置层（运行时配置），与 gate（编译期常量）两层独立——重启需手动恢复 ①② 配置（不做联动，理由见 `okr-req-gate-plan.md` §「开 gate 重启」）。
- **其他呈现点全盘扫**：架构期 MANDATORY 全盘扫 UI 上露出 OKR/req 的地方（mention `@requirement` 类型、task 创建表单的「挂 requirement」选择器、squad 看板 goal/KR 卡片等），都用 gate 包。

**与既有 spec 的对齐**：
- 全景 tab host 见 `specs/ui/components/studio-page/component-panorama-route.md`（固定 3 tab goals/requirements/tasks → gate 关时只留 tasks）。
- task 卡 requirement 引用见 `component-board-task-card.md`（gate 关时条件隐藏）。
- squad_board provider 见 `specs/tech/squad/[P1]squad_reminder_providers.md §4`（架构期调整产出过滤）。

### 2.2 块2 — 全景 task 视图优化（响应式 + 甬道色块可辨）[v0.0.223]

**优先级**：P1
**用户故事**：作为 squad leader 用户，我看全景 task 看板时，希望列宽能**随窗口宽度自适应**（窄屏不挤压、宽屏不浪费），以及**一眼就能看清每列代表哪个状态**（现在色块太小看不清，几个状态列混在一起）。

**产品规则**：
- **响应式宽度**：kanban 列从固定 240px + `shrink-0`（不可缩）改为「最小宽 + flex 自适应」——窄屏列收窄、宽屏多列平铺；横向滚动作兜底（不破坏「窄屏可用」）。
- **甬道色块多通道可辨**（防色弱，多通道编码）：
  - 列头**整条色带**（列顶全宽 / 列左缘竖条）替代当前 8×8px 小圆点；
  - 列头**底色**带状态色（透明度低，作背景标识）；
  - 状态**文字带色**（列标题文字直接用 statusColor）；
  - 卡片左缘竖条加强（同 statusColor）。
- **视觉待设计师 demo**：本块视觉基线标「待设计师 demo」——req.md 明确「需要看 demo」，PRD 出交互逻辑 + 多通道原则，具体字号/色号/几何待设计稿；设计稿到位后 coder 填组件 spec「视觉基线」字段并跑 vision_check compare。

**与既有 spec 的对齐**：
- 全景 = panorama kanban（`specs/tech/squad/[P1]panorama_overview.md` §1），列 = swimlane（每列一状态色）。
- statusColor 由 DSL `entity.display.status_colors[status]` 驱动（`panorama-utils.ts`，缺省灰）——**映射本身不动**，问题纯是渲染尺寸/对比度，改造在渲染层兜底（即使色未配也用对比明显的状态徽章）。

### 2.3 块3-A — 新增 todo 工具（session 级双层待办，与 task 拆开）[v0.0.223]

**优先级**：P0
**用户故事**：作为 agent，我在一个 session 里手头有一堆事要做（一个用户消息可能要我产出多个文件、回复多个对象），希望有个**当前 session 专属**的双层待办清单帮我理清结构——主条目记清楚「来自哪、要产出什么、备忘」，子步骤记清楚「要经过哪几步」——而不是把这些塞进跨 session 的团队 task 看板（那是两回事）。

**产品规则 — todo 是什么（能力边界，关键！）**：
- **todo ≠ task**：
  - **todo** = **当前 session 手头**的双层待办，**session 级**（不跨 session 共享）、agent 自主维护（用户不直接编辑）、纯文本主体 + 结构化引用 id。
  - **task** = squad **团队跨 session** 工作项，leader 创建/member 认领，有 DAG/状态机/权限/OKF md 主面（`specs/tech/squad/[P1]squad_tools.md §3` 权威）。
- **双层结构**：
  - **主 item**（layer 1）= 一句话 desc + 状态 + **来源**（source）+ **输出**（output）+ **备忘**（memo 纯文本）。
    - source（任务从哪来）：`task` / `user_message` / `agent`，可选 refId（如 source=task 时引 taskId）。
    - output（要产出什么）：`file` / `reply_session` / `reply_agent`，可选 refId（如 output=reply_session 时引目标 sessionId）。
    - memo：自由文本备忘（不是一句话 desc，是补充说明）。
  - **步骤**（layer 2，挂在主 item 下）= 一句话 desc + 状态。步骤记完成主 item 需要的环节。
- **状态机（5 态，free-form 跃迁）**：`未开始 / 进行中 / 已结束 / 跳过 / 出错`。**agent 自决跃迁路径**（任意状态间可跳转，工具层不校验合法路径，仅校验 enum）。
- **生命周期**：主 item 标「已结束」后，**下次更新 todo 时清理它**（agent 责任；不强制立即删，给 agent 完成确认窗口）。
- **工具归属**：todo 工具进**所有 `*.parent.main` profile** 的 toolBound（leader/mate/standalone parent.main 都给）；**subagent / forked 不绑**（短生命周期，todo 主在 parent session）；consolidate / summary session 不进。

**产品语义 — todo 视图与 reminder（配套）**：见 §2.4 / §2.6 / §2.5。

**与既有 spec 的对齐**：
- todo 工具参照 task-tool action 模式（`specs/tech/squad/[P1]squad_tools.md §0` 通用约定 + §3 action-based dispatch），但**无 leader/mate 权限、无 DAG/CAS、无状态机严格性**（todo 状态 free-form）。
- todo 工具进 toolBound 对齐 `specs/tech/agent/tools/index.md`（profile.toolBound 机制）。

**新概念（架构期落 tech spec + ui spec，PRD 不发明）**：todo 工具 action schema（候选 add_item/update_item/add_step/update_step/delete_item/list 等）/ todo 数据模型 / 存储路线（独立 store 仿 cron-adapter，避免 Session 频繁整写）/ todo provider 经 ReminderCtx 读 todo store —— **均归架构期落 `specs/tech/agent/tools/[P1]todo_tools.md`（新）+ `specs/tech/agent/context/[P0]system_reminder.md §3`（todo 行重定义）+ `specs/api/overall/`**。

#### E2E Use Cases（块3-A todo 工具）

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-223-TODO-1 | agent 收到用户消息（产出多文件 + 回复某 agent）→ 建 todo 主 item（source=user_message, output=file, memo）→ 加 3 个步骤 → 推进各步骤状态 → 主 item 标已结束 | todo 正确记录双层结构；状态自由跃迁；主 item 已结束后下次更新 todo 时被清理 |
| UC-223-TODO-2 | todo 数据持久化（关闭 session 重开）→ 同 session 继续 | todo 在同 session 内持久化（不跨 session 共享） |

### 2.4 块3-B — task reminder 改名收窄（squad_tasks → task，认领 ∪ 待认领池）[v0.0.223]

**优先级**：P0
**用户故事**：作为 mate（团队成员），我希望 reminder 里注入的「我的任务」明确包含两类——**我认领的**（assignee=me）+ **待认领池里我能抢的**（assignee=null）——而不是任何模糊的「团队任务」；并且这个 reminder 叫「task reminder」、不叫容易混淆的 squad_tasks。

**产品规则**：
- **改名**：reminder provider implId `squad_tasks` → `task`（或 `my_tasks`，**待用户拍板 §6 开放点**）；文件名 + plugin.json 同步。
- **查询规则收窄**（零新字段 / 零新 action）：`assignee=me` ∪ `assignee=null`（认领 ∪ 待认领池）。**无「关注」概念**（用户已纠正——不做 watchers[] / starred[] / watch-unwatch action；纯按 assignee 过滤）。
- **角色 filter 不变**：mate only（leader 用 squad_board / user 不注入）。
- **血缘 join 保留**：`task.source.requirementId → requirement → (relatedKRId?)KR → goal title` 显示（但块1 gate 关后，requirement/goal 数据仍在后端 store，血缘显示不受影响——只是 agent 不再能创建 OKR/req）。

**与既有 spec 的对齐**：
- 现 squad_tasks provider 见 `specs/tech/squad/[P1]squad_reminder_providers.md §3`（已 assignee=me 收窄，本版扩「∪ assignee=null」+ 改名）。
- 「待认领池」概念已在 task 工具体现（`squad_tools.md §3` claim 池 = `assignee=null`），reminder 收窄与工具一致。

**新概念（架构期落）**：provider 改名 + filter 扩 `assignee=null` —— 归架构期对齐 `specs/tech/squad/[P1]squad_reminder_providers.md §3` + `prompt/squad_tasks.ts` 实现重命名。

### 2.5 块3-C — todo reminder 填壳（语义重定义：task 进度 → session todo 进度）[v0.0.223]

**优先级**：P0
**用户故事**：作为 agent，每轮我都要被提醒「当前 session 手头 todo 进度怎样」——哪些主 item 还在进行、哪些步骤卡住——避免我遗忘手头待办。

**产品规则**：
- **填壳**：`reminder/todo.ts` 当前是 no-op 空壳（返 []；spec 注释说「来源 task_tools」但代码从不读）——本版**填此空壳**，语义重定义为「**当前 session todo 进度**」（不再读 task_tools）。
- **数据源**：当前 session 的 todo store（经 ReminderCtx 扩展读，仿 squad_tasks 的 `ctx.squadContext` 模式加 `ctx.todoStore` 或在 ReminderCtx 注入 sessionId 读 todo）。
- **产出格式**：注入未结束的主 item + 各 item 步骤状态摘要（如 `[todo] 进行中：写 spec 文档 (2/3 步骤) · 修复 bug X (未开始)`）。
- **prompt 必须讲清 todo reminder vs task reminder 差别**（关键！避免 agent 混淆）：todo reminder = session 手头双层待办；task reminder = squad 团队认领/待认领任务。prompt 段措辞归架构期落 prompt spec。

**与既有 spec 的对齐**：
- 现 todo provider spec 见 `specs/tech/agent/context/[P0]system_reminder.md §3` row 5（order 5，注释「task 进度 / task_tools 缺失 no-op」）—— 本版**重定义语义**为 session todo 进度，架构期同步改 spec 描述。
- 命名无冲突（旧 todo 是空壳，新 todo 是真产出）。

**新概念（架构期落）**：ReminderCtx 扩展（todoStore 入口）+ todo provider impl 重写 —— 归架构期对齐 system_reminder.md §3 + plugin.json（implId 沿用 `todo`，无需改名）。

### 2.6 块3-D — todo 视图（挂 float-menu 第 4 项）[v0.0.223]

**用户故事**：作为用户，我希望在会话右侧悬浮菜单里看到 agent 当前手头的 todo 清单（双层树 + 悬停看主 item 的来源/输出/备忘），以便我了解 agent 的工作结构——与 memory/cron/skills 并列。

**产品规则（功能 brief，视觉待 demo）**：
- **挂点**：`component-chat-float-menu`（v0.0.131 悬浮菜单，现竖向 3 项 memory/cron/skills）**加第 4 项 todo**（位于 skills 下方）。
- **交互逻辑**：

- **badge 语义**：候选「未完成主 item 数」或「总 item 数」——**待用户拍板 §6 开放点**；倾向「未完成主 item 数」（与 cron badge「enabled 数」同语义：反映活跃度）。
- **数据 hook**：仿 `use-cron-crud.ts`（session 级 CRUD hook，list/create/toggle/delete + refetch）；todo 高频更新走 SSE `todo` topic 或 polling 兜底（架构期定）。

**与既有 spec 的对齐**：
- 挂点 `specs/ui/components/chat-page/component-chat-float-menu.md`（现 3 项 memory/cron/skills + 3 modal + 3 hook；本版加第 4 项 todo + 第 4 modal + 第 4 hook）。
- 仿 cron 模式（session 级 + 工具 + 弹层列表 + badge）。

**新概念（架构期落 ui spec）**：todo 视图组件 spec（`specs/ui/components/chat-page/component-todo-modal.md` 新建）+ float-menu 加项 —— 归架构期/coder 落 `specs/ui/components/`。

## 5. 验收口径

- **功能**：UC-223-TODO-CREATE / TODO-REMIND / TODO-VIEW / TASKR / OKR-HIDE / PAN-RWD / PAN-COLOR 全 PASS（AT + ET + UT 共同覆盖；核心冒烟集 + UT 满足最低覆盖）。
