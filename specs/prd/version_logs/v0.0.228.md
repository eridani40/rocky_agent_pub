## 1. 版本主题（产品语义）

todo 面板自 v0.0.223 交付后存在 5 个体验缺口，本版一次收敛：

- **数据不实时**：todo 高频更新（agent 每 turn 可能改），但前端只靠 60s 轮询兜底——用户在面板里看到的是最迟 60s 前的旧数据，badge 计数同样滞后。本版加 SSE 实时推送，替换轮询。
- **打开不刷新**：点悬浮菜单打开弹层时看到的是挂载时刻的旧快照，不重新拉取。
- **面板太窄**：固定 520px 宽，长 desc/memo 拥挤。
- **hover 弹层行为发散**：悬停区域含步骤层（步骤 hover 也保持弹层）、弹层出现在整个 item 块底部而非主 item 正下方。
- **状态徽章难辨**：not_started 与 done 同为 muted 灰色系，一眼分不清「没开始」和「已完成」。

**边界**：本版只读视图定位不变（用户编辑归 follow-up）；SSE 只解决「数据实时性」，不改任何交互/数据语义。

## 2. 功能需求（用户可感知）

### 2.1 块1 — todo SSE 实时化（`session_todo_changed`）[v0.0.228]

**优先级**：P0
**用户故事**：作为用户，agent 在后台工作时，我希望 todo 的任何变化（新建、推进状态、清理）**立刻**反映在悬浮菜单 badge 和已打开的 todo 弹层里——而不是等最长 60s 的轮询。

**产品规则**：
- **实时性语义**：todo 发生任何写（agent 工具路径 / HTTP API 路径，任一路径）→ 正在查看该 session 的 chat 页在**秒级**内看到变化（badge 计数 + 已开弹层列表同步刷新）。
- **只有打开 session 才订阅**：进入会话自动订阅、切走/离开自动退订——复用既有 fanout 挂载机制（`useSessionPanelFanout`，随 chat 页装配层挂载），零新订阅 UI、零新设置项。
- **轻量信号 + 重拉**：事件本身不携带全量 todo 数据；前端收到事件后重拉该 session 全量列表（todo 规模小，重拉代价可忽略；对齐 `20-todo.md`「写操作返小对象、完整数据走 GET」的省 payload 原则）。
- **60s 轮询退役**：SSE 接管实时性后，原 60s 定时器移除。初始态仍靠挂载 GET（既有）；SSE 断链期间的数据空洞由「切回重挂载 GET」+「块2 打开弹层 refetch」兜底，不再保留定时轮询。
- **同源不变量保持**：badge 与弹层列表同一 hook 数据源（v0.0.223 既有不变量）——SSE 触发 refetch 后两处同时更新，不出现 badge 与弹层不一致。

**技术概念（需先落 tech spec，PRD 不发明）**：
- **新事件类型 `session_todo_changed`**：挂既有 `session_panel` topic（group `session_id:<sid>`）——复用 topic，零新 topic 注册、零 SSE 白名单变更。需先落 `specs/tech/agent/session/[P0]session_event.md §2`（SessionEvent 联合）+ `§3`（触发表）——**交 architect**。
- **后端 emit 注入点 = TodoStore 写方法**（upsertItem / removeItem / cleanupFinished）写成功后 emit：agent 工具（todo-tool）与 HTTP handler（todo-handler）两条写路径共享 TodoStore，store 层单点 emit 即全覆盖——参照 `session_workspace_dir_changed` 在 store 层经 statusBus emit 的既有范式（`session-workspace-store.ts`）。
- **前端扇出**：`useSessionPanelFanout` 在 workspace/read 两类之外加第三类 todo 扇出 → todo hook 增量 refetch（扇出枢纽是受控例外，`chat_area_hooks.md §4.2` 机制复用，具体接线归 architect/coder）。
- **不触发 `session_meta` broadcast**：todo 不在 SessionMetaView 字段内，会话列表无感知需求——对齐 `session_workspace_file_changed` 不触发 broadcast 的先例。

#### E2E Use Cases（块1）

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-228-SSE-1 | 打开 chat session（agent 运行中）→ agent 调 todo 工具建/改 item → 观察悬浮菜单 todo badge | badge 计数秒级更新（不等 60s 轮询） |
| UC-228-SSE-2 | todo 弹层打开中 → agent 推进某步骤状态（not_started→in_progress→done） | 弹层列表秒级反映新状态徽章 |
| UC-228-SSE-3 | agent 写 todo 期间切走到别的 session → 切回 | 切回后初始 GET 拉到最新 todo（SSE 断订期间不丢数据） |

### 2.2 块2 — 点击展开重新拉取 [v0.0.228]

**优先级**：P1
**用户故事**：作为用户，我点悬浮菜单「待办」打开弹层的那一刻，希望看到的就是**此刻最新**的数据，而不是页面挂载时的旧快照。

**产品规则**：
- **打开即刷新**：点悬浮菜单「待办」→ 打开弹层时调一次 `refetch()`——对齐 skills 弹层「每次打开由弹层侧调一次 catalog.refetch()」的既有先例（`component-chat-float-menu.md §7`）。
- **hook 恒挂不变**：数据 hook 仍恒挂载于悬浮菜单（badge 常驻数据源不动）；refetch 是打开弹层瞬间的命令式刷新，不改挂载模型。
- **与 SSE 互补**：SSE 管「打开期间的实时增量」，打开 refetch 管「打开瞬间必最新」——SSE 事件丢失的边界窗口由打开 refetch 兜底，两者不冗余。

#### E2E Use Cases（块2）

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-228-OPEN-1 | 页面挂载后 todo 数据有变化（SSE 未覆盖的边界场景）→ 点悬浮菜单「待办」 | 弹层打开即显示最新数据（非旧快照） |

### 2.3 块3 — 面板尺寸响应式 [v0.0.228]

**优先级**：P1
**用户故事**：作为用户，todo 弹层现在固定 520px 太窄——长 desc / memo 挤在一起看不全；我希望它宽一点、随窗口宽度自适应，高度也够用（长列表不频繁滚动）。

**产品规则**：
- **宽度响应式**：从固定 `w-[520px]` 改为更宽的响应式档位——参照 markdown viewer/editor 弹层档位（`w-[720px] max-w-[92vw]`，`component-modal-md-editor.tsx` 既有）：宽屏不浪费、窄屏 `max-w-[92vw]` 兜底不溢出。具体档位实现期定，约束 = 不窄于现状 520px、不超 92vw。
- **高度保持 `max-h-[88vh]`**（现状已对齐 md viewer/editor 档位），body 内部滚动行为不变。
- **布局稳定（MANDATORY 铁律）**：尺寸调整不引入任何元素位移问题——弹层内按钮（关闭）始终可见，无「hover 出现/消失导致相邻元素跳动」（对齐 CLAUDE.md 布局稳定性规范 + `_conventions.md`）。

#### E2E Use Cases（块3）

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-228-SIZE-1 | 打开 todo 弹层 | 宽度明显大于旧 520px（够用不窄）；窄窗口下压缩但不溢出屏幕（92vw 兜底） |
| UC-228-SIZE-2 | 长 todo 列表（20+ item）打开弹层 | 弹层高度不超 88vh，列表在 body 内滚动，标题栏/关闭按钮固定不滚走 |

### 2.4 块4 — hover 弹层收敛（主 item only + 正下方）[v0.0.228]

**优先级**：P1
**用户故事**：作为用户，我悬停某个主 item 看来源/输出/备忘时，详情弹层应该就贴在**这个主 item 正下方**；我把鼠标移到步骤上时不该触发详情弹层——现在悬停区域含步骤层（步骤上晃鼠标弹层也在）、弹层出现在整个 item 块（含步骤）底部，位置和触发都发散。

**产品规则**：
- **触发范围收敛**：仅**主 item 行** hover 触发详情弹层；步骤行 hover 不触发。
- **保持区域**：主 item 行 ∪ 详情弹层本身（二者相邻连续）——鼠标从主 item 行下移进弹层阅读详情时弹层保持；移出两者即收起。
- **位置**：弹层出现在**主 item 行正下方**（覆盖于步骤层之上的 absolute overlay）——现状是整个 item 块（含步骤）底部，偏离预期。
- **布局稳定（MANDATORY 铁律）**：弹层 absolute overlay 不推挤后续行（既有实现已满足，保持）；弹层出现/消失不导致任何其他元素位移。
- **有详情才弹**（既有逻辑保持）：source/output/memo 全空的主 item 不弹详情。

#### E2E Use Cases（块4）

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-228-HOVER-1 | 悬停某主 item 行 | 详情弹层出现在该主 item 正下方（非整个 item 块底部），后续行不被推挤 |
| UC-228-HOVER-2 | 悬停步骤行 | 不出现详情弹层 |
| UC-228-HOVER-3 | 从主 item 行下移进入详情弹层 → 再移出 | 进入弹层时弹层保持（可读详情）；移出后收起 |

### 2.5 块5 — 状态徽章颜色区分 [v0.0.228]

**优先级**：P1
**用户故事**：作为用户，「未开始」和「已结束」徽章现在都是一样的灰色，我扫一眼分不清哪些做完了、哪些还没动——要一眼可辨。

**产品规则**：
- **拉开 not_started vs done**：`done` 改用有区分度的色相（建议 **success 绿色系**——`--success` / `--success-bg` token 已存在，且与 tool-call「✓ done」同款语义色，全 app 一致）；`not_started` 保持 muted 灰（未开始 = 中性待机）。
- **全 5 态色板**（改后）：not_started = muted 灰 / in_progress = accent 蓝（既有不动）/ **done = success 绿（本版改）** / skipped = muted 灰 + 降透明度（既有不动，与 done 靠色相拉开）/ error = warning 橙（既有不动）。
- **token 化**：只用已有 token（`--success` / `--success-bg`），不新增色值、不硬编码 hex。

#### E2E Use Cases（块5）

| ID | 用户操作链路 | 预期结果 |
|----|-------------|---------|
| UC-228-COLOR-1 | todo 列表同时含 not_started + done 的 item | 两者徽章色相一眼可辨（灰 vs 绿）；全 5 态色板无两两混淆 |

## 5. 验收口径

- **功能**：UC-228-SSE-REALTIME / OPEN-FRESH / HOVER-SCOPE / VISUAL 全 PASS（UT + ET 冒烟共同覆盖）。
- **实时性不变量**：todo 任一路径写（agent 工具 / HTTP API）→ 打开中的 session 秒级可见；未打开的 session 无订阅无推送；60s 定时器代码移除。
- **同源不变量**：badge 与弹层列表始终同一数据源，SSE refetch 后同步更新。
- **布局稳定不变量**：hover 弹层 absolute 不推挤；弹层/按钮出现消失不导致任何元素位移。
- **token 不变量**：徽章颜色只用既有 token，零新色值零硬编码 hex。
- **回归不变量**：既有 AT `todo-crud-flow` / `todo-reminder` 全绿（emit 注入不改变写路径契约）；既有 ET `playground-todo-view` 主路径不回归。
- **视觉保真**：无设计稿 → vision_check compare 跳过（req 已确认）。

## 6. 待用户拍板的产品开放点

1. **done 徽章目标色**：建议 success 绿（`--success` 既有 token，tool-call 同款语义色）——若用户有其他偏好（如 accent 蓝加填充）可调；默认按绿推进。

3. **hover 保持区域**：建议「主 item 行 ∪ 详情弹层」（弹层可读）；若希望严格「移出主 item 行即收」也可——默认按前者推进。

> 以上 3 点均有默认推进方案（req「自动化推进，有问题问，没问题不问」）；无阻塞性开放点。
