## 1. 版本主题（产品语义）

**两轴模型重构**：把绑死的「task → propose → accept → done → 新 formal」一根线，拆成两根**正交轴**：

- **生产轴（task）**：coach 绝对主权、长期存活、可续训（round 在同一 task 内递增，不需新建 task）。
- **归档轴（采纳）**：`adopt(versionId)` 任意 process 版定稿为新 formal，可重复，**不改 task 状态**。

配套：head 退教室层（管学生/资产/任务监督），**不进 task 内场**，要内场效果就 `send_message` 给该 task 的 coach；head ∩ coach = **task 客观事实**（元数据 + 状态 + 版本集 + 轮次历史摘要）。

**直接动因**（`messages.log` 实证 + 用户痛点）：
- coach 撞 `maxTurns` / `done` 墙：任务 done 后 maxTurns=1 耗尽、task closed，用户想「基于 1.1.1 续训一个 iteration」却被迫开新 task（-messages.log line 745/885）。
- coach `bash ls .work` 摸目录：iteration_state 没注入 base ws 路径 + 版本谱系，coach 只能 ls 探目录。
- head 在 task 内是「傻子」（v0.0.215 痛点延续）：连只读 evaluate 也要经 coach，没有驱动内场的干净通道。
- 版本号 `1.1.x` 混乱：`version.json.versionLabel` 恒 "0.0"（写侧 bug），UI 又泄露目录名（4 段 `1.1.1.1` 且 major 算错）。

## 2. 功能需求（用户可感知）

### 2.1 coach 对 task 绝对主权 + task 可续训（生命周期重构）[v0.0.221]

**优先级**：P0
**用户故事**：作为 academy 用户，我希望一个训练任务一旦建好就长期存活——撞 maxTurns、done、或我主动叫停后都能**原地续训**，而不是被迫开新 task 丢掉之前的迭代脉络。

**产品规则**：
- **task 非终态**：原 `done / aborted / stopped` 统一为 `paused(reason)`，仅 `reason` 区分（`maxturns / completed / stopped / earlystop`）。coach 可 `resume` 任一 paused task 续训起 round N+1。
- **maxTurns 硬上限不可越过**（用户裁决）：到顶（reason=maxturns）即终态、coach 不可 resume 越过；要继续须先由 head/用户 `update_task(maxTurns=N+x)` 调大现有 task 的 maxTurns 再 resume——**不开新 task / 不产新 formal**。maxTurns **默认设大**避免过早触顶。
- **原 `awaiting_confirm` / `rejected` task 级状态去除**（采纳解耦后无「整 task 待审/被拒」态）；单个 process 版本仍可有 `status='rejected'`——那是 coach `fork` 丢弃的**版本级**状态，非 task 级。
- **directive 语义**：从「透传消费的硬命令」改为「advisory 输入」——coach 主权下，user/head 的 directive 是主要参考，非必须执行；coach 有权用自己的判断调整。
- **coach 对 task 全权**：执行独占 + 决策自主；user 与 head 是建议通道（directive / send_message）。

**用户感知**：
- 训练撞 maxTurns/done 后**不再被迫开新 task**，可原地续训。
- 可主动 `pause` 暂停（出门/思考），回来 `resume` 继续——task 不丢。
- 用户/head 建议（directive）是参考，coach 自主权衡调整（治「directive 当命令传但 coach 死板照执」）。

**概念落点**：`specs/tech/academy/[P0]training_engine.md §1` 状态机三态（pending/running/paused+reason）+ §3.3 acceptTask 守卫（不变）+ resume 原子 action（新增）；`[P0]train_student_tool.md` coach 新增 pause/resume。

### 2.2 采纳解耦（adopt 任意版本 + 可重复 + 不杀 task）[v0.0.221]

**优先级**：P0
**用户故事**：作为 academy 用户，我希望能在训练中途**随时把某个中间版本定稿为正式版**做快照（比如 round 2 那版已经够好用），同时训练继续打磨——而不是只能等最后 propose 一个版本。

**产品规则**：
- `adopt(versionId)` 把**任意** process 版本（不只是最后那个）复制为新 formal 版本（x.0 递增）；原 base 不动；记 `adoptedFromProcessVersionId` 溯源（§12.13.1 已落字段）。
- **可多次 adopt**：采纳 1.1.2 → formal 2.0，继续迭代，再采纳 1.1.5 → formal 3.0——一个 task 一生可产出多个 formal 版本。
- **adopt 不改 task 状态**：task 仍在产，可继续 round。归档与生产彻底解耦。
- `propose` action **取消**（采纳解耦后不需要这道 gate；coach 直接 adopt）。
- UI「点采纳」走同一 engine action（人触发口，不阻塞 coach）——用户可中途手动采纳某版本做快照。

**用户感知**：
- 中途可采纳中间版做快照定稿，训练继续打磨，不再「一 task 一 formal」。
- 没有最后的 propose → 接受/拒绝 gate；采纳是任何时候可调的旁路。

**概念落点**：`[P0]training_engine.md` adopt 旁路（不在状态机里、任何时候可调、不动 task 状态）；`[P0]data_model.md §3/§6` adopt 可重复 + `adoptedFromProcessVersionId`（沿用 v0.0.219 字段）；`[P0]train_student_tool.md` coach 新增 adopt，去 propose。

### 2.3 临时基线可干预（fork 切任一历史版本作起点）[v0.0.221]

**优先级**：P0
**用户故事**：作为 academy 用户，当我觉得「round 2 那版更好、想从它继续打磨」时，希望教练能**直接切回那版作起点**——而不是只能线性往前，或被迫开新 task。

**产品规则**：
- iteration「下一轮从谁开始 / 拿谁当对比基准」= **临时基线（temporaryBaselineVersionId）** 的选择。
- **默认规则（自动接续）**：`revise` —— 本轮 candidate 经 acceptGate 判 `improve`，则自动晋升为临时基线，下轮 candidate 自它 fork（即「上一轮变好了就替换」）。
- **可干预（分叉 / 回退）**：coach `fork(baseVersionId=<任一历史版本>)` 把临时基线**切到指定版本**（如「用 round 2 那版」），下轮自它开始、后续 acceptGate 也对比它。coach 主权决定。
- user/head 可建议（advisory）；UI 可让用户点某版本 → 路由到 coach 的 fork（人触发口）。
- **versionLabel = `{major}.{taskSeq}.{round}`**（3 段）：前两段 = **任务身份**（major.taskSeq，task 一生不变），第三段 = **iteration 序**（round，递增）。round 之间「从谁开始、到谁结束」有默认规则（上轮变好则接续），但保留灵活性（fork 切任意版本作基线）——不强制线性链，允许分叉与回退。

**用户感知**：
- 「基于 1.1.1 续训一个 iteration」这种诉求不再需开新 task——直接 `fork(1.1.1)` 把基线切回。
- 支持回退（发现走偏了回到之前某版）与分叉（探索不同方向）。

**概念落点**：`[P0]training_engine.md §3.2` forkCandidate 扩 baseVersionId 参数（切任一历史版本）；`[P0]data_model.md §6` versionLabel 3 段规则（不变，修复写正确，见 §2.5）。

### 2.4 head 退教室层 + 不进 task 内场（分工收紧）[v0.0.221]

**优先级**：P0
**用户故事**：作为 academy 用户，我希望 head_teacher 当好班主任（管学生/资产/任务监督），**不要**伸手到 task 内场瞎指挥——但又能在觉得 task 哪里需要调整时，通过 send_message 告诉 coach（而不是自己做不到只能干瞪眼）。

**产品规则**：

| 维度 | head_teacher | coach |
|---|---|---|
| 作用域 | 教室（classroom）全局 | **单个 task**（1:1 绑定） |
| 访问粒度 | 实体级（Id） | 文件级（workspace 路径） |
| 学生/版本 | CRUD + 五元组读写 | 只读自己 task 的 base/candidate/谱系 |
| 教室资产（dataset/grader/skill） | **增删改查** | 只读（反思用） |
| 任务 | `start_task`（建生产线）/ 监督看板 | **全权推进 + 定稿 + 生命周期** |
| task 内部动作 | ❌ **一律不执行** → `send_message` 给 coach | ✅ 全部（evaluate/revise/fork/adopt/pause/resume） |
| 决策权 | 教室层决策 | task 内**绝对决策**（自主，听取建议） |
| 通信 | `send_message` → coach（建议/请求） | `send_message` → head（报告/请示）+ 直接收 user |

- head 工具**没有**任何 task 内部动作：`evaluate / revise / fork / sample / grade / adopt / pause / resume / propose` 全交还 coach。
- head 仅有的 task 相关 action：`start_task / list_tasks / get_task / update_task(maxTurns?, directive?) / send_message`（监督级，不下钻 per-case）。
- `update_task` 仅调 `maxTurns / directive` 两字段——用于让 coach 续训越过原 maxTurns 上限（§2.1），或调整 directive 给建议。
- **head ∩ coach = task 客观事实**（元数据 + 状态 + 版本集 + 轮次历史摘要）；差异仅在访问粒度（head 实体级 / coach 文件级）与动作权（head 无 / coach 全权）——这是 send_message 协作的契约锚点。

**用户感知**：
- head 在 task 内不再是「傻子」（v0.0.215 痛点）——通过 `send_message` 驱动 coach 做事，coach 拿全路径不再 bash 摸目录。
- 班主任管教室，教练管任务，职责边界清晰。

**概念落点**：`[P0]academy_overview.md §2` 角色边界 + §8 关键路径（adopt 旁路 + resume + send_message 协作）；`[P0]session_kind_extension.md` toolBound（head=manage-classroom / coach=manage-task）+ §7 三工具并两；`specs/tech/academy/index.md §④` 跨 KB 不变量 2 调整（双引擎咬合重画为「coach 主权 + head 实体级」）。

### 2.5 版本号修复 + 信息供给完善（用户可见层）[v0.0.221]

**优先级**：P0
**用户故事**：作为 academy 用户，我希望看到的版本号（1.1.x / 2.0 / 3.0）**准确反映训练脉络**、不再混乱；同时 coach 能拿到完整路径和版本谱系，不再看到它瞎 `ls .work` 探目录。

**产品规则**：

**① versionLabel 写正确（BUG，产品层修）**：
- `version.json.versionLabel` 之前恒为 `"0.0"`（写侧 bug）→ fork/adopt **必须写正确** `{major}.{taskSeq}.{round}`（过程版）/ `{x}.0`（formal 版）。
- **UI 显 versionLabel 字段、不显目录名**：过程版目录路径段数（multi-turn 下变 4+ 段）是隐藏实现细节，不进产品层 UI。
- 用户看到的「1.1.x」混乱根因 = versionLabel 字段坏了 + UI 泄露目录名；本版两处一起修。
- **过程版目录段数简化**（如 `.work/{taskSeq}/{round}/`）列 follow-up，不在本版。

**② coach 信息供给完善（mapper `academy_iteration_state` 扩充）**：每轮常驻注入——
- taskId / taskSeq / classroomId / studentId+name / mode / optimizeStyle
- 生命周期：status（active/paused/done）+ **resumable 标志** + maxTurns（软提示）+ roundsUsed
- **candidate：versionId + versionLabel + workspaceDir 绝对路径**（coach edit 目标）
- **base：versionId + versionLabel + workspaceDir 绝对路径**（只读参考，读 base AGENTS.md）
- temporaryBaseline：versionId + avgScore
- **版本谱系**（本 task 全部 process 版）：`[{round, versionId, label, decision, avgScore, workspaceDir}]`
- **已采纳 formal**（本 task 归档的）：`[{versionId, label, adoptedFromProcessLabel}]`
- dataset/grader（multi 反思路径）

→ coach 拥有**它 task 的一切路径 + 状态**，永远不需要 `ls`/猜目录（修 messages.log 里 coach `bash ls .work` 摸路的病）。

**③ head 信息供给完善**：
- mapper `academy_task_status` **补每 task 的 `coachSessionId`**——head 能直接 `send_message` 驱动 coach。
- **新增 `academy_head_role` mapper**：注入 head 角色职责 +「task 内部要效果 → send_message 给该 task 的 coach，别自己伸手」指引。

**附 BUG（随本版修，技术细节归 architect）**：
1. **`version.json.versionLabel` 恒为 `"0.0"`**：`forkVersionWorkspace` / `adoptToFormal` 写 version.json 时未写 versionLabel。实证：formal 2.0 的 version.json versionLabel=`"0.0"`。→ 写侧补写正确 label。
2. **过程版目录 major 算错**：Task2 base=formal 2.0，过程版目录却是 `1.1.1.1`（major=1）。根因：目录路径用 base.versionLabel 全段，而 versionLabel 又是坏的 `"0.0"` → major 计算链路污染。修 #1 后复核；倾向目录不再用 versionLabel 拼接（follow-up）。
3. **accept 不同步 `student.currentFormalVersionId` 指针**（pre-existing BUG-001）：`get_student` / `list_students` 在 adopt 后仍报旧 formal。→ adopt 改造时一并修写侧。

**概念落点**：`[P0]data_model.md §3/§6` versionLabel 写正确（BUG 修复）+ `[P0]session_kind_extension.md §4` mapper 扩充清单（`academy_iteration_state` 扩 + `academy_head_role` 新增 + `academy_task_status` 补 coachSessionId）；`specs/api/overall/18-academy.md` task DTO 反规范化 `coachSessionId`。

### 3.2 对现有路径的更新（§12.8 UC-D / UC-E 对齐）

- **UC-D 发起简单学习训练**：去 `propose → 接受/拒绝` 尾段，改为「coach 自主迭代 → 可 `adopt(versionId)` 定稿为新 formal（用户/UI 也可点采纳走同一 action）」。task 一旦建就长期存活，不随单轮结束。
- **UC-E 发起多轮训练式训练**：去 `最终 propose → 接受/拒绝`；改为「多轮迭代中任何时刻可 `adopt` 某版定稿；task 不结束，round 可继续递增（受 maxTurns 上限，到顶需 update_task 调大）」。
- **UC-F 训练中对话 + subagent 只读观察**：head 不再有只读 `evaluate` 工具，要看 task 内部细节 → `send_message` coach；其余不变。

> 覆盖方式遵循「核心冒烟集 + UT」原则（CLAUDE.md 持久化测试用例库铁律）：普通 feature 不逐路径新建持久 AT/ET case。本版 UC-221-A/B/C 涉及**新的 task 生命周期状态机 + adopt 解耦**（LLM 参与的 coach 决策链路），评估入选 AT；UC-221-D/E/F/G 以 UT + 既有 academy 冒烟集回归覆盖为主。
