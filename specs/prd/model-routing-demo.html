Part 1 配置 demo（怎么配）

① 配置层级：四层职责（老板架构讨论 10:49）
app 定义方案 → group 挂载方案或默认模型 → session 只能选 model / default。箭头表示「向下生效 / 被覆盖」。
App 级 · 方案库（CRUD）
  • 模型组合方案 = 可命名/可编辑/可删除的有序条目链
  • 唯一定义处：新建 / 重命名 / 删除 / 复制
  • 编辑后所有挂载方立即生效
Group / Playground（studio）
  • 挂载一个方案 → 该 group 下所有 session 走方案链
  • 或只配 默认模型（现有逻辑）
  • 本期仅 studio / playground 可用方案
Session 级
  • 只能配 model / default（不能配方案）
  • session 显式模型 = 覆盖 group 默认模型
  • session = default → 直接走 group 挂载方案链
resolve(session, group):
  ├─ group 无方案（只配模型）→ 分支 1：现有单模型逻辑（resolveModel 原链，零改动）
  └─ group 有方案 → 分支 2：
       ├─ session.modelId == 'default' → 直接走方案链（方案条目本身）
       └─ session 显式配了模型 → session 模型作为 priority 0 合成插入方案顶部
            （临时合成，不写回方案实体；熔断键 = planId + session 模型）
② 模型组合方案编辑：有序条目列表 + 时间条件 + 熔断参数
方案 = 可命名实体，条目按 priority 升序 = 尝试顺序。下方是「主力+兜底」方案编辑器的核心控件。

熔断参数（可选覆盖，默认 4 / 2 / 60 / 0.6 / 10）
参数默认含义

interface CircuitConfig {
  failure_threshold?: number;   // 默认 4
  success_threshold?: number;   // 默认 2
  timeout_seconds?:   number;   // 默认 60
  error_rate_threshold?: number; // 默认 0.6
  min_requests?:      number;   // 默认 10
}

同模型条目约束（老板 D9 · 保存时硬拒绝）

同一个模型（providerId + modelId 复合）最多 2 个条目：1 个带时间 + 1 个不带时间，且带时间必须排在上面（时间命中用带时间的，未命中滑到无条件的兜底）。
组合是否允许说明
带时间 ×1 + 不带时间 ×1（带时间在上）✅ 允许正常用法：时间窗口内用带时间条目，窗口外滑到无条件兜底
带时间 ×2✕ 硬拒绝同模型不允许 2 个带时间条目
不带时间 ×2✕ 硬拒绝重复 = 冗余
带时间在无条件的下面✕ 硬拒绝带时间条目必须在不带时间条目上面
interface RoutingItem {
  providerId: string;            // 指向 app_config providers 实例（ModelRef 复合，防同名跨 provider 歧义）
  modelId: string;
  priority: number;            // 1 = 最高优先（尝试顺序 = priority 升序）
  timeCondition?: TimeCondition;  // 可选；不配置 = 随时可用（无条件条目）
}

interface ModelRoutingPlan {
  id: string;
  name: string;            // 可命名实体（如「主力+兜底」）；group 挂载引用
  items: RoutingItem[];    // 有序降级链（按 priority 升序 = 尝试顺序）
  circuit?: CircuitConfig; // 熔断参数覆盖（可选）
  createdAt: number;
}

Part 2 调用时的情况说明（怎么走）

① resolve 双分支：先定「走方案 / 走单模型」，逐步决策在 attempt 内
路由不是调用前 resolve 一次定死模型（老板架构讨论 ④）——resolve 只产出「候选链起点」，attempt 循环内部逐步决策。
LLM 调用请求到来→ resolve(session, group)→ group 无方案 ?
├─ 是 → 分支 1：单模型（现有 resolveModel 原链）→直接调用该模型
└─ 否 → 分支 2：有方案→ session = default ?
├─ 是 → 候选链 = 方案 items（按 priority 升序）
└─ 否（显式模型）→ priority 0 合成插入方案顶部→ 候选链 = [session 模型] + 方案 items（临时，不写回；熔断键 planId+模型） 
interface RoutingItem { ... }  // 见 Part 1
// resolve 产出 = 候选链起点；后续每一步（调谁 / sleep 多久）都在 attempt 循环内 f(config, state) 决定
② attempt 内部路由循环：时间过滤 → 熔断 → 去重 → 按序尝试 → 失败决策 → 退避
① 时间过滤→ ② 熔断检查→ ③ bannedModels 去重→ ④ 发起 LLM 调用
成功 → 返回结果（熔断收敛） 失败 → 记原因 + 按错误类型决策
重试（模型内 N 次）/ 放弃（abandoned → 进 bannedModels）/ 跳过（skipped）→ 退避 sleep→ 下一个候选（cursor+1） 
while (还有候选):
  next = f(config, state)   // 决策：时间过滤 → 熔断检查 → 候选游标 → 退避 sleep
  sleep(next.delay)          // 按错误类型/退避决策
  result = llmCall(next.item)
  state.record(result)       // 记录成功/失败 + 原因（called/failed/abandoned/skipped）
  if (result.ok) break       // 收敛返回
// 循环耗尽 → 上抛聚合错误（各条目失败原因摘要）
失败决策明细：按错误类型差异化「模型内重试次数」（老板 D1）
错误类别模型内重试熔断行为
RATE_LIMITED（429）/ PROVIDER_OVERLOADED（529）0（快速失败直接降级）计失败；达阈值 → Open
NETWORK / TIMEOUT_* / SERVER_ERROR / STREAM_INCOMPLETE / EMPTY_RESPONSE1（瞬态重试）计失败；达阈值 → Open
AUTH_INVALID（401）/ AUTH_FORBIDDEN（403）0直接熔断 Open（短期不恢复）
MAX_TOKENS_TOO_HIGH1（降 maxTokens ×0.7）计失败；达阈值 → Open
CONTEXT_LENGTH_EXCEEDED / MAX_TOKENS_EXCEEDED0（走压缩/bump 修复流程）修复后仍失败才计
CONTENT_FILTERED / MODEL_NOT_FOUND / MALFORMED_TOOL_CALL / BAD_REQUEST_OTHER0计失败；达阈值 → Open
ABORTED_BY_USER—不算失败，直接返回
超时沿用现有看门狗（TTFB 45s / stall 30/30/120，老板 D2）；sleep 决策 = f(config, state)，同模型内重试走 backoff，换模型降级可 0 sleep 或短 sleep。
③ Config / State 分离：决策 = f(config, state)，可复现（老板 10:52/10:53）
维度内容生命周期特性
Config（静态定义） 方案实体（items 有序链 + 时间条件 + 熔断参数）+ 熔断状态（planId+providerId+modelId 三维，谁在备选、谁熔断了） 跨 call 存活（挂方案实体维度） 静态可查询；熔断 = 运行时内存态（不持久化，重启丢失可接受）
State（动态执行） agent loop 对「这一次 llm call」的状态：候选处置轨迹 + 游标 + bannedModels call 级瞬时（单次调用生命周期） 每次 llm call 独立；不落盘，call 结束即弃 
interface AttemptState {
  tried: CandidateRecord[];   // 已处置候选的轨迹（调用过谁、失败了、放弃了谁）
  cursor: number;             // 当前尝试到候选列表哪个位置
  bannedModels: Set<string>;  // 本次 call 被放弃/熔断的模型配置（providerId+modelId），v3.1
}

interface CandidateRecord {
  item: RoutingItem;          // 候选条目（provider+model）
  status: 'called' | 'failed' | 'abandoned' | 'skipped';
  error?: LlmError;           // 失败原因（错误分类）
  attemptCount?: number;      // 模型内尝试次数
  sleepUntil?: number;        // 退避等待截止（429/限流时）
}
四态：called 发起了调用 / failed 调用失败（记录原因分类）/ abandoned 放弃了（不重试不降级，401/403/429 快速失败）/ skipped 跳过了（时间未命中 / 熔断 Open / bannedModels 去重）。

5 个场景（每个：图文 + 可展开步骤）

A 时间条件：Kimi hours=[2-23]，当前 1 点 → 跳过 → DeepSeek
当前 1 点→ P1 Kimi（hours=[2..23]）时间未命中 → skipped→ P2 DeepSeek（无条件）→ 调用成功
展开步骤细节
  1. agent 发起 llm call → resolve 产出候选链：[Kimi(带时间), DeepSeek(无条件), ...]
  2. attempt 循环 ① 时间过滤：当前小时 = 1，Kimi 的 hours=[2..23] 不含 1 → 跳过（skipped），不消耗尝试、不计熔断失败
  3. ② 熔断检查：DeepSeek 无熔断 → 放行；③ bannedModels 无 DeepSeek
  4. ④ 发起 DeepSeek 调用 → 成功 → 返回结果
state.tried = [ { item: kimi(priority 1), status: 'skipped' }, // 时间过滤未命中 { item: deepseek(priority 2), status: 'called' } // 成功 ]
B 熔断三态：Closed →（连续失败 4 次）→ Open →（等 60s）→ HalfOpen 探测 → 成功×2 → Closed
Closed（全部放行）→ 连续失败 ≥ 4 → Open→ 等 60s → HalfOpen（限流 1 探测）→ 探测成功 ×2 → Closed 
       连续失败 ≥ failure_threshold  或 (total ≥ min_requests 且 error_rate ≥ error_rate_threshold)
Closed ──────────────────────────────────────────────────────────────────────► Open
  ▲                                                                              │
  │ 半开连续成功 ≥ success_threshold                                             │ timeout_seconds 到期
  │ ◄────────────────────────────────────────── HalfOpen ◄──────────────────────┘
                                                      │ 限流 1 探测请求
                                                      │ 探测失败 → 立即回 Open
展开步骤细节
  1. 熔断键 = (planId, providerId, modelId) 三维，挂方案实体维度——方案 A 里 Kimi 熔断 ≠ 方案 B 里 Kimi 熔断；同一方案多处挂载共享熔断状态
  2. Closed：全部放行。连续 4 次调用失败（任何错误类别都计失败，老板 D1）→ 状态机转 Open
  3. Open：拒绝该模型请求（该条目 skipped + 进 bannedModels）→ 等待 timeout_seconds = 60s 到期
  4. HalfOpen：放行 1 个真实用户请求做探测（零额外成本）；探测成功 → success 计数；连续 2 次成功 → 回 Closed
  5. 探测失败 → 立即回 Open（重新计时）；半开 permit 必须归还（防卡死，对齐 cc-switch release_half_open_permit）
circuit[planId+moonshot+kimi-k2] = { state: 'Open', openedAt: t0, ... } // 熔断状态属 Config（跨 call 共享存活），不持久化，重启丢失可接受
C 降级链：P1 Kimi 失败(超时) → 重试 1 次再失败 → P2 DeepSeek 成功
P1 Kimi 调用→ TIMEOUT（看门狗）→ 模型内重试 1 次→ 再失败 → failed→ 退避 sleep→ P2 DeepSeek 成功
展开步骤细节
  1. P1 Kimi 发起调用 → 首 chunk 超时（看门狗 TTFB 45s 触发）
  2. 错误类别 TIMEOUT_FIRST_CHUNK → 模型内重试次数 = 1 → 退避后重试 1 次
  3. 重试仍失败 → record failed（原因：超时）→ 降级：cursor 前进到 P2
  4. 换模型降级可 0 sleep 或短 sleep（决策 = f(config, state) 可复现）→ P2 DeepSeek 调用成功 → 返回结果
  5. Kimi 失败计入熔断计数（连续失败 +1）——但未达阈值 4，熔断仍 Closed
state.tried = [ { item: kimi, status: 'failed', error: TIMEOUT_FIRST_CHUNK, attemptCount: 2 }, // 1 次重试后仍失败 { item: deepseek, status: 'called' } // 成功 ]
D 模型去重：Kimi 带时间 item 失败放弃 → bannedModels 含 Kimi → 后面 Kimi 无条件 item 跳过（即使配置了）
放弃/熔断挂钩模型配置（providerId+modelId），不是 item（老板 10:55）——同一模型在一次 attempt 内可能以多个 item 出现（session 合成 + 带时间 + 无条件），一旦被放弃/熔断，本次 attempt 内后续该模型全部 skipped。
候选链：[Kimi(带时间 P1), DeepSeek(P2), Kimi(无条件 P3), GLM(P4)]
P1 Kimi 带时间 → 调用→ 401 AUTH_INVALID → abandoned→ Kimi 进 bannedModels→ P2 DeepSeek 成功
P3 Kimi 无条件（已配置）→ 因 bannedModels 含 Kimi → skipped（不再尝试）
展开步骤细节
  1. 候选链含两个 Kimi 条目：P1 带时间（2–23 点）+ P3 无条件——这是合法配置（同模型最多 2 条，带时间在上）
  2. P1 Kimi 调用 → 401 AUTH_INVALID → 直接熔断 Open + 快速失败放弃（abandoned）（凭证失效短期不恢复）
  3. Kimi 模型配置（moonshot+kimi-k2）加入本次 call 的 bannedModels
  4. P2 DeepSeek 调用成功 → 返回结果
  5. 关键：即使 P3 配置了 Kimi 无条件条目，也不会再尝试（skipped）——同一模型一次 attempt 只尝试一次
state.tried = [ { item: kimi(带时间), status: 'abandoned', error: AUTH_INVALID }, { item: deepseek, status: 'called' }, { item: kimi(无条件), status: 'skipped' } // bannedModels 含 moonshot+kimi-k2 → 跳过 ] state.bannedModels = { "moonshot+kimi-k2" }
E resolve 双分支：session default vs session 显式模型（priority 0 合成）
group 挂载了方案「主力+兜底」。session 的 model 选择决定候选链起点。
session.modelId候选链说明
'default' [Kimi(P1), DeepSeek(P2), GLM(P3), GLM(P4)] = 方案 items 本身 直接走方案链，无合成
显式模型（如 glm-4.6） [glm-4.6(P0 合成), Kimi(P1), DeepSeek(P2), GLM(P3), GLM(P4)] session 模型作为 priority 0 插入顶部；临时合成不写回方案实体；熔断键 = planId + session 模型
展开步骤细节（显式模型分支）
  1. resolve(session, group)：group 有方案 → 分支 2；session.modelId ≠ default（显式配了 glm-4.6）
  2. 合成候选链：glm-4.6 作为 priority 0 插入方案顶部——优先用用户显式选的模型
  3. 合成只发生在内存（临时），不写回方案实体（方案库不变）
  4. 熔断键 = (planId, zhipu, glm-4.6) —— session 显式模型也享受方案熔断控制（同一方案内与 P3/P4 的 GLM 条目共享熔断状态）
  5. 若 P0 glm-4.6 失败被放弃 → bannedModels 含 zhipu+glm-4.6 → 后续 P3/P4 的 GLM 条目也 skipped（同模型去重，场景 D 机制）
resolve 产出（分支 2 · 显式模型）： 合成链 = [ { model: glm-4.6, priority: 0, 来源: session }, // 不写回 { model: kimi-k2, priority: 1, 来源: plan.items }, ... ] circuitKey = planId + "zhipu" + "glm-4.6" // 共享方案熔断
