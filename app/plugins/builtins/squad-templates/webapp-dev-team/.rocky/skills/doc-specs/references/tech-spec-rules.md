# 技术设计文档规范（OKF 版）

> tech specs 用 **OKF**（Open Knowledge Format）组织：`specs/tech/` 是一个 OKF 知识库，每个子系统目录是一个 KB。
> OKF 方法本身（业务无关）见 `.rocky/skills/okf-skill/`；本文是 tech specs **怎么用 OKF** 的消费规范。
> 三层叠加：`convention.md`（格式：命名/ID/时间）+ 本规范（目录组织 + index/log + frontmatter）+ `docs_guide.md`（单文件怎么写，§2 必备章节）。

---

## 1. 知识库布局（每个子系统目录 = 一个 KB）

```
specs/tech/
├── index.md                          # 顶层总起（子系统导航）
├── <子系统>/                          # 一个 KB
│   ├── index.md                      # 子系统总起（5 章，§2）
│   ├── log.md                        # 本目录变更（ISO 倒序，§4）
│   ├── {topic}.md                    # 知识节点 = spec 文件（§3）
│   └── <子目录>/index.md             # 嵌套 KB（父 index 链向子 index）
└── version_logs/vX.Y/change_log.md   # 跨版本发布说明（§4）
```

- **入口名统一 `index.md`**（OKF 保留名）。现状 `README.md` / `overall.md` / `[P0]overview.md` 三种叫法 → 统一 `index.md`。
- `overall.md` 大全量 **并入 index.md**（按类拆流，§2.3），不再 index/overall 双存。

## 2. index.md（子系统总起，5 章）

读者读完应能回答：**这是什么、管不管某事、怎么嵌进系统、去哪个文件看细节。**

- **篇幅 60–120 行硬上限**（超 = 内容该下沉 topic 文件或 version_logs；否则退化成 monolith，如旧 squad/overall.md 26KB）。
- frontmatter：`type: index` + `title` + `priority` + `updated`。
- 5 章固定顺序：

| 章 | 必/选 | 含什么 | 不含 |
|---|---|---|---|
| ①是什么 | 必 | 1–2 段定位（解决什么/为谁/建在谁之上）+ **核心概念表**（3–8 个本子系统名词，一词一句） | 实现细节、字段、版本史 |
| ②边界 | 必 | 两列表「管 ｜ 不管(→别的 KB 链接)」 | 零件级归属（→ 单文件 §边界） |
| ③与系统的关系 | 必 | 一张 ASCII 关系图 + 对外协作点（注册到哪/被谁调用/依赖谁/注入哪） | 内部子模块细节 |
| ④核心设计原则 | 可选 | 3–6 条跨文件**稳定**不变量「结论 + 一句理由 + →详述链接」 | per-version 叙事(→version_logs)、单文件内部决策 |
| ⑤本目录导航 | 必 | 表「文档 ｜ 管什么(一句话) ｜ 优先级 ｜ 链接」；子目录单列指向子 index | 文件内章节 |

- **①概念表必备**：治"板块没头没脑"根因（术语无定义，读者不知道名词指什么后面全看不懂）。
- **④可选**：无跨文件不变量的小目录（如纯接口定义目录）省略，别硬凑。

### 2.3 overall.md 并入 index（按类拆流，不整块搬）

| overall 里的内容 | 去向 |
|---|---|
| 范围/文件索引/关系（稳定总起） | → index ①②③⑤ |
| 稳定核心概念 | → index ① 概念表 |
| 跨文件稳定不变量 | → index ④（压成一句 + 链接） |
| `[vX.Y]` per-version 落地叙事 | → **version_logs/vX.Y/** |
| 字段/schema/代码路径 | → 对应 topic spec 文件 |

**判据**：一句话含版本号/「本版本」/代码路径/字段名 → 不进 index。index 只留「抽象 + 稳定 + 指路」。

## 3. 单个 spec 文件

### 3.1 frontmatter（机器路由层）
```yaml
---
type: spec          # 唯一必填；细分可选 concept | interface | design
title: Squad 工具收敛
priority: P0        # P0|P1|P2，唯一权威（§5）
status: active      # active | draft | deprecated
updated: 2026-06-30 # 每次改必更
since: v0.0.33.2    # 可选：首次引入版本（替代正文"哪版引入"）
related: [x.md]     # 可选：相对路径链接（坏链容忍）
---
```
只有 `type` 必填（OKF 核心）；其余消费端宽容。`priority`/`since` 让正文彻底卸掉版本噪声。

### 3.2 章节（对齐 docs_guide §2）
| 章节 | 必/选 | 内容 |
|---|---|---|
| §1 概述 | **必（强约束）** | (a) 管什么/**不管什么**；(b) **范畴一句话**（讲人话不用黑话）；(c) **与外界如何交互**（注册到哪/被谁调用） |
| §2 接口定义 / 概念模型 | 必 | TS 类型+字段表（接口类）或 概念模型（设计类） |
| §3 设计决策 | 可选 | 结论 → 理由 → 反例（三段式） |
| §4 示例 | 可选 | 精简 JSON/TS，**禁 `...` 省略关键字段** |
| §5 边界 | 必 | 零件唯一归属表（跨文件不重叠） |
| ~~§6 版本~~ | **退役** | 版本信息全进 frontmatter + 两套 log |

**§1 概述升强约束**（治"文档/板块没头没脑"）：读者原话需求——①这文档讲什么 ②它和系统/外界如何交互；缺一不可。

### 3.3 现状 / log 分离（per-file）
- 正文 = **现状**：删所有 inline `[vX.Y]` / `[vX.Y modified]`，只描述"当前是什么"。
- 顶部多段 `> version: …` 版本史 → 删（"干了什么"去 log）；"某字段哪版引入"→ frontmatter `since` 或一句话，不堆段落。

## 4. 两套 log（正交两轴，都要）

| | per-KB `log.md` | 跨版本 `version_logs/vX.Y/change_log.md` |
|---|---|---|
| 切片轴 | **位置**（本目录/KB） | **版本**（一次发布跨所有子系统） |
| 粒度 | 一变更一行（精简） | 一版本一篇（详述：设计原则+文件清单+验证） |
| 回答 | 「这目录最近改了什么」 | 「vX.Y 发布到底干了什么、为什么」 |
| 谁写 | 改本目录文件的人随手记 | doc-modifier 版本收口时写 |

`log.md` 格式：ISO 倒序，`## YYYY-MM-DD · vX.Y` 分组，一行一 feature，行尾 → version_logs 详情指针。

## 5. frontmatter + 文件名（E2）

`priority` **唯一权威**落 frontmatter；`[P0]` 文件名前缀 = **可丢的速览镜像**（便于 `ls`/排序），与 frontmatter 冲突时**以 frontmatter 为准**，**不为去前缀专门 rename**（改名要同步所有相对链接 + 污染 git history；优先级速览看 index 导航表即可）。文件因别的原因改名时顺手去前缀。

## 6. 写作质量红线（OKF 不替代，仍强制）

以下任一不满足 = 不合格，打回重写：
1. **设计思路是废话** — "为了性能""便于维护""提高可靠性"等无信息量表述。写不出具体"如果不这样会怎样"就不要写。
   - 好：「Live 和 Replay 分离，因为 Topic 层只管语义、不关心投递节奏，同一 Topic 可被不同节奏 Channel 消费」
2. **代码路径不精确** — 必须 `文件.方法() → 文件.方法()`，精确到源文件+方法，覆盖 2-3 条端到端关键路径。
3. **接口只列签名不解释** — 每个 public/abstract 方法一句话说明。
4. **按版本碎片化** — 按领域组织成"当前现状"，不按版本拆文件（v014/v015 分开 = 错）。
5. **JSON 示例用 `...` 省略关键字段** — 被讨论的字段必须完整。
