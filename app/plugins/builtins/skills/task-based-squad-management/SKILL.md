# Task-Based Squad Management

> **方法论**：多 agent 团队按流水线（Pipeline）组织生产，每条流水线内部按 task 分类，item 在 task 甬道中流转，独立审核保障质量。一个团队可有多条流水线，流水线之间有上下游依赖。

---

## 1. 核心概念

| 概念 | 定义 | 举例 |
|---|---|---|
| **流水线（Pipeline）** | 一条完整的价值流，从源头到成品。每条流水线 = 一个独立看板 | 素材积累流水线、创意生产流水线、小说写作流水线 |
| **task** | 流水线内部的一类工作。task 是组织维度 | 正文提取 task、T1 概括 task、大纲 task、章节写作 task |
| **item** | 流经多个 task 的工作对象 | 一本书（素材线）、一个创意方案（创意线）、一部小说（写作线）|
| **甬道图** | item 在一条流水线各 task 间的流转状态视图 | A1: 正文提取✅ → T1🔄 → T2⏳ → 完成⏳ |

### 1.1 流水线之间的关系

```
流水线 1（素材积累）         流水线 2（创意生产）        流水线 3（小说写作）
书单→正文→T1→T2→完成  →  创意→原型→大纲→完成  →  章节→审稿→修改→完本
                          ↑ 上游产出 = 下游输入         ↑
```

- 流水线之间有**上下游依赖**：上游流水线的产出（如 T2 全局文档）是下游流水线的输入（如创意的素材）
- 每条流水线**独立看板**，task 不混在一起
- item 可以跨流水线（一本书既是素材线的 item，其规律又成为创意线的输入）
- 流水线可以按需启动，不必同时开

## 2. Task 分类与组织

### 2.1 每个 task 的要素

- **task 名称**：明确是哪类工作
- **task 目标**：这步做什么、产出什么
- **进度度量**：量化进度（如 380/1928 章 = 19.7%）
- **当前阻塞**：当前卡在哪
- **依赖关系**：哪个 task 必须先完成才能启动

### 2.2 task 内部子阶段（生产-审核循环）

一个 task 不是简单的 in_progress，而是内部循环：

```
生产（工作员在工作区做）
  → 提审（工作员 cp 到提审区，通知审核员）
    → 审核（审核员只读提审区，盲评）
      → PASS → 转交付区 → item 进入下一 task
      → FAIL → 退回工作区 → 工作员修复后提 v2 → 再审
```

## 3. 团队架构

### 3.1 核心原则：每类 task 尽量有独立的工作员和审核员

| 角色 | 职责 |
|---|---|
| **工作员** | 在自己的工作区生产产出 |
| **审核员** | 只读提审区，盲评产出质量（不看工作报告）|
| **leader** | 派单、转交付、协调瓶颈、与老板对齐 |

### 3.2 铁律

- **审核员不能审核自己的产出**
- **审核员不跨 task**（正文审查员审原文，概括审查员审 T1，不交叉）
- **瓶颈可加人**：生产慢加工作员，审核慢加审核员（分片并行）
- 跨流水线的成员：一条流水线的审核员可以是另一条流水线的工作员（只要不在同一条线内自审）

### 3.3 招聘弹性

- 发现瓶颈 → leader 判断是生产端还是审核端 → hire 对应角色
- 新流水线启动 → 可能需要全新角色（如创意生产线需要「创意策划员」）
- 向老板申请 hire，说明瓶颈和预期效果

## 4. 文件三区

### 4.1 目录结构

```
outputs/
├── 工作区/                    # 所有工作在这里做
│   └── {member名}/            # 每个 member 一个目录 = 工作主阵地
│       └── {item}/            # 按 item 再拆分
├── 提审区/                    # 待审核·保留多版本
│   └── {task类型}/            # 按 task 类型分（原文/T1/T2/大纲/章节...）
│       └── {item}/            # 按 item 分
│           └── v{N}/          # 按版本分（v1/v2/v3 不覆盖）
├── 交付区/                    # 审核通过的最新正式产出
│   └── {task类型}/
│       └── {item}/            # 只放最终 PASS 版
└── 不合格区/（可选）          # 审核不通过·待修复
```

### 4.2 三区规则

| 区 | 谁写 | 规则 |
|---|---|---|
| **工作区** | 各工作员 | 自由操作，试错、草稿都在这里 |
| **提审区** | 工作员 cp（不 mv）| **保留多版本**，不覆盖。提审 = cp + 通知 |
| **交付区** | **leader 整理** | 只放最终 PASS 版，严禁历史版本/过程稿 |
| **不合格区** | 审核员标记 | FAIL 版本隔离，修复后重新提审 |

### 4.3 流转规则

```
工作区 →[cp]→ 提审区 →[PASS]→ [leader cp] → 交付区
                    ↓
              [FAIL] → 工作区修复 →[cp]→ 提审区 v2 → 再审
```

## 5. 全景视图

### 5.1 Task 视图（每条流水线内，每个 task 一行）

| Task | 状态 | 工作员 | 审核员 | 进度 | 阻塞 | 依赖 |
|---|---|---|---|---|---|---|
| 正文提取 | in_progress | 淘书专家 | 正文审查员 | 10/10 本 | A4 缺口 | 无 |
| T1 概括 | in_progress | T1概括员 | 概括审查员×2 | 380/1928 | ch381-400 复验中 | 正文提取 PASS |
| T2 概括 | not_started | T2概括员 | 概括审查员×2 | 0/1 | - | T1 整本 PASS |

### 5.2 甬道图（item 在 task 间的流转）

item 在每个 task 节点的状态：

| 状态 | 含义 |
|---|---|
| ⏳ 未进入 | item 还没到这个 task |
| 🔧 加工中 | 工作员正在做 |
| 📋 提审中 | 已提审，等审核员 |
| 🔍 审核中 | 审核员正在审 |
| ✅ PASS | 审核通过，进入下一 task |
| ❌ FAIL | 退回修复 |

示例：

| Item | 正文提取 | T1 概括 | T2 概括 |
|---|---|---|---|
| A1《我不是戏神》| ✅ PASS | 🔧 380/1928 | ⏳ 未进入 |
| B1《诡秘之主》| ✅ PASS | ⏳ 未进入 | ⏳ 未进入 |

### 5.3 流水线总览（跨流水线）

| 流水线 | 状态 | item 数量 | 关键产出 |
|---|---|---|---|
| 素材积累 | 🔄 运行中 | 10 本 | 原文/T1/T2 |
| 创意生产 | ⏳ 待启动 | 0 | 创意/原型/大纲 |
| 小说写作 | ⏳ 待启动 | 0 | 章节作品 |

## 6. 多流水线架构

### 6.1 为什么需要多流水线

终极目标不是「分析小说」，而是「写出爆款小说」。分析只是第一步。完整的业务需要多条流水线串联：

```
素材积累 → 创意生产 → 小说写作
(What works) → (What to create) → (How to write)
```

### 6.2 流水线设计原则

- **独立看板**：每条流水线有自己的 task 视图 + 甬道图
- **上下游依赖**：上游流水线的交付区 = 下游流水线的输入源
- **按需启动**：不必同时开，上游积累够了一定数据再启动下游
- **角色可复用**：同一个人在不同流水线可以扮演不同角色（只要不自审）
- **文件隔离**：每条流水线的三区目录可以按流水线前缀区分（如 `交付区/素材-T1/` vs `交付区/写作-章节/`）

### 6.3 流水线间交接

上游流水线的最终交付 → 下游流水线的起点：

```
素材线交付区/T2/A1/全局文档.md → 创意线输入（作为创意的素材参考）
创意线交付区/大纲/方案X/大纲.md → 写作线输入（作为章节写作的蓝本）
```

交接时 leader 确认：上游产出已 PASS + 下游输入路径明确。

---

## 7. Leader 职责

### 7.1 核心循环

1. **接需求** → 判断属于哪条流水线 → 拆 task
2. **派单** → send_message（目标+输入路径+产出路径+红线+节奏）
3. **收交付** → 审核员 PASS → leader 转交付区
4. **跟瓶颈** → 哪个 task 卡了 → 加人/调资源
5. **跨线协调** → 上游交付够了吗？可以启动下游了吗？
6. **对齐老板** → 重要决策找老板确认

### 7.2 leader 不做

- ❌ 不直接编码/生产
- ❌ 不审核（审核员独立盲评）
- ❌ 不动工作员的工作区

---

## 8. 实施检查清单

新流水线启动时：

- [ ] 这条流水线的 item 是什么？
- [ ] item 经过哪些 task？（画出甬道）
- [ ] 每个 task 的工作员和审核员是谁？需要 hire 吗？
- [ ] 三区目录建好
- [ ] 上游流水线的交付准备好了吗？
- [ ] 全景看板定义好（task 视图 + 甬道图）
- [ ] 审核标准工作员+审核员双方对齐

## 附录：与 panorama 工具的关系

- **task 视图** = panorama task entity（标准看板）
- **甬道图** = panorama 自定义 entity（DSL 定义 item entity + 状态机）

- task.status: todo → in_progress → done
- item.stage: 未进入 → 加工中 → 提审中 → 审核中 → PASS → FAIL
